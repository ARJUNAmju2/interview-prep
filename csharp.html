2 Q2. What is an object in C#? ▼ 
An Object is an instance of a class. It is a real-world entity created in 
memory that has state (data/properties) and behavior (methods).

Key points:
- Object is created using the 'new' keyword
- Memory is allocated on the HEAP when object is created
- Object has actual values for properties defined in the class
- Multiple objects can be created from the same class
- Each object is independent (has its own copy of data)

Example:
public class Car
{
    // State (properties)
    public string Brand { get; set; }
    public string Color { get; set; }
    public int Speed { get; set; }
    
    // Behavior (methods)
    public void Start()
    {
        Console.WriteLine($"{Brand} started");
    }
    
    public void Accelerate(int amount)
    {
        Speed += amount;
    }
}

// Creating objects (instances)
Car car1 = new Car { Brand = "Toyota", Color = "Red", Speed = 0 };
Car car2 = new Car { Brand = "BMW", Color = "Black", Speed = 0 };

car1.Start();          // "Toyota started"
car1.Accelerate(60);   // car1.Speed = 60
// car2.Speed is still 0 (independent object)

Object characteristics:
- Identity: Each object is unique (different memory address)
- State: Current values of its properties
- Behavior: Methods it can perform

In C#, everything derives from System.Object:
- ToString()        ? String representation
- Equals()          ? Equality check
- GetHashCode()     ? Hash code for collections
- GetType()         ? Runtime type information
3 Q3. What is Managed or Unmanaged Code? ▼ 
MANAGED CODE:
Code that runs under the control of the CLR (Common Language Runtime).
CLR provides automatic memory management, type safety, and exception handling.

- Executed by CLR
- Automatic Garbage Collection (no manual memory free)
- Type safety enforced
- Exception handling built-in
- Security (Code Access Security)
- Cross-language interoperability
- Examples: C#, VB.NET, F# code

public class Employee
{
    public string Name { get; set; }
}
var emp = new Employee();  // CLR manages memory
// No need to free memory � GC handles it

UNMANAGED CODE:
Code that runs directly on the operating system, outside CLR control.
Developer is responsible for memory allocation and deallocation.

- Executed directly by OS
- Manual memory management (malloc/free)
- No automatic garbage collection
- Can cause memory leaks, buffer overflows
- Faster in some cases (no CLR overhead)
- Examples: C, C++, COM components, Win32 API calls

// Calling unmanaged code from C# using P/Invoke:
[DllImport("user32.dll")]
static extern int MessageBox(IntPtr hWnd, string text, string caption, int type);

// Or using COM interop:
// Excel, Word automation

Comparison:
| Feature          | Managed Code         | Unmanaged Code       |
|------------------|----------------------|----------------------|
| Executed by      | CLR                  | OS directly          |
| Memory           | Automatic (GC)       | Manual               |
| Type safety      | Yes                  | No                   |
| Security         | CLR enforced         | Developer handles    |
| Performance      | Slight overhead      | Potentially faster   |
| Memory leaks     | Rare                 | Common               |
| Languages        | C#, VB.NET, F#       | C, C++, Assembly     |

Interop (using unmanaged from managed):
- P/Invoke: Call native DLL functions
- COM Interop: Use COM components
- unsafe keyword: Pointer operations in C#

unsafe
{
    int x = 10;
    int* ptr = &x;  // Pointer � unmanaged-style code in C#
}
4 Q4. What is Boxing and Unboxing in C#? ▼ 
BOXING:
Converting a VALUE TYPE to a REFERENCE TYPE (object).
The value is copied from Stack to Heap, wrapped inside an object.

int number = 42;          // Value type (Stack)
object obj = number;      // Boxing: int ? object (copied to Heap)

What happens internally:
1. Memory allocated on Heap
2. Value copied from Stack to Heap
3. Reference to heap object stored

UNBOXING:
Converting a REFERENCE TYPE (object) back to a VALUE TYPE.
The value is copied from Heap back to Stack.

object obj = 42;          // Boxed int on Heap
int number = (int)obj;    // Unboxing: object ? int (copied to Stack)

What happens internally:
1. Check if object actually contains the expected type
2. If type mismatch ? InvalidCastException
3. Value copied from Heap to Stack

Example:
int x = 10;
object boxed = x;         // Boxing (implicit, no cast needed)
int y = (int)boxed;       // Unboxing (explicit cast required)

// Type must match exactly:
object boxed = 10;        // Boxed as int
// double d = (double)boxed;  // ERROR! InvalidCastException
// Must unbox to original type first:
double d = (double)(int)boxed;  // OK: unbox to int, then convert

Performance impact:
// BAD - Boxing in every iteration:
ArrayList list = new ArrayList();
for (int i = 0; i < 1000000; i++)
{
    list.Add(i);  // Boxing! int ? object (1 million times)
}

// GOOD - No boxing with generics:
List<int> list = new List<int>();
for (int i = 0; i < 1000000; i++)
{
    list.Add(i);  // No boxing! Stays as int
}

Common boxing scenarios:
int x = 5;
Console.WriteLine("Value: " + x);       // x boxed for concatenation
string.Format("{0}", x);                 // Boxing
object[] arr = { 1, 2, 3 };             // All values boxed
IComparable comp = x;                   // Boxing (interface is ref type)

Why avoid boxing:
- Heap allocation (memory pressure)
- Garbage Collection overhead
- Copying data between Stack and Heap
- Slower than direct value type operations
- Use Generics (List<int>) to avoid boxing
5 Q5. What is the difference between a struct and a class in C#? ▼ 
STRUCT (Value Type):
- Stored on STACK
- Holds actual data directly
- Copied by VALUE (independent copies)
- Cannot be null (unless Nullable<T>)
- Cannot inherit from another struct/class
- Implicitly sealed (cannot be base class)
- No destructor/finalizer
- Lightweight, faster for small data
- Default constructor initializes all fields to default

STRUCT example:
public struct Point
{
    public int X { get; set; }
    public int Y { get; set; }
    
    public Point(int x, int y)
    {
        X = x;
        Y = y;
    }
}

Point p1 = new Point(10, 20);
Point p2 = p1;    // COPIES entire value
p2.X = 99;
// p1.X is still 10 (independent copy)

CLASS (Reference Type):
- Stored on HEAP (reference on Stack)
- Holds reference (address) to data
- Copied by REFERENCE (both point to same object)
- Can be null
- Supports inheritance
- Can be sealed or abstract
- Can have destructor/finalizer
- More overhead (GC, heap allocation)

CLASS example:
public class Person
{
    public string Name { get; set; }
    public int Age { get; set; }
}

Person p1 = new Person { Name = "John", Age = 30 };
Person p2 = p1;    // COPIES reference (same object!)
p2.Name = "Jane";
// p1.Name is now "Jane" (same object modified!)

Detailed Comparison:
| Feature              | Struct               | Class                |
|----------------------|----------------------|----------------------|
| Type                 | Value type           | Reference type       |
| Storage              | Stack                | Heap                 |
| Assignment           | Copies data          | Copies reference     |
| Null                 | Cannot (unless T?)   | Can be null          |
| Inheritance          | No                   | Yes                  |
| Can be abstract      | No                   | Yes                  |
| Can be sealed        | Always (implicit)    | Optional             |
| Destructor           | No                   | Yes                  |
| Default constructor  | Always exists        | Only if no other     |
| Interface            | Can implement        | Can implement        |
| Performance          | Faster (no GC)       | GC overhead          |
| Best for             | Small, immutable     | Complex objects      |

When to use STRUCT:
- Small data (< 16 bytes recommended)
- Immutable data (read-only after creation)
- Frequently created/destroyed (avoid GC pressure)
- Logically represents a single value
- Examples: Point, Color, DateTime, Guid, int, decimal

When to use CLASS:
- Complex objects with behavior
- Need inheritance
- Need null reference
- Large data
- Long-lived objects
- Need to pass by reference
- Examples: Employee, Order, DbContext, Controller

Real-world .NET structs:
- int, double, bool, decimal (all primitives)
- DateTime, TimeSpan, Guid
- Point, Size, Rectangle
- KeyValuePair<K,V>
- Nullable<T>
6 Q6. What is the difference between Interface and Abstract Class in C#? ▼ 
ABSTRACT CLASS:
- Can have both abstract (no body) and concrete (with body) methods
- Can have fields, properties, constructors
- Can have access modifiers (private, protected, public)
- Supports SINGLE inheritance only
- Can maintain state (instance variables)
- Represents IS-A relationship
- Used when classes share common code + contract

public abstract class Animal
{
    protected string Name;  // Field with state
    
    public Animal(string name)  // Constructor
    {
        Name = name;
    }
    
    public abstract void Speak();  // Abstract - MUST override
    
    public void Breathe()  // Concrete - shared implementation
    {
        Console.WriteLine($"{Name} is breathing");
    }
    
    protected virtual void Sleep()  // Virtual - CAN override
    {
        Console.WriteLine("Sleeping 8 hours");
    }
}

public class Dog : Animal
{
    public Dog(string name) : base(name) { }
    
    public override void Speak()
    {
        Console.WriteLine($"{Name} says Woof!");
    }
}

INTERFACE:
- Only method signatures (no implementation, before C# 8)
- Cannot have fields (no state)
- Cannot have constructors
- All members are implicitly public
- Supports MULTIPLE implementation
- Cannot maintain state
- Represents CAN-DO relationship (capability/contract)
- Used for loose coupling and DI

public interface IFlyable
{
    void Fly();
    int MaxAltitude { get; }
}

public interface ISwimmable
{
    void Swim();
    int MaxDepth { get; }
}

// Multiple interfaces - OK!
public class Duck : Animal, IFlyable, ISwimmable
{
    public Duck() : base("Duck") { }
    
    public override void Speak() => Console.WriteLine("Quack!");
    public void Fly() => Console.WriteLine("Duck flying");
    public void Swim() => Console.WriteLine("Duck swimming");
    public int MaxAltitude => 1000;
    public int MaxDepth => 5;
}

DEFAULT INTERFACE METHODS (C# 8+):
public interface ILogger
{
    void Log(string message);
    
    // Default implementation (optional to override)
    void LogError(string message)
    {
        Log($"ERROR: {message}");
    }
}

DETAILED COMPARISON:
| Feature              | Abstract Class         | Interface              |
|----------------------|------------------------|------------------------|
| Methods              | Abstract + Concrete    | Abstract only (pre C#8)|
| Default impl.       | Yes (always)           | Yes (C# 8+ only)      |
| Fields               | Yes                    | No                     |
| Properties           | Full (with backing)    | Declaration only       |
| Constructor          | Yes                    | No                     |
| Access modifiers     | Any (private, etc.)    | Public (implicit)      |
| Inheritance          | Single only            | Multiple               |
| State                | Can hold state         | Cannot hold state      |
| Static members       | Yes                    | Yes (C# 8+)           |
| Sealed               | Can be sealed method   | No                     |
| Instantiation        | Cannot                 | Cannot                 |

WHEN TO USE ABSTRACT CLASS:
- Related classes sharing common code
- Need fields/state
- Need constructors for initialization
- Need access modifiers (protected members)
- Base class with some default behavior
- Example: Shape ? Circle, Rectangle (share Color, Area logic)

WHEN TO USE INTERFACE:
- Unrelated classes sharing a contract
- Need multiple inheritance
- Dependency Injection (loose coupling)
- Define capability (what it CAN do)
- Testability (mock interfaces)
- Example: IDisposable, IComparable, ILogger

REAL-WORLD EXAMPLE (both together):
public interface INotificationService
{
    Task SendAsync(string to, string message);
}

public abstract class NotificationBase : INotificationService
{
    protected readonly ILogger _logger;
    
    protected NotificationBase(ILogger logger)
    {
        _logger = logger;
    }
    
    public async Task SendAsync(string to, string message)
    {
        _logger.LogInformation($"Sending to {to}");
        await SendInternalAsync(to, message);
    }
    
    protected abstract Task SendInternalAsync(string to, string message);
}

public class EmailService : NotificationBase
{
    public EmailService(ILogger logger) : base(logger) { }
    
    protected override async Task SendInternalAsync(string to, string message)
    {
        // Email-specific logic
    }
}

public class SmsService : NotificationBase
{
    public SmsService(ILogger logger) : base(logger) { }
    
    protected override async Task SendInternalAsync(string to, string message)
    {
        // SMS-specific logic
    }
}

// DI registration uses interface:
builder.Services.AddScoped<INotificationService, EmailService>();
7 Q7. What is an enum in C#? ▼ 
An Enum (Enumeration) is a value type that defines a set of named constants 
representing integer values. It makes code more readable and type-safe.

Basic enum:
public enum DayOfWeek
{
    Sunday,     // 0 (default starts from 0)
    Monday,     // 1
    Tuesday,    // 2
    Wednesday,  // 3
    Thursday,   // 4
    Friday,     // 5
    Saturday    // 6
}

// Usage
DayOfWeek today = DayOfWeek.Monday;
Console.WriteLine(today);        // "Monday"
Console.WriteLine((int)today);   // 1

Custom values:
public enum HttpStatusCode
{
    OK = 200,
    Created = 201,
    BadRequest = 400,
    Unauthorized = 401,
    NotFound = 404,
    InternalServerError = 500
}

int code = (int)HttpStatusCode.NotFound;  // 404

Enum with specific underlying type:
public enum FileSize : long  // Default is int
{
    KB = 1024,
    MB = 1024 * 1024,
    GB = 1024 * 1024 * 1024
}

Flags enum (bitwise combinations):
[Flags]
public enum Permissions
{
    None = 0,
    Read = 1,       // 0001
    Write = 2,      // 0010
    Execute = 4,    // 0100
    Delete = 8,     // 1000
    All = Read | Write | Execute | Delete  // 1111
}

// Combine permissions
Permissions userPerms = Permissions.Read | Permissions.Write;
Console.WriteLine(userPerms);  // "Read, Write"

// Check permission
bool canWrite = userPerms.HasFlag(Permissions.Write);  // true
bool canDelete = userPerms.HasFlag(Permissions.Delete); // false

Common operations:
// String to enum
DayOfWeek day = Enum.Parse<DayOfWeek>("Monday");
bool success = Enum.TryParse<DayOfWeek>("Monday", out DayOfWeek result);

// Get all values
DayOfWeek[] allDays = Enum.GetValues<DayOfWeek>();

// Get all names
string[] names = Enum.GetNames<DayOfWeek>();

// Check if value is defined
bool valid = Enum.IsDefined(typeof(DayOfWeek), 5);  // true (Friday)

Real-world usage:
public enum OrderStatus
{
    Pending,
    Processing,
    Shipped,
    Delivered,
    Cancelled
}

public class Order
{
    public int Id { get; set; }
    public OrderStatus Status { get; set; }
}

// Clean, readable code:
if (order.Status == OrderStatus.Shipped)
{
    SendTrackingEmail();
}

// Instead of magic numbers:
// if (order.Status == 2)  // What does 2 mean? Unclear!

Benefits:
- Readable code (named constants instead of magic numbers)
- Type safety (can't assign invalid values easily)
- IntelliSense support
- Easy to maintain (change value in one place)
- Good for fixed set of options (status, days, directions)
8 Q8. What is the difference between "continue" and "break" statements in C#? ▼ 
BREAK:
- EXITS the entire loop immediately
- No more iterations execute
- Control moves to the statement AFTER the loop

for (int i = 1; i <= 10; i++)
{
    if (i == 5)
        break;  // Exit loop completely
    Console.Write(i + " ");
}
// Output: 1 2 3 4
// Loop stops at 5, doesn't continue to 6, 7, 8...

CONTINUE:
- SKIPS the current iteration only
- Jumps to the NEXT iteration of the loop
- Loop continues running

for (int i = 1; i <= 10; i++)
{
    if (i == 5)
        continue;  // Skip this iteration, go to next
    Console.Write(i + " ");
}
// Output: 1 2 3 4 6 7 8 9 10
// Only 5 is skipped, rest continues

Comparison:
| Feature        | break                  | continue               |
|----------------|------------------------|------------------------|
| Action         | Exits entire loop      | Skips current iteration|
| Loop continues | No                     | Yes (next iteration)   |
| Control goes   | After the loop         | Loop's next iteration  |
| Use case       | Stop when found        | Skip unwanted items    |

Practical examples:

// break - Search and stop when found:
string[] names = { "John", "Jane", "Bob", "Alice" };
foreach (var name in names)
{
    if (name == "Bob")
    {
        Console.WriteLine("Found Bob!");
        break;  // No need to check remaining
    }
}

// continue - Skip invalid items:
int[] numbers = { 1, -2, 3, -4, 5, -6 };
int sum = 0;
foreach (var num in numbers)
{
    if (num < 0)
        continue;  // Skip negative numbers
    sum += num;
}
// sum = 9 (1 + 3 + 5)

// break in switch statement:
switch (day)
{
    case "Monday":
        Console.WriteLine("Start of week");
        break;  // Exit switch (required in C#)
    case "Friday":
        Console.WriteLine("Weekend coming!");
        break;
}

// break in nested loops (exits inner loop only):
for (int i = 0; i < 3; i++)
{
    for (int j = 0; j < 3; j++)
    {
        if (j == 2)
            break;  // Exits inner loop only
        Console.Write($"({i},{j}) ");
    }
}
// Output: (0,0) (0,1) (1,0) (1,1) (2,0) (2,1)
9 Q9. What is the difference between constant and readonly in C#? ▼ 
CONST (Compile-time constant):
- Value must be assigned at DECLARATION only
- Cannot be changed anywhere (ever)
- Implicitly STATIC (accessed via class name)
- Value is embedded in IL code at compile time
- Only primitive types + string allowed
- Faster (value inlined by compiler)

public class Config
{
    public const double PI = 3.14159;
    public const string AppName = "MyApp";
    public const int MaxRetries = 3;
    
    // const DateTime Now = DateTime.Now;  // ERROR! Not compile-time value
    // const List<int> Items = new List<int>();  // ERROR! Not primitive
}

// Access via class name (static):
double area = Config.PI * radius * radius;

READONLY (Runtime constant):
- Value can be assigned at DECLARATION or in CONSTRUCTOR
- Cannot be changed after constructor completes
- Can be INSTANCE or STATIC
- Value resolved at RUNTIME
- ANY type allowed (objects, collections, DateTime)
- Slightly slower (runtime resolution)

public class Config
{
    public readonly DateTime CreatedAt = DateTime.Now;  // Runtime value OK
    public readonly string ConnectionString;
    public static readonly int MaxUsers = LoadFromConfig();
    public readonly List<string> AllowedRoles;
    
    public Config(string connStr)
    {
        ConnectionString = connStr;  // Set in constructor - OK
        AllowedRoles = new List<string> { "Admin", "User" };
    }
    
    public void SomeMethod()
    {
        // ConnectionString = "new";  // ERROR! Cannot change after constructor
        AllowedRoles.Add("Manager");  // OK! List itself is readonly, not its contents
    }
}

DETAILED COMPARISON:
| Feature          | const                  | readonly               |
|------------------|------------------------|------------------------|
| Assigned at      | Declaration only       | Declaration/Constructor|
| When resolved    | Compile-time           | Runtime                |
| Static           | Always (implicit)      | Can be instance/static |
| Types allowed    | Primitives + string    | Any type               |
| Can use new      | No                     | Yes                    |
| Performance      | Slightly faster        | Normal                 |
| Memory           | No allocation (inlined)| Allocated              |
| Versioning       | Dangerous (see below)  | Safe                   |

VERSIONING PROBLEM WITH CONST:
// Assembly A (Library):
public class Settings
{
    public const int Version = 1;  // Compiled into all consumers
}

// Assembly B (Consumer):
Console.WriteLine(Settings.Version);  // Compiler puts literal 1 here

// If Assembly A changes to Version = 2 and recompiles:
// Assembly B STILL shows 1 (old value baked in at compile time!)
// Assembly B must ALSO be recompiled!

// With readonly � no problem:
public static readonly int Version = 1;
// Assembly B always reads current value at runtime

WHEN TO USE:
- const: True constants that NEVER change across versions
  - Math.PI, days in week, fixed config values
  
- readonly: Values set at runtime or might change between versions
  - Connection strings, configuration, DateTime.Now
  - Objects, collections, computed values

STATIC READONLY vs CONST:
public static readonly int MaxSize = CalculateMax();  // Can use method
public const int MaxSize = 100;  // Must be literal value

// static readonly = runtime constant (flexible)
// const = compile-time constant (rigid but faster)
10 Q10. What is the difference between ref and out keywords? ▼ 
Both pass parameters BY REFERENCE (not by value), meaning the method can 
modify the original variable. But they have different rules.

REF:
- Variable MUST be initialized BEFORE passing
- Method MAY or MAY NOT modify the value
- Used when method needs to READ and MODIFY the value

void DoubleIt(ref int number)
{
    number = number * 2;  // Read and modify
}

int x = 5;          // Must be initialized
DoubleIt(ref x);
Console.WriteLine(x);  // 10 (modified)

OUT:
- Variable does NOT need to be initialized before passing
- Method MUST assign a value before returning
- Used when method needs to RETURN multiple values

void GetMinMax(int[] arr, out int min, out int max)
{
    min = arr.Min();  // Must assign before method ends
    max = arr.Max();  // Must assign before method ends
}

int min, max;  // No initialization needed
GetMinMax(new[] { 3, 1, 7, 2 }, out min, out max);
Console.WriteLine($"Min: {min}, Max: {max}");  // Min: 1, Max: 7

// C# 7+ inline declaration:
GetMinMax(new[] { 3, 1, 7, 2 }, out int minimum, out int maximum);

// Discard unwanted out parameters:
GetMinMax(new[] { 3, 1, 7, 2 }, out int minVal, out _);  // Ignore max

COMPARISON:
| Feature              | ref                    | out                    |
|----------------------|------------------------|------------------------|
| Initialize before    | YES (required)         | NO (not required)      |
| Assign in method     | Optional               | REQUIRED               |
| Direction            | Two-way (in + out)     | Out only               |
| Purpose              | Read + Modify          | Return extra values    |
| Common use           | Modify existing value  | TryParse pattern       |

COMMON REAL-WORLD EXAMPLES:

// out - TryParse pattern (most common):
string input = "123";
if (int.TryParse(input, out int result))
{
    Console.WriteLine($"Parsed: {result}");  // 123
}
else
{
    Console.WriteLine("Invalid number");
}

// out - Dictionary.TryGetValue:
var dict = new Dictionary<string, int> { ["age"] = 30 };
if (dict.TryGetValue("age", out int age))
{
    Console.WriteLine(age);  // 30
}

// ref - Swap two values:
void Swap(ref int a, ref int b)
{
    int temp = a;
    a = b;
    b = temp;
}

int x = 10, y = 20;
Swap(ref x, ref y);
// x = 20, y = 10

// ref - Modify struct (value type):
void MoveRight(ref Point p)
{
    p.X += 10;
}

Point point = new Point { X = 0, Y = 0 };
MoveRight(ref point);
// point.X = 10

IN KEYWORD (C# 7.2) - Read-only reference:
void PrintDistance(in Point p)
{
    // p.X = 10;  // ERROR! Cannot modify 'in' parameter
    Console.WriteLine(Math.Sqrt(p.X * p.X + p.Y * p.Y));
}
// Passes by reference (no copy) but prevents modification
// Good for large structs (avoids copy without allowing changes)

SUMMARY:
| Keyword | Must init before | Must assign in method | Can read | Can modify |
|---------|------------------|----------------------|----------|------------|
| ref     | YES              | NO                   | YES      | YES        |
| out     | NO               | YES                  | NO*      | YES        |
| in      | YES              | NO                   | YES      | NO         |

* out parameter should not be read before assigning
11 Q11. Can "this" be used within a static method? ▼ 
NO. "this" CANNOT be used inside a static method.

Reason:
- "this" refers to the CURRENT INSTANCE of the class
- Static methods belong to the CLASS, not to any instance
- Since there is no instance, there is no "this" to refer to

public class Employee
{
    public string Name { get; set; }
    public static int Count = 0;
    
    // Instance method - "this" works
    public void Display()
    {
        Console.WriteLine(this.Name);  // OK! Instance exists
    }
    
    // Static method - "this" does NOT work
    public static void ShowCount()
    {
        // Console.WriteLine(this.Name);  // ERROR! 'this' not valid in static
        // this.Display();                // ERROR!
        
        Console.WriteLine(Count);  // OK - accessing static member
    }
}

Why it makes sense:
- Static method can be called WITHOUT creating an object:
  Employee.ShowCount();  // No object ? no instance ? no "this"

14 Q14. What is the difference between Dispose and Finalize in C#? ▼ 
DISPOSE:
- Called by the DEVELOPER explicitly (or via 'using' statement)
- Deterministic � YOU control WHEN it runs
- Implements IDisposable interface
- Releases BOTH managed and unmanaged resources
- Fast and predictable
- Recommended approach

public class DatabaseConnection : IDisposable
{
    private SqlConnection _conn;
    
    public void Dispose()
    {
        _conn?.Close();
        _conn?.Dispose();
        GC.SuppressFinalize(this);  // Tell GC: no need to finalize
    }
}

// Usage:
using (var db = new DatabaseConnection())
{
    // Use db
}  // Dispose() called automatically here

// Or C# 8:
using var db = new DatabaseConnection();
// Dispose() called at end of scope

FINALIZE (Destructor):
- Called by the GARBAGE COLLECTOR automatically
- Non-deterministic � you DON'T know WHEN it runs
- Uses destructor syntax (~ClassName)
- Should release ONLY unmanaged resources
- Slow (adds GC overhead)
- Safety net if Dispose wasn't called

public class FileHandler
{
    private IntPtr _fileHandle;  // Unmanaged resource
    
    ~FileHandler()  // Finalizer
    {
        // Release unmanaged resources only
        CloseHandle(_fileHandle);
    }
}

COMPARISON:
| Feature          | Dispose              | Finalize (~)           |
|------------------|----------------------|------------------------|
| Called by        | Developer / using    | Garbage Collector      |
| When             | Deterministic (now)  | Non-deterministic      |
| Interface        | IDisposable          | Object.Finalize        |
| Syntax           | public void Dispose()| ~ClassName()           |
| Resources        | Managed + Unmanaged  | Unmanaged only         |
| Performance      | Fast                 | Slow (extra GC cycle)  |
| Control          | Full control         | No control             |
| Can be called    | Multiple times       | Only once by GC        |
| Inheritance      | Via interface        | Virtual (override)     |

WHY FINALIZE IS SLOW:
1. Object with finalizer goes to Finalization Queue
2. GC doesn't collect it in first pass
3. Finalizer thread runs the destructor
4. Object collected in NEXT GC cycle
5. Result: Object survives one extra generation (more memory pressure)

COMPLETE DISPOSE PATTERN (best practice):
public class ResourceManager : IDisposable
{
    private SqlConnection _connection;   // Managed resource
    private IntPtr _handle;              // Unmanaged resource
    private bool _disposed = false;
    
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);  // Skip finalizer (already cleaned up)
    }
    
    protected virtual void Dispose(bool disposing)
    {
        if (!_disposed)
        {
            if (disposing)
            {
                // Release MANAGED resources
                _connection?.Close();
                _connection?.Dispose();
            }
            
            // Release UNMANAGED resources (always)
            if (_handle != IntPtr.Zero)
            {
                CloseHandle(_handle);
                _handle = IntPtr.Zero;
            }
            
            _disposed = true;
        }
    }
    
    ~ResourceManager()  // Finalizer (safety net)
    {
        Dispose(false);  // Only unmanaged cleanup
    }
}

WHEN TO USE:
- Dispose: ALWAYS for classes holding resources (DB, files, streams, HTTP)
- Finalize: ONLY when wrapping unmanaged resources directly (rare)
- Most developers only need Dispose (finalize is for framework/library authors)

BEST PRACTICES:
1. Always implement IDisposable for resource-holding classes
2. Always use 'using' statement when consuming IDisposable objects
3. Call GC.SuppressFinalize(this) in Dispose
4. Make Dispose safe to call multiple times (check _disposed flag)
5. Avoid finalizers unless absolutely necessary
15 Q15. What is the difference between String and StringBuilder in C#? ▼ 
STRING (System.String):
- IMMUTABLE (cannot be changed after creation)
- Every modification creates a NEW string object in memory
- Old string becomes garbage (GC overhead)
- Good for: few modifications, short strings
- Thread-safe (immutable = safe)

string name = "Hello";
name += " World";   // Creates NEW string "Hello World"
name += "!";        // Creates ANOTHER new string "Hello World!"
// 3 string objects created in memory, 2 are garbage!

// What happens internally:
string s = "Hello";    // Object 1: "Hello"
s += " ";              // Object 2: "Hello " (Object 1 = garbage)
s += "World";          // Object 3: "Hello World" (Object 2 = garbage)

STRINGBUILDER (System.Text.StringBuilder):
- MUTABLE (modifies same object in memory)
- No new objects created on modification
- Uses internal buffer (resizes when needed)
- Good for: many modifications, loops, large strings
- NOT thread-safe

StringBuilder sb = new StringBuilder("Hello");
sb.Append(" World");   // Same object modified
sb.Append("!");        // Same object modified
string result = sb.ToString();  // "Hello World!"
// Only 1 object used throughout!

PERFORMANCE COMPARISON:
// BAD - String in loop (creates 10,000 objects!):

for (int i = 0; i < 10000; i++)
{
    result += i.ToString();  // New string object EVERY iteration!
}
// Very slow! O(n�) � each += copies entire string

// GOOD - StringBuilder in loop (1 object):
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10000; i++)
{
    sb.Append(i);  // Modifies same buffer
}
string result = sb.ToString();
// Very fast! O(n)

// Benchmark (approximate):
// 10,000 concatenations:
// String: ~500ms
// StringBuilder: ~1ms

DETAILED COMPARISON:
| Feature          | String               | StringBuilder          |
|------------------|----------------------|------------------------|
| Mutability       | Immutable            | Mutable                |
| Namespace        | System               | System.Text            |
| Memory           | New object each time | Same object modified   |
| Performance      | Slow for many changes| Fast for many changes  |
| Thread safety    | Thread-safe          | NOT thread-safe        |
| Use case         | Few/no modifications | Many modifications     |
| Methods          | Concat, Replace, etc.| Append, Insert, Remove |

17 Q17. What are sealed classes in C#? ▼ 
A Sealed class is a class that CANNOT be inherited. No other class can 
derive from it. It prevents further extension of the class hierarchy.

Keyword: sealed

SEALED CLASS:
public sealed class MathHelper
{
    public static double SquareRoot(double number)
    {
        return Math.Sqrt(number);
    }
    
    public static int Factorial(int n)
    {
        if (n <= 1) return 1;
        return n * Factorial(n - 1);
    }
}

// COMPILE ERROR - Cannot inherit from sealed class:
public class AdvancedMath : MathHelper  // ERROR!
{
}

SEALED METHOD (prevent further overriding in chain):
public class Animal
{
    public virtual void Speak()
    {
        Console.WriteLine("Animal sound");
    }
}

public class Dog : Animal
{
    public sealed override void Speak()  // Override + seal it
    {
        Console.WriteLine("Bark!");
    }
}

public class Puppy : Dog
{
    // COMPILE ERROR - Cannot override sealed method:
    public override void Speak() { }  // ERROR!
    
    // But can hide with 'new' (not recommended):
    public new void Speak()  // This works but breaks polymorphism
    {
        Console.WriteLine("Yip!");
    }
}

1. Security - Prevent tampering:
public sealed class PasswordHasher
{
    public string Hash(string password)
    {

    }
}
// No one can inherit and weaken the hashing logic

2. Performance - JIT optimization:

// - No virtual method dispatch needed
// - Methods can be inlined
// - Slightly faster execution

    public string Database { get; }
    // Complete implementation, no need to extend
}

{

- String
- StringBuilder
- DateTime
- Math
- Console
- Environment
- Tuple<T>

|-----------|-------------|------------------|

EARLY BINDING (Compile-time / Static binding):
- Method to call is determined at COMPILE TIME
- Compiler knows the exact type and method
- Faster execution (no runtime lookup)
- Type-safe (errors caught at compile time)
- IntelliSense support available
- Achieved through: direct method calls, method overloading

Example:
// Compiler knows exactly which method to call
Calculator calc = new Calculator();
int result = calc.Add(5, 3);        // Compiler resolves Add(int, int)
double d = calc.Add(5.0, 3.0);     // Compiler resolves Add(double, double)

// Method overloading = early binding
public class Calculator
{
    public int Add(int a, int b) => a + b;         // Resolved at compile time
    public double Add(double a, double b) => a + b; // Based on argument types
}

LATE BINDING (Runtime / Dynamic binding):
- Method to call is determined at RUNTIME
- Compiler doesn't know the exact type/method
- Slower execution (runtime lookup needed)
- NOT type-safe (errors only at runtime)
- No IntelliSense
- Achieved through: virtual/override, dynamic, reflection

Example 1 - Polymorphism (virtual/override):
Animal animal = new Dog();    // Reference type: Animal, Object type: Dog
animal.Speak();               // Which Speak()? Decided at RUNTIME!
// Compiler doesn't know if it's Dog, Cat, or Bird until runtime

public class Animal
{
    public virtual void Speak() => Console.WriteLine("...");
}
public class Dog : Animal
{
    public override void Speak() => Console.WriteLine("Bark!");
}
public class Cat : Animal
{
    public override void Speak() => Console.WriteLine("Meow!");
}

// Late binding - actual method resolved at runtime:
Animal[] animals = { new Dog(), new Cat(), new Dog() };
foreach (var a in animals)
{
    a.Speak();  // Runtime decides: Dog.Speak() or Cat.Speak()
}

Example 2 - dynamic keyword:
dynamic obj = GetSomeObject();  // Compiler doesn't check anything
obj.SomeMethod();               // Resolved at RUNTIME
obj.AnyProperty = 10;           // No compile-time checking
// If method doesn't exist ? RuntimeBinderException at runtime

Example 3 - Reflection:
Type type = typeof(Calculator);
object instance = Activator.CreateInstance(type);
MethodInfo method = type.GetMethod("Add");
object result = method.Invoke(instance, new object[] { 5, 3 });
// Method resolved entirely at runtime

COMPARISON:
| Feature          | Early Binding          | Late Binding             |
|------------------|------------------------|--------------------------|
| Resolved at      | Compile time           | Runtime                  |
| Performance      | Faster                 | Slower                   |
| Type safety      | Yes (compile errors)   | No (runtime errors)      |
| IntelliSense     | Yes                    | No (for dynamic)         |
| Error detection  | At compile time        | At runtime               |
| Flexibility      | Less flexible          | More flexible            |
| Keywords         | Normal method calls    | virtual/override/dynamic |
| Also called      | Static binding         | Dynamic binding          |

WHEN EACH IS USED:
Early Binding:
- Normal method calls
- Method overloading
- Direct type references
- Most everyday code

Late Binding:
- Polymorphism (virtual/override) � most common
- Plugin architectures
- COM interop
- Reflection-based frameworks
- Working with unknown types at compile time
- dynamic keyword (interop with JavaScript, Python, COM)

IEnumerable<T> (In-Memory / Client-side):
- Namespace: System.Collections.Generic
- Executes queries in APPLICATION MEMORY
- Fetches ALL data first, then filters in C#
- Uses LINQ to Objects
- Suitable for: in-memory collections (List, Array)
- Deferred execution (iterates lazily)

IQueryable<T> (Database / Server-side):
- Namespace: System.Linq
- Builds EXPRESSION TREE, executes on SERVER (database)
- Translates LINQ to SQL, filters at database level
- Uses LINQ to Entities / LINQ to SQL
- Suitable for: database queries (EF Core)
- Deferred execution + query composition

var expensive = products.Where(p => p.Price > 100).ToList();
// SQL generated: SELECT * FROM Products  (gets ALL rows!)
// Then C# filters in memory: removes rows where Price <= 100
// Problem: If table has 1 million rows, ALL are loaded into memory!

// IQueryable - Filters in Database (GOOD):
IQueryable<Product> products = _context.Products;
var expensive = products.Where(p => p.Price > 100).ToList();
// SQL generated: SELECT * FROM Products WHERE Price > 100
// Only matching rows transferred from DB to app
// Much faster and less memory!

// SELECT * FROM Products WHERE Name LIKE '%phone%' AND Price >= 100 
//   AND CategoryId = 5 ORDER BY Name OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY
var results = await query.ToListAsync();  // Executes HERE

| Feature          | IEnumerable<T>         | IQueryable<T>          |

| Filter location  | Application memory     | Database server        |

| Performance      | Slow for large data    | Fast (DB does work)    |
| LINQ provider    | LINQ to Objects        | LINQ to Entities       |
| Extends          | -                      | Extends IEnumerable<T> |
| Deferred exec    | Yes                    | Yes                    |

IEnumerable<T>:
- Working with in-memory data (List, Array)

- Small datasets
- LINQ to Objects operations
- After calling .ToList() or .AsEnumerable()

24 Q26. What's the difference between the Array.CopyTo() and Array.Clone()? ▼ 
Both create copies of an array, but they work differently.

Array.Clone():
- Creates a NEW array with same elements
- Returns object (needs casting)
- Creates a SHALLOW copy
- New array has same length as original

int[] original = { 1, 2, 3, 4, 5 };
int[] cloned = (int[])original.Clone();  // Cast needed (returns object)

cloned[0] = 99;
// original[0] is still 1 (independent copy for value types)

Console.WriteLine(original[0]);  // 1
Console.WriteLine(cloned[0]);    // 99

Array.CopyTo():
- Copies elements into an EXISTING array
- Destination array must already exist and be large enough
- Copies starting at specified index in destination
- Also a SHALLOW copy

int[] source = { 1, 2, 3 };
int[] destination = new int[5];  // Must exist and be large enough

source.CopyTo(destination, 0);  // Copy starting at index 0
// destination = { 1, 2, 3, 0, 0 }

source.CopyTo(destination, 2);  // Copy starting at index 2
// destination = { 0, 0, 1, 2, 3 }

COMPARISON:
| Feature            | Clone()                | CopyTo()               |
|--------------------|------------------------|------------------------|
| Returns            | New array (as object)  | void (copies to existing)|
| Destination        | Creates new array      | Must already exist     |
| Casting needed     | Yes (returns object)   | No                     |
| Starting index     | Always from 0          | Can specify index      |
| Destination size   | Same as source         | Must be >= source      |
| Copy type          | Shallow                | Shallow                |

SHALLOW COPY - Important for reference types:
// For VALUE types (int, struct) - both create independent copies:
int[] nums = { 1, 2, 3 };
int[] copy = (int[])nums.Clone();
copy[0] = 99;
// nums[0] still 1 ? (independent)

25 Q27. Can Multiple Catch Blocks be executed in C#? ▼ 
NO. Only ONE catch block executes for a single exception. Once a matching 
catch block is found, the remaining catch blocks are SKIPPED.

HOW IT WORKS:
- Exception is thrown
- Runtime checks catch blocks from TOP to BOTTOM
- FIRST matching catch block executes
- Remaining catch blocks are ignored
- Control goes to finally (if exists), then continues after try-catch

Example:
try
{
    int[] arr = { 1, 2, 3 };
    Console.WriteLine(arr[10]);  // Throws IndexOutOfRangeException
}
catch (IndexOutOfRangeException ex)
{
    Console.WriteLine("Index error");  // THIS executes (first match)
}
catch (Exception ex)
{
    Console.WriteLine("General error");  // SKIPPED (already caught above)
}

// Output: "Index error" (only one catch runs)

ORDER MATTERS - Specific to General:
// CORRECT order (specific first):
try
{
    // code
}
catch (FileNotFoundException ex)    // Most specific
{
    Console.WriteLine("File not found");
}
catch (IOException ex)              // Parent of FileNotFoundException
{
    Console.WriteLine("IO error");
}
catch (Exception ex)                // Most general (catch-all)
{
    Console.WriteLine("Unknown error");
}

// WRONG order (compile error):
try
{
    // code
}
catch (Exception ex)                // COMPILE ERROR! 
{                                   // General before specific
    Console.WriteLine("Error");     // Unreachable catch blocks below
}
catch (FileNotFoundException ex)    // ERROR: Unreachable code
{
    Console.WriteLine("File not found");
}

MULTIPLE EXCEPTIONS - SAME HANDLER (C# 6+):
// When you want same handling for different exception types:
try
{
    // code
}
catch (Exception ex) when (ex is FormatException || ex is OverflowException)
{
    Console.WriteLine("Invalid input");
}

// Or C# 9+ pattern:
catch (Exception ex) when (ex is FormatException or OverflowException)
{
    Console.WriteLine("Invalid input");
}

EXCEPTION FILTERS (when keyword):
// Multiple catch blocks CAN be checked using 'when':
try
{
    CallApi();
}
catch (HttpRequestException ex) when (ex.StatusCode == 404)
{
    Console.WriteLine("Not found");
}
catch (HttpRequestException ex) when (ex.StatusCode == 500)
{
    Console.WriteLine("Server error");
}
catch (HttpRequestException ex)
{
    Console.WriteLine($"HTTP error: {ex.StatusCode}");
}
// Only ONE of these executes (first matching 'when' condition)

NESTED TRY-CATCH (multiple catches CAN execute in different levels):
try
{
    try
    {
        throw new InvalidOperationException("Inner error");
    }
    catch (InvalidOperationException ex)
    {
        Console.WriteLine("Inner catch");  // Executes
        throw new Exception("Outer error", ex);  // Throws new exception
    }
}
catch (Exception ex)
{
    Console.WriteLine("Outer catch");  // Also executes (different try-catch)
}
// Output:
// Inner catch
// Outer catch
// Two catches execute, but in DIFFERENT try-catch blocks

KEY POINTS:
- Only ONE catch block per try-catch executes
- Order: specific exceptions FIRST, general LAST
- Compiler prevents unreachable catch blocks
- Use 'when' for conditional catch (exception filters)
- Nested try-catch can have multiple catches execute (different levels)
- finally block ALWAYS runs regardless of which catch executed
26 Q28. What is the Singleton Design Pattern, and how to implement it in C#? ▼ 
Singleton ensures a class has ONLY ONE instance throughout the application 
lifetime and provides a global point of access to it.

When to use:
- Database connection manager
- Logger
- Configuration/Settings
- Cache manager
- Thread pool
- Any shared resource that should exist only once

METHOD 1: Basic Singleton (NOT thread-safe):
public sealed class Singleton
{
    private static Singleton _instance;
    
    private Singleton()  // Private constructor - prevents external instantiation
    {
        Console.WriteLine("Singleton created");
    }
    
    public static Singleton Instance
    {
        get
        {
            if (_instance == null)
            {
                _instance = new Singleton();
            }
            return _instance;
        }
    }
    
    public void DoSomething()
    {
        Console.WriteLine("Singleton method called");
    }
}

// Usage:
Singleton obj1 = Singleton.Instance;
Singleton obj2 = Singleton.Instance;
// obj1 and obj2 are SAME instance (ReferenceEquals = true)
// new Singleton();  // COMPILE ERROR! Constructor is private

METHOD 2: Thread-Safe with lock:
public sealed class Singleton
{
    private static Singleton _instance;
    private static readonly object _lock = new object();
    
    private Singleton() { }
    
    public static Singleton Instance
    {
        get
        {
            lock (_lock)  // Only one thread can enter at a time
            {
                if (_instance == null)
                {
                    _instance = new Singleton();
                }
                return _instance;
            }
        }
    }
}

METHOD 3: Double-Check Locking (better performance):
public sealed class Singleton
{
    private static volatile Singleton _instance;
    private static readonly object _lock = new object();
    
    private Singleton() { }
    
    public static Singleton Instance
    {
        get
        {

33 Q35. What are the Different Ways a Method can be Overloaded? ▼ 
Method Overloading: Multiple methods with SAME NAME but DIFFERENT signatures 
in the same class. Compiler decides which to call based on arguments.

WAYS TO OVERLOAD:

1. DIFFERENT NUMBER OF PARAMETERS:
public int Add(int a, int b)
{
    return a + b;
}

public int Add(int a, int b, int c)
{
    return a + b + c;
}

public int Add(int a, int b, int c, int d)
{
    return a + b + c + d;
}

Add(5, 3);        // Calls 2-param version
Add(5, 3, 2);     // Calls 3-param version
Add(5, 3, 2, 1);  // Calls 4-param version

2. DIFFERENT TYPE OF PARAMETERS:
public void Print(int number)
{
    Console.WriteLine($"Integer: {number}");
}

public void Print(string text)
{
    Console.WriteLine($"String: {text}");
}

public void Print(double value)
{
    Console.WriteLine($"Double: {value}");
}

Print(42);       // Calls int version
Print("Hello");  // Calls string version
Print(3.14);     // Calls double version

3. DIFFERENT ORDER OF PARAMETERS:
public void Display(string name, int age)
{
    Console.WriteLine($"{name} is {age}");
}

public void Display(int age, string name)
{
    Console.WriteLine($"Age {age}: {name}");
}

Display("John", 30);  // Calls (string, int)
Display(30, "John");  // Calls (int, string)

4. REF / OUT / IN MODIFIERS:
public void Process(int x)
{
    Console.WriteLine("By value");
}

public void Process(ref int x)
{
    Console.WriteLine("By ref");
}

int num = 5;
Process(num);      // Calls by-value version
Process(ref num);  // Calls ref version

// NOTE: ref and out CANNOT overload each other:
// void Method(ref int x) { }
// void Method(out int x) { }  // ERROR! Cannot overload

5. PARAMS KEYWORD:
public int Sum(int a, int b)
{
    return a + b;
}

public int Sum(params int[] numbers)
{
    return numbers.Sum();
}

Sum(5, 3);           // Calls (int, int) - more specific match
Sum(1, 2, 3, 4, 5); // Calls params version

WHAT CANNOT BE USED FOR OVERLOADING:

// RETURN TYPE alone - NOT valid:
public int Calculate(int a, int b) { return a + b; }
// public double Calculate(int a, int b) { return a + b; }  // ERROR!

// PARAMETER NAME alone - NOT valid:
public void Print(int x) { }
// public void Print(int y) { }  // ERROR! Same signature

// ACCESS MODIFIER alone - NOT valid:

// private void Show() { }  // ERROR!

public void Test(double x) { }     // 2
public void Test(object x) { }     // 3

Test(5.0);    // Calls 2 (exact match: double)
Test("hi");   // Calls 3 (string ? object)
Test(5L);     // Calls 2 (long ? double implicit conversion)

// Compiler picks MOST SPECIFIC match

| Criteria                    | Valid for Overloading? |
|-----------------------------|-----------------------|
| Number of parameters        | YES                   |
| Type of parameters          | YES                   |
| Order of parameters         | YES                   |
| ref/out/in vs by-value      | YES                   |
| Return type only            | NO                    |
| Parameter name only         | NO                    |
| Access modifier only        | NO                    |
| ref vs out (same position)  | NO                    |
34 Q36. What is Object Pooling? ▼ 
Object Pooling is a design pattern that reuses objects from a pool instead of 
creating new ones each time. Reduces GC pressure and allocation cost.

Problem without pooling:
for (int i = 0; i < 10000; i++)
{
    var connection = new DatabaseConnection();  // Expensive creation!
    connection.Execute(query);
    connection.Dispose();  // Destroyed, GC must clean up
}
// 10,000 objects created and destroyed!

With pooling:
for (int i = 0; i < 10000; i++)
{
    var connection = pool.Get();      // Reuse from pool
    connection.Execute(query);
    pool.Return(connection);          // Return to pool (not destroyed)
}
// Only a few objects created, reused thousands of times!

SIMPLE IMPLEMENTATION:
public class ObjectPool<T> where T : new()
{
    private readonly ConcurrentBag<T> _pool = new ConcurrentBag<T>();
    private readonly int _maxSize;
    
    public ObjectPool(int maxSize = 100)
    {
        _maxSize = maxSize;
    }
    
    public T Get()
    {
        if (_pool.TryTake(out T item))
            return item;       // Reuse existing
        return new T();        // Create new if pool empty
    }
    
    public void Return(T item)
    {
        if (_pool.Count < _maxSize)
            _pool.Add(item);   // Return to pool
        // Else discard (pool full)
    }
}

.NET BUILT-IN POOLING:
// ArrayPool<T> (reuse arrays):
var pool = ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(1024);    // Get from pool
// Use buffer...
pool.Return(buffer);                 // Return to pool

// ObjectPool<T> (Microsoft.Extensions.ObjectPool):
var policy = new DefaultPooledObjectPolicy<StringBuilder>();
var pool = new DefaultObjectPool<StringBuilder>(policy);

StringBuilder sb = pool.Get();
sb.Append("Hello");
string result = sb.ToString();
sb.Clear();
pool.Return(sb);  // Reuse later

// Connection Pooling (ADO.NET - automatic):
// SQL connections are automatically pooled
// "Pooling=true;Max Pool Size=100" in connection string

When to use:
- Expensive object creation (DB connections, HTTP clients)
- Frequent allocation/deallocation
- High-throughput scenarios
- Large objects (reduce GC pressure)

Examples in .NET:
- Database Connection Pooling (ADO.NET)
- HttpClient (IHttpClientFactory)
- ArrayPool<T>
- Thread Pool

37 Q39. What is a Virtual Method in C#? ▼ 
A Virtual method is a method in a base class that CAN be overridden by 
derived classes to provide different behavior (runtime polymorphism).

Keywords: virtual (base) + override (derived)

public class Shape
{
    public virtual double Area()  // CAN be overridden
    {
        return 0;  // Default implementation
    }
    
    public virtual void Draw()
    {
        Console.WriteLine("Drawing shape");
    }
}

public class Circle : Shape
{
    public double Radius { get; set; }
    
    public override double Area()  // Overrides base
    {
        return Math.PI * Radius * Radius;
    }
    
    public override void Draw()
    {
        Console.WriteLine($"Drawing circle with radius {Radius}");
    }
}

public class Square : Shape
{
    public double Side { get; set; }
    
    public override double Area()
    {
        return Side * Side;
    }
    // Draw() not overridden - uses base implementation
}

// Runtime polymorphism:
Shape shape = new Circle { Radius = 5 };
Console.WriteLine(shape.Area());  // 78.54 (Circle's version at runtime)

shape = new Square { Side = 4 };
Console.WriteLine(shape.Area());  // 16 (Square's version at runtime)

Rules:
- virtual: base class, provides default implementation
- override: derived class, replaces base behavior
- Derived class MAY override (not required)
- Cannot be: static, abstract, private, sealed (with virtual)

49What happens if you forget await? What is async deadlock?▼
FORGETTING AWAIT:
async Task<string> GetDataAsync()
{
    var result = GetFromApiAsync();  // Missing await!
    // result is Task<string>, NOT string!
    // Method continues without waiting
    // Exception inside is SWALLOWED (fire-and-forget)
}

// Fix:
var result = await GetFromApiAsync();  // Now waits and gets string

DEADLOCK with .Result or .Wait():
public IActionResult Index()
{
    var data = GetDataAsync().Result;  // DEADLOCK!
    return View(data);
}

Why deadlock happens:
1. .Result blocks the current thread (waiting for task)
2. async method needs that SAME thread to continue after await
3. Thread is blocked ? async can't complete ? DEADLOCK!

Fix:
public async Task<IActionResult> Index()
{
    var data = await GetDataAsync();  // No deadlock!
    return View(data);
}

Rules:
- NEVER use .Result or .Wait() on async methods
- Use await all the way (async all the way down)
- If you MUST call async from sync: use .GetAwaiter().GetResult() (last resort)
50What is Task vs Thread vs ValueTask?▼
THREAD:
- OS-level unit of execution
- Heavy (1MB stack each)
- Manual management (start, join, synchronize)
- Low-level, avoid in modern C#

Thread thread = new Thread(() => DoWork());
thread.Start();
thread.Join();

TASK:
- Higher-level abstraction over threads
- Uses ThreadPool (efficient, reuses threads)
- Supports async/await
- Preferred for async operations

Task task = Task.Run(() => DoWork());
await task;

Task<int> task = Task.Run(() => Calculate());
int result = await task;

VALUETASK:
- Struct (value type) � no heap allocation
- Better performance when result is often available synchronously
- Use when method frequently returns cached/immediate results

public ValueTask<int> GetCountAsync()
{
    if (_cache.TryGet("count", out int cached))
        return new ValueTask<int>(cached);  // No allocation!
    
    return new ValueTask<int>(GetFromDbAsync());  // Async path
}

56What is the difference between Authentication and Authorization?▼
AUTHENTICATION = WHO are you? (Identity verification)
- Verifying user's identity (login)
- Username + Password / JWT token / OAuth
- Happens FIRST
- 401 Unauthorized if fails

AUTHORIZATION = Are you ALLOWED? (Permission check)
- Checking what authenticated user can access
- Role-based, Policy-based, Claims-based
- Happens AFTER authentication
- 403 Forbidden if fails

In my Audit project:
Authentication:
- User enters credentials ? API validates against Oracle DB
- JWT token generated with claims (email, role)
- Session cookie set ("_audit_session")
- SessionAuthFilter checks cookie on every request

Authorization:
- Role stored in JWT: Auditor, AuditManager, AuditHead
- Different dashboards per role
- API checks role before processing
- [Authorize(Roles = "Admin")] on sensitive endpoints

ASP.NET Core:
app.UseAuthentication();   // WHO are you? (validate token/cookie)
app.UseAuthorization();    // Are you ALLOWED? (check roles/policies)
// Order matters! Auth before Authz

[Authorize]                         // Must be authenticated
[Authorize(Roles = "Admin")]        // Must have Admin role
[Authorize(Policy = "MinAge18")]    // Must satisfy policy
[AllowAnonymous]                    // Skip both (login page)

Analogy:
- Authentication = Showing your ID at building entrance
- Authorization = Your ID card only opens certain floors
