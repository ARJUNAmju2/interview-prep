SQL Interview Questions

1 Q1. What is SQL and what are its types (DDL, DML, DCL, TCL, DQL)? ▼ 
SQL (Structured Query Language) is a standard language for managing and 
manipulating relational databases.

5 Types of SQL Commands:

1. DDL (Data Definition Language) - Structure/Schema:
   CREATE   - Create database/table/view/index
   ALTER    - Modify structure
   DROP     - Delete object completely
   TRUNCATE - Remove all rows (reset table)

   CREATE TABLE Employee (Id INT PRIMARY KEY, Name VARCHAR(100));
   ALTER TABLE Employee ADD Salary DECIMAL(10,2);
   DROP TABLE Employee;
   TRUNCATE TABLE Employee;

2. DML (Data Manipulation Language) - Data:
   INSERT - Add new rows
   UPDATE - Modify existing rows
   DELETE - Remove specific rows

   INSERT INTO Employee (Id, Name) VALUES (1, 'John');
   UPDATE Employee SET Salary = 50000 WHERE Id = 1;
   DELETE FROM Employee WHERE Id = 1;

3. DQL (Data Query Language) - Retrieve:
   SELECT - Query/fetch data

   SELECT * FROM Employee WHERE Salary > 40000;

4. DCL (Data Control Language) - Permissions:
   GRANT  - Give permissions
   REVOKE - Remove permissions

   GRANT SELECT ON Employee TO UserA;
   REVOKE INSERT ON Employee FROM UserA;

5. TCL (Transaction Control Language) - Transactions:
   BEGIN TRANSACTION
   COMMIT   - Save changes permanently
   ROLLBACK - Undo changes
   SAVEPOINT - Partial rollback point

   BEGIN TRANSACTION
   UPDATE Account SET Balance = Balance - 1000 WHERE Id = 1;
   UPDATE Account SET Balance = Balance + 1000 WHERE Id = 2;
   COMMIT;
2 Q2. What is the difference between DELETE, TRUNCATE, and DROP? ▼ 
DELETE:
- DML command
- Removes SPECIFIC rows (with WHERE) or all rows
- Can be rolled back (logged operation)
- Fires triggers
- Does NOT reset identity
- Slower (row-by-row logging)

DELETE FROM Employee WHERE Department = 'HR';
DELETE FROM Employee;  -- All rows, but table exists

TRUNCATE:
- DDL command
- Removes ALL rows (no WHERE clause)
- Cannot be rolled back easily (minimal logging)
- Does NOT fire triggers
- RESETS identity counter to seed
- Faster (deallocates pages)

TRUNCATE TABLE Employee;  -- All rows gone, identity reset

DROP:
- DDL command
- Removes the ENTIRE TABLE (structure + data)
- Table no longer exists
- Cannot be rolled back

DROP TABLE Employee;  -- Table completely gone

| Feature        | DELETE           | TRUNCATE         | DROP             |
|----------------|-----------------|------------------|------------------|
| Type           | DML             | DDL              | DDL              |
| WHERE clause   | Yes             | No               | No               |
| Rollback       | Yes             | No (mostly)      | No               |
| Triggers       | Yes             | No               | No               |
| Identity reset | No              | Yes              | N/A              |
| Speed          | Slow            | Fast             | Fast             |
| Table exists   | Yes             | Yes (empty)      | No               |
| Logging        | Full (row-level)| Minimal (page)   | Minimal          |
3 Q3. What is the difference between WHERE and HAVING clause? ▼ 
WHERE:
- Filters INDIVIDUAL ROWS before grouping
- Used with SELECT, UPDATE, DELETE
- Cannot use aggregate functions
- Executes BEFORE GROUP BY

HAVING:
- Filters GROUPS after grouping
- Used only with GROUP BY
- CAN use aggregate functions
- Executes AFTER GROUP BY

Example:
-- WHERE: Filter rows first
SELECT Department, COUNT(*) AS EmpCount
FROM Employee
WHERE Salary > 30000          -- Filter individual rows BEFORE grouping
GROUP BY Department;

-- HAVING: Filter groups after
SELECT Department, COUNT(*) AS EmpCount
FROM Employee
GROUP BY Department
HAVING COUNT(*) > 5;          -- Filter groups AFTER grouping

-- Both together:
SELECT Department, AVG(Salary) AS AvgSalary
FROM Employee
WHERE IsActive = 1            -- First: filter active employees
GROUP BY Department
HAVING AVG(Salary) > 50000;  -- Then: only departments with avg > 50K

Execution order:
FROM ? WHERE ? GROUP BY ? HAVING ? SELECT ? ORDER BY

| Feature        | WHERE                | HAVING               |
|----------------|----------------------|----------------------|
| Filters        | Individual rows      | Groups               |
| Aggregates     | Cannot use           | Can use              |
| GROUP BY       | Not required         | Required             |
| Executes       | Before GROUP BY      | After GROUP BY       |
4 Q4. What is the difference between UNION and UNION ALL? ▼ 
UNION:
- Combines results of two queries
- REMOVES duplicate rows
- Slower (must check for duplicates)
- Performs implicit DISTINCT

UNION ALL:
- Combines results of two queries
- KEEPS all rows including duplicates
- Faster (no duplicate check)

Example:
-- Table1: {1, 2, 3, 4}
-- Table2: {3, 4, 5, 6}

SELECT Id FROM Table1
UNION
SELECT Id FROM Table2;
-- Result: 1, 2, 3, 4, 5, 6 (duplicates removed)

SELECT Id FROM Table1
UNION ALL
SELECT Id FROM Table2;
-- Result: 1, 2, 3, 4, 3, 4, 5, 6 (all rows kept)

Rules:
- Both queries must have same number of columns
- Corresponding columns must have compatible data types
- Column names come from FIRST query

| Feature        | UNION              | UNION ALL            |
|----------------|--------------------|----------------------|
| Duplicates     | Removed            | Kept                 |
| Performance    | Slower             | Faster               |
| Use when       | Need unique rows   | Need all rows        |

Best practice: Use UNION ALL when you KNOW there are no duplicates 
(or duplicates are acceptable) � better performance.
5 Q5. What are Aggregate Functions? ▼ 
Aggregate functions perform calculations on a SET of values and return a 
single value.

COUNT(*) - Number of rows:
SELECT COUNT(*) FROM Employee;                    -- All rows
SELECT COUNT(ManagerId) FROM Employee;            -- Non-null values only
SELECT COUNT(DISTINCT Department) FROM Employee;  -- Unique departments

SUM() - Total:
SELECT SUM(Salary) FROM Employee;
SELECT Department, SUM(Salary) FROM Employee GROUP BY Department;

AVG() - Average:
SELECT AVG(Salary) FROM Employee;

MIN() / MAX():
SELECT MIN(Salary), MAX(Salary) FROM Employee;
SELECT MIN(HireDate) AS FirstHire FROM Employee;

Combined example:
SELECT 
    Department,
    COUNT(*) AS TotalEmployees,
    SUM(Salary) AS TotalSalary,
    AVG(Salary) AS AvgSalary,
    MIN(Salary) AS MinSalary,
    MAX(Salary) AS MaxSalary
FROM Employee
GROUP BY Department
HAVING COUNT(*) > 3
ORDER BY AvgSalary DESC;

Note: Aggregate functions ignore NULL values (except COUNT(*)).


Q6-Q7. GROUP BY and ORDER BY
--------------------------------------------------------------------------------
GROUP BY:
- Groups rows with same values into summary rows
- Used with aggregate functions
- Each group produces one row in result

SELECT Department, COUNT(*) AS EmpCount, AVG(Salary) AS AvgSalary
FROM Employee
GROUP BY Department;

-- Result:
-- IT        | 10 | 65000
-- HR        | 5  | 55000
-- Finance   | 8  | 70000

ORDER BY:
- Sorts the result set
- ASC (ascending - default) or DESC (descending)
- Can sort by multiple columns
- Can sort by column position

SELECT * FROM Employee ORDER BY Salary DESC;
SELECT * FROM Employee ORDER BY Department ASC, Salary DESC;
SELECT * FROM Employee ORDER BY 3 DESC;  -- 3rd column


Q8-Q9. CHAR vs VARCHAR vs NVARCHAR
--------------------------------------------------------------------------------
CHAR(n):
- Fixed length (always uses n bytes)
- Padded with spaces if shorter
- Faster for fixed-length data
- Use for: Gender(1), CountryCode(2), PIN(6)

CHAR(10) storing "Hello" ? "Hello     " (5 chars + 5 spaces = 10 bytes)

VARCHAR(n):
- Variable length (uses actual length + 2 bytes)
- No padding
- Saves space for variable-length data
- Use for: Name, Email, Address

VARCHAR(100) storing "Hello" ? "Hello" (5 + 2 = 7 bytes)

NVARCHAR(n):
- Variable length UNICODE (2 bytes per character)
- Supports international characters (Chinese, Arabic, Hindi)
- Uses more space (double)
- Use for: multilingual data

NVARCHAR(100) storing "Hello" ? 10 + 2 = 12 bytes (2 bytes per char)

| Type       | Storage          | Characters    | Use case           |
|------------|------------------|---------------|--------------------|
| CHAR(10)   | Always 10 bytes  | ASCII only    | Fixed-length codes |
| VARCHAR(10)| 1-10 + 2 bytes   | ASCII only    | Variable English   |
| NVARCHAR(10)| 2-20 + 2 bytes  | Unicode (all) | Multilingual       |
6 Q10. What are NULL values and how to handle them? ▼ 
NULL means UNKNOWN or MISSING value. It is NOT zero, empty string, or space.

-- NULL comparisons:
SELECT * FROM Employee WHERE ManagerId IS NULL;      -- Correct
SELECT * FROM Employee WHERE ManagerId IS NOT NULL;  -- Correct
-- SELECT * FROM Employee WHERE ManagerId = NULL;    -- WRONG! Always false

-- ISNULL(value, replacement): SQL Server specific
SELECT Name, ISNULL(Phone, 'N/A') AS Phone FROM Employee;

-- COALESCE(val1, val2, val3...): Returns first non-null (ANSI standard)
SELECT Name, COALESCE(Phone, Mobile, Email, 'No Contact') AS Contact
FROM Employee;

-- NULLIF(a, b): Returns NULL if a = b
SELECT NULLIF(Salary, 0) AS Salary FROM Employee;  -- Returns NULL if salary is 0

-- NULL in calculations:
-- Any arithmetic with NULL = NULL
SELECT 100 + NULL;  -- NULL
SELECT NULL * 5;    -- NULL

-- Handle in aggregates:
SELECT AVG(ISNULL(Salary, 0)) FROM Employee;  -- Treat NULL as 0
SELECT AVG(Salary) FROM Employee;             -- Ignores NULL rows

ISNULL vs COALESCE:
| Feature    | ISNULL           | COALESCE              |
|------------|------------------|-----------------------|
| Parameters | Exactly 2        | 2 or more             |
| Standard   | SQL Server only  | ANSI SQL (portable)   |
| Data type  | First parameter  | Highest precedence    |
| Performance| Slightly faster  | Slightly slower       |

7 Q11. What are JOINS in SQL? Why are they used? ▼ 
JOINS combine rows from two or more tables based on a related column 
(usually Foreign Key - Primary Key relationship).

Why needed:
- Data is split across multiple tables (normalization)
- Need to retrieve related data together
- Example: Employee table + Department table ? Employee with Department name

Types:
- INNER JOIN: Only matching rows from both tables
- LEFT JOIN: All from left + matching from right
- RIGHT JOIN: All from right + matching from left
- FULL OUTER JOIN: All from both tables
- CROSS JOIN: Every row combined with every row (Cartesian product)
- SELF JOIN: Table joined with itself

Sample tables for examples:
Employee: {Id, Name, DepartmentId}
| Id | Name  | DepartmentId |
|----|-------|--------------|
| 1  | John  | 1            |
| 2  | Jane  | 2            |
| 3  | Bob   | 1            |
| 4  | Alice | NULL         |

Department: {Id, DeptName}
| Id | DeptName  |
|----|-----------|
| 1  | IT        |
| 2  | HR        |
| 3  | Finance   |
8 Q12. What is INNER JOIN? ▼ 
Returns ONLY rows that have matching values in BOTH tables.
Non-matching rows are excluded.

SELECT e.Name, d.DeptName
FROM Employee e
INNER JOIN Department d ON e.DepartmentId = d.Id;

Result:
| Name | DeptName |
|------|----------|
| John | IT       |
| Jane | HR       |
| Bob  | IT       |

-- Alice excluded (DepartmentId is NULL - no match)
-- Finance excluded (no employee in Finance)
9 Q13. What is LEFT JOIN (LEFT OUTER JOIN)? ▼ 
Returns ALL rows from LEFT table + matching rows from RIGHT table.
If no match, RIGHT side columns show NULL.

SELECT e.Name, d.DeptName
FROM Employee e
LEFT JOIN Department d ON e.DepartmentId = d.Id;

Result:
| Name  | DeptName |
|-------|----------|
| John  | IT       |
| Jane  | HR       |
| Bob   | IT       |
| Alice | NULL     |  ? No matching department, but Alice still appears

-- All employees shown (even without department)
-- Finance not shown (no employee references it)

Use case: Show all employees, even those not assigned to any department.
10 Q14. What is RIGHT JOIN (RIGHT OUTER JOIN)? ▼ 
Returns ALL rows from RIGHT table + matching rows from LEFT table.
If no match, LEFT side columns show NULL.

SELECT e.Name, d.DeptName
FROM Employee e
RIGHT JOIN Department d ON e.DepartmentId = d.Id;

Result:
| Name | DeptName |
|------|----------|
| John | IT       |
| Bob  | IT       |
| Jane | HR       |
| NULL | Finance  |  ? No employee in Finance, but Finance still appears

-- All departments shown (even without employees)
-- Alice not shown (has NULL DepartmentId)

Note: RIGHT JOIN is rarely used. You can always rewrite as LEFT JOIN 
by swapping table order.
11 Q15. What is FULL OUTER JOIN? ▼ 
Returns ALL rows from BOTH tables. NULL where no match exists.

SELECT e.Name, d.DeptName
FROM Employee e
FULL OUTER JOIN Department d ON e.DepartmentId = d.Id;

Result:
| Name  | DeptName |
|-------|----------|
| John  | IT       |
| Bob   | IT       |
| Jane  | HR       |
| Alice | NULL     |  ? Employee without department
| NULL  | Finance  |  ? Department without employee

-- Everything from both sides shown
12 Q16. What is CROSS JOIN? ▼ 
Returns Cartesian Product � every row from first table combined with every 
row from second table. No ON condition needed.

SELECT e.Name, d.DeptName
FROM Employee e
CROSS JOIN Department d;

Result: 4 employees � 3 departments = 12 rows
| Name  | DeptName |
|-------|----------|
| John  | IT       |
| John  | HR       |
| John  | Finance  |
| Jane  | IT       |
| Jane  | HR       |
| Jane  | Finance  |
| Bob   | IT       |
| Bob   | HR       |
| Bob   | Finance  |
| Alice | IT       |
| Alice | HR       |
| Alice | Finance  |

Use cases:
- Generate all combinations (sizes � colors)
- Calendar generation (years � months)
- Test data generation
13 Q17. What is SELF JOIN? ▼ 
A table joined with ITSELF. Used for hierarchical/recursive relationships.

Example: Employee-Manager relationship (ManagerId references same table)
| Id | Name    | ManagerId |
|----|---------|-----------|
| 1  | CEO     | NULL      |
| 2  | VP      | 1         |
| 3  | Manager | 2         |
| 4  | Dev     | 3         |

-- Find employee with their manager name:
SELECT 
    e.Name AS Employee, 
    m.Name AS Manager
FROM Employee e
LEFT JOIN Employee m ON e.ManagerId = m.Id;

Result:
| Employee | Manager |
|----------|---------|
| CEO      | NULL    |
| VP       | CEO     |
| Manager  | VP      |
| Dev      | Manager |
14 Q18. What is the difference between INNER JOIN and LEFT JOIN? ▼ 
INNER JOIN:
- Returns ONLY matching rows from both tables
- Excludes non-matching rows from BOTH sides
- Result is smaller or equal to both tables

LEFT JOIN:
- Returns ALL rows from left table
- Matching rows from right table
- NULL for non-matching right side
- Result always includes all left table rows

-- INNER JOIN: Only employees WITH departments
SELECT e.Name, d.DeptName
FROM Employee e
INNER JOIN Department d ON e.DepartmentId = d.Id;
-- Alice excluded (no department)

-- LEFT JOIN: ALL employees, department if available
SELECT e.Name, d.DeptName
FROM Employee e
LEFT JOIN Department d ON e.DepartmentId = d.Id;
-- Alice included with NULL department

When to use:
- INNER JOIN: Need only complete/matched data
- LEFT JOIN: Need all records from main table regardless of match
15 Q19. How to join more than 2 tables? ▼ 
Chain multiple JOINs:

SELECT 
    e.Name,
    d.DeptName,
    p.ProjectName,
    m.Name AS ManagerName
FROM Employee e
INNER JOIN Department d ON e.DepartmentId = d.Id
INNER JOIN Project p ON e.ProjectId = p.Id
LEFT JOIN Employee m ON e.ManagerId = m.Id
WHERE e.IsActive = 1
ORDER BY d.DeptName, e.Name;

-- Each JOIN adds another table to the result
-- Can mix JOIN types (INNER + LEFT)
-- Order of JOINs can affect performance
16 Q20. What is the difference between JOIN and Subquery? Which is faster? ▼ 
JOIN approach:
SELECT e.Name, d.DeptName
FROM Employee e
INNER JOIN Department d ON e.DepartmentId = d.Id
WHERE d.DeptName = 'IT';

Subquery approach:
SELECT Name
FROM Employee
WHERE DepartmentId IN (SELECT Id FROM Department WHERE DeptName = 'IT');

| Feature      | JOIN               | Subquery             |
|--------------|--------------------|----------------------|
| Readability  | Better for complex | Better for simple    |
| Performance  | Usually faster     | Can be slower        |
| Columns      | Can select from both| Only outer table    |
| Optimization | Better optimized   | May run per row      |

Performance:
- JOINs are generally FASTER (optimizer handles well)
- Correlated subqueries are SLOW (run for each row)
- Non-correlated subqueries are OK (run once)
- Modern SQL Server optimizer often converts subqueries to joins

Use JOIN when: Need columns from multiple tables
Use Subquery when: Simple existence check, IN clause, cleaner logic

17 Q21. What is a Subquery (Nested Query)? ▼ 
A Subquery is a query inside another query. The inner query executes first 
and its result is used by the outer query.

-- Find employees earning more than average salary:
SELECT Name, Salary
FROM Employee
WHERE Salary > (SELECT AVG(Salary) FROM Employee);

-- Find employees in IT department:
SELECT Name FROM Employee
WHERE DepartmentId IN (SELECT Id FROM Department WHERE DeptName = 'IT');

-- Subquery in SELECT:
SELECT Name, Salary,
    (SELECT AVG(Salary) FROM Employee) AS CompanyAvg
FROM Employee;

-- Subquery in FROM (derived table):
SELECT DeptName, AvgSalary
FROM (
    SELECT DepartmentId, AVG(Salary) AS AvgSalary
    FROM Employee
    GROUP BY DepartmentId
) AS DeptAvg
INNER JOIN Department d ON DeptAvg.DepartmentId = d.Id;

Types:
- Single-row subquery: Returns one value (use =, >, <)
- Multi-row subquery: Returns multiple values (use IN, ANY, ALL)
- Correlated subquery: References outer query (runs per row)
18 Q22. What is the difference between Correlated and Non-Correlated Subquery? ▼ 
NON-CORRELATED (Independent):
- Inner query runs ONCE independently
- Does NOT reference outer query
- Result is used by outer query
- Faster

-- Runs inner query once, gets avg, then filters:
SELECT Name, Salary
FROM Employee
WHERE Salary > (SELECT AVG(Salary) FROM Employee);

CORRELATED (Dependent):
- Inner query runs ONCE FOR EACH ROW of outer query
- References outer query's columns
- Slower (executes multiple times)

-- For each employee, checks if they earn more than their dept average:
SELECT e.Name, e.Salary
FROM Employee e
WHERE e.Salary > (
    SELECT AVG(e2.Salary) 
    FROM Employee e2 
    WHERE e2.DepartmentId = e.DepartmentId  -- References outer query!
);

| Feature        | Non-Correlated       | Correlated           |
|----------------|----------------------|----------------------|
| Execution      | Once                 | Per outer row        |
| References     | Independent          | Uses outer columns   |
| Performance    | Faster               | Slower               |
| Can run alone  | Yes                  | No                   |
19 Q23. What is EXISTS vs IN? ▼ 
IN:
- Checks if value exists in a list/subquery result
- Compares values
- Better for small result sets from subquery

SELECT Name FROM Employee
WHERE DepartmentId IN (SELECT Id FROM Department WHERE DeptName IN ('IT', 'HR'));

EXISTS:
- Checks if subquery returns ANY rows (true/false)
- Stops as soon as first match found (short-circuits)
- Better for large result sets

SELECT Name FROM Employee e
WHERE EXISTS (
    SELECT 1 FROM Department d 
    WHERE d.Id = e.DepartmentId AND d.DeptName = 'IT'
);

| Feature      | IN                   | EXISTS               |
|--------------|----------------------|----------------------|
| Returns      | Values to compare    | True/False           |
| NULL handling| Problems with NULL   | Handles NULL well    |
| Performance  | Better for small set | Better for large set |
| Short-circuit| No                   | Yes (stops early)    |

Rule of thumb:
- Small subquery result ? IN
- Large subquery result ? EXISTS
- NULL values in subquery ? EXISTS (IN has issues with NULL)


Q24-Q25. Scalar Subquery and Multiple Row Subquery
--------------------------------------------------------------------------------
SCALAR SUBQUERY (returns single value):
SELECT Name, Salary,
    Salary - (SELECT AVG(Salary) FROM Employee) AS DiffFromAvg
FROM Employee;

MULTIPLE ROW SUBQUERY (returns multiple values):
-- Use with IN, ANY, ALL:
SELECT Name FROM Employee
WHERE DepartmentId IN (SELECT Id FROM Department WHERE Budget > 100000);

-- ANY: True if condition matches ANY value
SELECT Name FROM Employee
WHERE Salary > ANY (SELECT Salary FROM Employee WHERE Department = 'HR');
-- Employees earning more than at least one HR employee

-- ALL: True if condition matches ALL values
SELECT Name FROM Employee
WHERE Salary > ALL (SELECT Salary FROM Employee WHERE Department = 'HR');
-- Employees earning more than every HR employee

20 Q26. What is an Index in SQL? ▼ 
An Index is a database object that speeds up data retrieval. Like a book's 
index � instead of reading every page, you look up the topic and go directly.

Without index: Full Table Scan (reads every row) � SLOW for large tables
With index: Index Seek (goes directly to matching rows) � FAST

-- Create index:
CREATE INDEX IX_Employee_Name ON Employee(Name);
CREATE INDEX IX_Employee_Dept_Salary ON Employee(DepartmentId, Salary);

-- Drop index:
DROP INDEX IX_Employee_Name ON Employee;

How it works:
- Index creates a separate data structure (B-Tree)
- Stores indexed column values + pointer to actual row
- Sorted for fast searching (binary search)

Trade-offs:
- Faster SELECT (reads)
- Slower INSERT/UPDATE/DELETE (must update index too)
- Uses additional disk space
21 Q27. What is Clustered vs Non-Clustered Index? ▼ 
CLUSTERED INDEX:
- Determines PHYSICAL ORDER of data in table
- Table data is SORTED by clustered index key
- Only ONE per table (data can only be sorted one way)
- Leaf nodes contain ACTUAL DATA rows
- Primary Key creates clustered index by default
- Faster for range queries

CREATE CLUSTERED INDEX IX_Employee_Id ON Employee(Id);
-- Or automatically: PRIMARY KEY creates clustered index

NON-CLUSTERED INDEX:
- Separate structure with POINTERS to data
- Does NOT change physical order of data
- Multiple per table (up to 999)
- Leaf nodes contain index key + row pointer (RID or clustered key)
- Like a book's index at the back

CREATE NONCLUSTERED INDEX IX_Employee_Name ON Employee(Name);
CREATE NONCLUSTERED INDEX IX_Employee_Email ON Employee(Email);

| Feature          | Clustered            | Non-Clustered        |
|------------------|----------------------|----------------------|
| Physical order   | Yes (sorts data)     | No (separate struct) |
| Per table        | Only 1               | Up to 999            |
| Leaf nodes       | Actual data rows     | Pointers to data     |
| Speed            | Faster (data is there)| Slightly slower (lookup)|
| Space            | No extra (IS the data)| Extra space needed   |
| Default          | Primary Key          | Must create manually |
| Range queries    | Excellent            | Good                 |

Analogy:
- Clustered = Dictionary (words sorted alphabetically, definition right there)
- Non-Clustered = Book index (topics listed, page number to look up)
22 Q28. What is a Unique Index? ▼ 
A Unique Index ensures all values in the indexed column(s) are DISTINCT.
No duplicate values allowed.

CREATE UNIQUE INDEX IX_Employee_Email ON Employee(Email);

-- Now:
INSERT INTO Employee (Name, Email) VALUES ('John', 'john@mail.com');  -- OK
INSERT INTO Employee (Name, Email) VALUES ('Jane', 'john@mail.com');  -- ERROR! Duplicate

-- Unique constraint automatically creates a unique index:
ALTER TABLE Employee ADD CONSTRAINT UQ_Email UNIQUE (Email);

Note: Unique index allows ONE NULL value (in SQL Server).
23 Q29. What is a Composite Index? ▼ 
A Composite Index is an index on MULTIPLE columns.

CREATE INDEX IX_Employee_Dept_Salary ON Employee(DepartmentId, Salary);

-- This index helps queries that filter by:
-- DepartmentId alone ?
-- DepartmentId AND Salary ?
-- Salary alone ? (leftmost column must be used)

-- Helps:
SELECT * FROM Employee WHERE DepartmentId = 1;
SELECT * FROM Employee WHERE DepartmentId = 1 AND Salary > 50000;

-- Does NOT help:
SELECT * FROM Employee WHERE Salary > 50000;  -- Missing leftmost column

Rule: "Leftmost Prefix" � index is used only if query includes the 
leftmost column(s) of the composite index.

Column order matters! Put most selective (most filtered) column first.
24 Q30. When to use and when NOT to use indexes? ▼ 
USE indexes when:
- Column is frequently used in WHERE clause
- Column is used in JOIN conditions
- Column is used in ORDER BY
- Column has high selectivity (many unique values)
- Table is large and queries return small % of rows
- Column used in GROUP BY

DO NOT use indexes when:
- Small tables (full scan is fast enough)
- Columns with low selectivity (Gender: M/F only)
- Tables with heavy INSERT/UPDATE/DELETE (index maintenance overhead)
- Columns rarely used in queries
- Columns frequently updated

Over-indexing problems:
- Slower writes (every INSERT/UPDATE must update all indexes)
- More disk space
- Index maintenance overhead
- Diminishing returns


Q31-Q32. Index Fragmentation and Covering Index
--------------------------------------------------------------------------------
INDEX FRAGMENTATION:
- Over time, indexes become fragmented (pages out of order)
- Causes more I/O, slower queries
- Fix: REBUILD or REORGANIZE

-- Check fragmentation:
SELECT * FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED');

-- Fix:
ALTER INDEX IX_Employee_Name ON Employee REBUILD;      -- > 30% fragmentation
ALTER INDEX IX_Employee_Name ON Employee REORGANIZE;   -- 10-30% fragmentation

COVERING INDEX:
- Index that contains ALL columns needed by a query
- Query can be answered entirely from index (no table lookup)
- Very fast (avoids "key lookup")

-- Query needs: Name, Salary WHERE DepartmentId = 1
CREATE INDEX IX_Covering ON Employee(DepartmentId) INCLUDE (Name, Salary);

-- Now this query uses ONLY the index (no table access):
SELECT Name, Salary FROM Employee WHERE DepartmentId = 1;
25 Q33. How many Clustered indexes can a table have? ▼ 
Only ONE clustered index per table.

Reason: Clustered index determines the PHYSICAL ORDER of data rows.
Data can only be physically sorted in ONE way.

- 1 Clustered index (usually on Primary Key)
- Up to 999 Non-Clustered indexes

-- By default, PRIMARY KEY = Clustered Index
CREATE TABLE Employee (
    Id INT PRIMARY KEY,  -- Clustered index created automatically
    Name VARCHAR(100)
);

-- You can make PK non-clustered and cluster on another column:
CREATE TABLE Employee (
    Id INT PRIMARY KEY NONCLUSTERED,
    Name VARCHAR(100),
    CreatedDate DATETIME
);
CREATE CLUSTERED INDEX IX_Employee_Date ON Employee(CreatedDate);

26 Q34. What is a Stored Procedure? ▼ 
A Stored Procedure is a precompiled collection of SQL statements stored in 
the database that can be executed as a single unit.

CREATE PROCEDURE sp_GetEmployeesByDept
    @DepartmentId INT,
    @MinSalary DECIMAL(10,2) = 0  -- Default parameter
AS
BEGIN
    SELECT Id, Name, Salary
    FROM Employee
    WHERE DepartmentId = @DepartmentId
      AND Salary >= @MinSalary
    ORDER BY Salary DESC;
END

-- Execute:
EXEC sp_GetEmployeesByDept @DepartmentId = 1;
EXEC sp_GetEmployeesByDept 1, 50000;

Benefits:
- Precompiled (faster execution, cached plan)
- Reusable (call from multiple places)
- Security (grant EXEC permission without table access)
- Reduces network traffic (one call instead of multiple queries)
- Maintainability (change logic in one place)
- Prevents SQL injection (parameterized)
27 Q35. What is the difference between Stored Procedure and Function? ▼ 
| Feature          | Stored Procedure     | Function               |
|------------------|----------------------|------------------------|
| Return           | 0 or more values     | Must return ONE value  |
| Return type      | INT (status) + OUT   | Scalar or Table        |
| Call in SELECT   | Cannot               | Can                    |
| DML allowed      | Yes (INSERT/UPDATE)  | No (read-only)         |
| Transaction      | Can use              | Cannot use             |
| TRY-CATCH        | Can use              | Cannot use             |
| Call syntax       | EXEC sp_Name        | SELECT dbo.FnName()   |
| Output params    | Yes                  | No                     |
| Table-valued     | Via result set       | Returns TABLE          |

-- Function can be used in SELECT:
SELECT Name, dbo.fn_GetTax(Salary) AS Tax FROM Employee;

-- SP cannot be used in SELECT:
-- SELECT Name, EXEC sp_GetTax(Salary) FROM Employee;  -- ERROR!
28 Q36. What are Input and Output parameters in SP? ▼ 
INPUT parameters (pass data IN):
CREATE PROCEDURE sp_GetEmployee
    @Id INT  -- Input parameter
AS
BEGIN
    SELECT * FROM Employee WHERE Id = @Id;
END

EXEC sp_GetEmployee @Id = 5;

OUTPUT parameters (get data OUT):
CREATE PROCEDURE sp_GetEmployeeCount
    @DepartmentId INT,           -- Input
    @Count INT OUTPUT,           -- Output
    @AvgSalary DECIMAL OUTPUT    -- Output
AS
BEGIN
    SELECT @Count = COUNT(*), @AvgSalary = AVG(Salary)
    FROM Employee
    WHERE DepartmentId = @DepartmentId;
END

-- Call with OUTPUT:
DECLARE @EmpCount INT, @Avg DECIMAL;
EXEC sp_GetEmployeeCount @DepartmentId = 1, 
     @Count = @EmpCount OUTPUT, 
     @AvgSalary = @Avg OUTPUT;
PRINT @EmpCount;
PRINT @Avg;

SCALAR FUNCTION (returns single value):
CREATE FUNCTION fn_GetFullName(@FirstName VARCHAR(50), @LastName VARCHAR(50))
RETURNS VARCHAR(100)
AS

    RETURN @FirstName + ' ' + @LastName;
END

30 Q41. What is a View? ▼ 
A View is a virtual table based on a SELECT query. It doesn't store data 
physically � it executes the query each time it's accessed.

CREATE VIEW vw_EmployeeDetails
AS
SELECT e.Id, e.Name, e.Salary, d.DeptName, m.Name AS ManagerName
FROM Employee e
LEFT JOIN Department d ON e.DepartmentId = d.Id
LEFT JOIN Employee m ON e.ManagerId = m.Id
WHERE e.IsActive = 1;

-- Usage (like a table):
SELECT * FROM vw_EmployeeDetails;
SELECT * FROM vw_EmployeeDetails WHERE DeptName = 'IT';

Benefits:
- Simplify complex queries (write once, use many times)
- Security (expose only certain columns/rows)
- Abstraction (hide table structure from users)
- Consistent data access

Limitations:
- Cannot use ORDER BY without TOP/OFFSET
- Cannot have parameters (use function instead)
- Performance same as underlying query (not cached)

31 Q46. What is a Trigger? ▼ 
A Trigger is a special stored procedure that automatically executes when a 
specific event (INSERT, UPDATE, DELETE) occurs on a table.

AFTER TRIGGER (executes AFTER the DML operation):
CREATE TRIGGER trg_Employee_Audit
ON Employee
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    -- Log changes to audit table
    INSERT INTO AuditLog (TableName, Action, DateTime)
    SELECT 'Employee', 
           CASE 
               WHEN EXISTS(SELECT 1 FROM inserted) AND EXISTS(SELECT 1 FROM deleted) THEN 'UPDATE'
               WHEN EXISTS(SELECT 1 FROM inserted) THEN 'INSERT'
               ELSE 'DELETE'
           END,
           GETDATE();
END

INSTEAD OF TRIGGER (executes INSTEAD of the DML operation):
CREATE TRIGGER trg_Employee_SoftDelete
ON Employee
INSTEAD OF DELETE
AS
BEGIN
    -- Soft delete instead of actual delete
    UPDATE Employee SET IsActive = 0, DeletedDate = GETDATE()
    WHERE Id IN (SELECT Id FROM deleted);
END

Q51-Q61. Constraints, Keys, and Referential Integrity
--------------------------------------------------------------------------------
CONSTRAINTS enforce rules on data in tables:

PRIMARY KEY:
- Uniquely identifies each row
- Cannot be NULL
- Only ONE per table
- Creates clustered index by default

CREATE TABLE Employee (
    Id INT PRIMARY KEY IDENTITY(1,1),
    Name VARCHAR(100) NOT NULL
);

FOREIGN KEY:
- References Primary Key of another table
- Enforces referential integrity
- Can be NULL (optional relationship)

CREATE TABLE Employee (
    Id INT PRIMARY KEY,
    DepartmentId INT FOREIGN KEY REFERENCES Department(Id)
);

UNIQUE:
- All values must be distinct
- Allows ONE NULL
- Multiple unique constraints per table

ALTER TABLE Employee ADD CONSTRAINT UQ_Email UNIQUE (Email);

CHECK:
- Validates data against a condition

ALTER TABLE Employee ADD CONSTRAINT CK_Salary CHECK (Salary > 0);
ALTER TABLE Employee ADD CONSTRAINT CK_Age CHECK (Age BETWEEN 18 AND 65);

DEFAULT:
- Provides default value if none specified

ALTER TABLE Employee ADD CONSTRAINT DF_HireDate DEFAULT GETDATE() FOR HireDate;
ALTER TABLE Employee ADD CONSTRAINT DF_IsActive DEFAULT 1 FOR IsActive;

NOT NULL:
- Column cannot contain NULL values

CREATE TABLE Employee (
    Id INT PRIMARY KEY,
    Name VARCHAR(100) NOT NULL,
    Email VARCHAR(200) NOT NULL
);

PRIMARY KEY vs UNIQUE KEY:
| Feature      | Primary Key        | Unique Key         |
|--------------|--------------------|--------------------|
| NULL         | Not allowed        | One NULL allowed   |
| Per table    | Only 1             | Multiple           |
| Index        | Clustered (default)| Non-clustered      |
| Purpose      | Row identifier     | Prevent duplicates |

CASCADE DELETE/UPDATE:
CREATE TABLE Employee (
    Id INT PRIMARY KEY,
    DepartmentId INT FOREIGN KEY REFERENCES Department(Id)
        ON DELETE CASCADE      -- Delete employees when department deleted
        ON UPDATE CASCADE      -- Update FK when department Id changes
);

-- Options: CASCADE, SET NULL, SET DEFAULT, NO ACTION

Q62-Q67. Normalization
--------------------------------------------------------------------------------
Normalization is organizing database tables to reduce redundancy and 
dependency. Each normal form has specific rules.

1NF (First Normal Form):
- Each column has atomic (single) values
- No repeating groups or arrays
- Each row is unique

BAD: | Id | Name | Phones              |
     | 1  | John | 123-456, 789-012    |  ? Multiple values!

GOOD: | Id | Name | Phone   |
      | 1  | John | 123-456 |
      | 1  | John | 789-012 |  ? Separate rows

2NF (Second Normal Form):
- Must be in 1NF
- No PARTIAL dependency (non-key column depends on PART of composite key)
- Every non-key column depends on the ENTIRE primary key

BAD (composite key: StudentId + CourseId):
| StudentId | CourseId | StudentName | CourseName | Grade |
StudentName depends only on StudentId (partial dependency!)

GOOD: Split into separate tables:
Students: | StudentId | StudentName |
Courses:  | CourseId | CourseName |
Enrollments: | StudentId | CourseId | Grade |

3NF (Third Normal Form):
- Must be in 2NF
- No TRANSITIVE dependency (non-key depends on another non-key)

BAD:
| EmpId | EmpName | DeptId | DeptName |
DeptName depends on DeptId (not directly on EmpId) � transitive!

GOOD: Split:
Employee: | EmpId | EmpName | DeptId |
Department: | DeptId | DeptName |

DENORMALIZATION:
- Intentionally adding redundancy for READ performance
- Used in reporting databases, data warehouses
- Trade-off: faster reads, slower writes, more storage
- Example: Store calculated TotalAmount in Order table

Q68-Q74. Transactions, ACID, Deadlocks, Isolation Levels
--------------------------------------------------------------------------------
TRANSACTION:
A unit of work that must complete entirely or not at all.

BEGIN TRANSACTION
    UPDATE Account SET Balance = Balance - 1000 WHERE Id = 1;
    UPDATE Account SET Balance = Balance + 1000 WHERE Id = 2;
    
    IF @@ERROR <> 0
        ROLLBACK;
    ELSE
        COMMIT;

-- Better with TRY-CATCH:
BEGIN TRY
    BEGIN TRANSACTION
        UPDATE Account SET Balance = Balance - 1000 WHERE Id = 1;
        UPDATE Account SET Balance = Balance + 1000 WHERE Id = 2;
    COMMIT TRANSACTION
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION
    PRINT ERROR_MESSAGE();
END CATCH

ACID PROPERTIES:
- Atomicity: All or nothing (complete fully or rollback)
- Consistency: Database moves from one valid state to another
- Isolation: Concurrent transactions don't interfere
- Durability: Committed changes survive system failure

DEADLOCK:
Two transactions waiting for each other's locks � neither can proceed.

Transaction 1: Locks Table A, wants Table B
Transaction 2: Locks Table B, wants Table A
? DEADLOCK! SQL Server kills one (victim)

Prevention:
- Access tables in same order
- Keep transactions short
- Use appropriate isolation level
- Use NOLOCK hint for read-only queries (carefully)

ISOLATION LEVELS:
| Level              | Dirty Read | Non-Repeatable | Phantom |
|--------------------|------------|----------------|---------|
| Read Uncommitted   | YES        | YES            | YES     |
| Read Committed*    | NO         | YES            | YES     |
| Repeatable Read    | NO         | NO             | YES     |
| Serializable       | NO         | NO             | NO      |
| Snapshot           | NO         | NO             | NO      |
* Default in SQL Server

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

Dirty Read: Reading uncommitted data from another transaction
Non-Repeatable Read: Same query returns different data (another committed)
Phantom Read: New rows appear between two reads (another inserted)

33 Q75. What is CTE (Common Table Expression)? ▼ 
CTE is a temporary named result set defined within a single statement.
More readable than subqueries.

WITH HighEarners AS (
    SELECT Name, Salary, DepartmentId
    FROM Employee
    WHERE Salary > 70000
)
SELECT h.Name, h.Salary, d.DeptName
FROM HighEarners h
INNER JOIN Department d ON h.DepartmentId = d.Id;

-- Multiple CTEs:
WITH 
DeptStats AS (
    SELECT DepartmentId, AVG(Salary) AS AvgSalary, COUNT(*) AS EmpCount
    FROM Employee GROUP BY DepartmentId
),
TopDepts AS (
    SELECT DepartmentId FROM DeptStats WHERE AvgSalary > 60000
)
SELECT e.Name, e.Salary
FROM Employee e
WHERE e.DepartmentId IN (SELECT DepartmentId FROM TopDepts);

Recursive CTE (hierarchy):
WITH EmpHierarchy AS (
    -- Anchor: Top-level (no manager)
    SELECT Id, Name, ManagerId, 0 AS Level
    FROM Employee WHERE ManagerId IS NULL
    
    UNION ALL
    
    -- Recursive: Join with parent
    SELECT e.Id, e.Name, e.ManagerId, h.Level + 1
    FROM Employee e
    INNER JOIN EmpHierarchy h ON e.ManagerId = h.Id
)
SELECT * FROM EmpHierarchy ORDER BY Level;
34 Q77. What is TEMP Table vs Table Variable? ▼ 
TEMP TABLE (#table):
CREATE TABLE #TempEmployees (
    Id INT, Name VARCHAR(100), Salary DECIMAL
);
INSERT INTO #TempEmployees SELECT Id, Name, Salary FROM Employee;
-- Exists until session ends or explicitly dropped
-- Stored in tempdb
-- Can have indexes
-- Visible in nested SPs
-- Better for large datasets

TABLE VARIABLE (@table):
DECLARE @TempEmployees TABLE (
    Id INT, Name VARCHAR(100), Salary DECIMAL
);
INSERT INTO @TempEmployees SELECT Id, Name, Salary FROM Employee;
-- Exists only in current batch/scope
-- Stored in memory (small) or tempdb (large)
-- Cannot have non-clustered indexes (before SQL 2014)
-- Not visible in nested SPs
-- Better for small datasets (< 1000 rows)

| Feature        | #Temp Table          | @Table Variable      |
|----------------|----------------------|----------------------|
| Scope          | Session/SP           | Batch/scope only     |
| Storage        | tempdb               | Memory/tempdb        |
| Indexes        | Yes (all types)      | Limited              |
| Statistics     | Yes                  | No                   |
| Transactions   | Affected by rollback | NOT affected         |
| Performance    | Better for large data| Better for small data|
| Recompilation  | May cause            | Does not cause       |
35 Q79. What are Window Functions (ROW_NUMBER, RANK, DENSE_RANK)? ▼ 
Window Functions perform calculations across a set of rows RELATED to 
current row, without collapsing rows (unlike GROUP BY).

SELECT 
    Name, Department, Salary,
    ROW_NUMBER() OVER (ORDER BY Salary DESC) AS RowNum,
    RANK() OVER (ORDER BY Salary DESC) AS Rank,
    DENSE_RANK() OVER (ORDER BY Salary DESC) AS DenseRank
FROM Employee;

| Name  | Salary | ROW_NUMBER | RANK | DENSE_RANK |
|-------|--------|------------|------|------------|
| Alice | 90000  | 1          | 1    | 1          |
| Bob   | 80000  | 2          | 2    | 2          |
| Carol | 80000  | 3          | 2    | 2          |
| Dave  | 70000  | 4          | 4    | 3          |

Differences:
- ROW_NUMBER: Always unique (1,2,3,4) � no ties
- RANK: Same rank for ties, SKIPS next (1,2,2,4)
- DENSE_RANK: Same rank for ties, NO skip (1,2,2,3)

SELECT Name, Department, Salary,

SELECT Name, Salary,

Page 3, 10 records per page:
SELECT * FROM Employee

OFFSET 20 ROWS          -- Skip first 20 (page 1 & 2)
FETCH NEXT 10 ROWS ONLY; -- Take next 10 (page 3)

SELECT

LEFT JOIN Employee m ON e.ManagerId = m.Id;

42 Q94. RANK() vs DENSE_RANK() vs ROW_NUMBER() ▼ 
Data: Salaries = 90000, 80000, 80000, 70000

ROW_NUMBER(): 1, 2, 3, 4 (always unique, arbitrary for ties)
RANK():       1, 2, 2, 4 (ties get same rank, next rank SKIPPED)
DENSE_RANK(): 1, 2, 2, 3 (ties get same rank, next rank NOT skipped)

Use cases:
- ROW_NUMBER: Pagination, unique numbering
- RANK: Competition ranking (1st, 2nd, 2nd, 4th)
- DENSE_RANK: Find Nth highest (no gaps)
43 Q95. @@IDENTITY vs SCOPE_IDENTITY() vs IDENT_CURRENT() ▼ 
@@IDENTITY:
- Last identity value generated in current SESSION
- ANY table, ANY scope (including triggers)
- Dangerous if trigger inserts into another identity table

SCOPE_IDENTITY():
- Last identity value in current SESSION and SCOPE
- Ignores trigger inserts
- RECOMMENDED

IDENT_CURRENT('TableName'):
- Last identity value for specific table
- ANY session, ANY scope
- Not safe for concurrent inserts

INSERT INTO Employee (Name) VALUES ('John');
SELECT SCOPE_IDENTITY();  -- Returns new Employee Id (safe)
SELECT @@IDENTITY;        -- Might return trigger's insert Id (unsafe)
44 Q96. What is a Cursor? Why avoid it? ▼ 
A Cursor processes rows ONE AT A TIME (row-by-row) instead of set-based.

DECLARE @Name VARCHAR(100)
DECLARE emp_cursor CURSOR FOR
    SELECT Name FROM Employee WHERE IsActive = 1;

OPEN emp_cursor;
FETCH NEXT FROM emp_cursor INTO @Name;

WHILE @@FETCH_STATUS = 0
BEGIN
    PRINT 'Processing: ' + @Name;
    FETCH NEXT FROM emp_cursor INTO @Name;
END

CLOSE emp_cursor;
DEALLOCATE emp_cursor;

Why AVOID cursors:
- VERY SLOW (row-by-row vs set-based)
- High memory usage
- Locks held longer
- 10-100x slower than set-based equivalent

Alternative (set-based - always prefer):
UPDATE Employee SET Salary = Salary * 1.1 WHERE IsActive = 1;
-- One statement processes ALL rows at once (fast!)
45 Q97. ISNULL vs COALESCE ▼ 
ISNULL(value, replacement):
- SQL Server specific
- Exactly 2 parameters
- Returns data type of first parameter

SELECT ISNULL(Phone, 'N/A') FROM Employee;

COALESCE(val1, val2, val3, ...):
- ANSI standard (portable)
- Multiple parameters (returns first non-null)
- Returns highest precedence data type

SELECT COALESCE(Phone, Mobile, WorkPhone, 'No Contact') FROM Employee;

Prefer COALESCE (standard, more flexible).
46 Q99. STRING_AGG / FOR XML PATH (String Concatenation) ▼ 
-- Combine multiple rows into one comma-separated string:

-- SQL Server 2017+ (STRING_AGG):
SELECT Department, STRING_AGG(Name, ', ') AS Employees
FROM Employee
GROUP BY Department;
-- Result: IT | John, Jane, Bob

-- Older versions (FOR XML PATH):
SELECT Department,
    STUFF((
        SELECT ', ' + Name 
        FROM Employee e2 
        WHERE e2.Department = e1.Department 
        FOR XML PATH('')
    ), 1, 2, '') AS Employees
FROM Employee e1
GROUP BY Department;

47What is Clustered vs Non-Clustered Index?▼
CLUSTERED INDEX:
- Physically sorts and stores data rows in the table
- Only ONE per table (like a phone book sorted by name)
- Primary Key creates clustered index by default
- Faster for range queries (WHERE Price BETWEEN 100 AND 500)
- Table IS the index (leaf nodes = actual data)

CREATE CLUSTERED INDEX IX_Employee_Id ON Employees(Id);

NON-CLUSTERED INDEX:
- Separate structure with pointers to actual data
- Multiple per table (up to 999)
- Like an index at the back of a book
- Contains: indexed columns + pointer to row
- Faster for specific lookups

CREATE NONCLUSTERED INDEX IX_Employee_Name ON Employees(LastName, FirstName);

| Feature          | Clustered            | Non-Clustered        |
|------------------|----------------------|----------------------|
| Count per table  | Only 1               | Up to 999            |
| Data storage     | Sorts actual data    | Separate structure   |
| Speed            | Fast for ranges      | Fast for lookups     |
| Size             | No extra space       | Extra storage needed |
| Leaf nodes       | Actual data rows     | Pointers to data     |

When to use Non-Clustered:
- Columns frequently used in WHERE clause
- Columns used in JOIN conditions
- Columns used in ORDER BY
- Foreign key columns

Covering Index (includes all needed columns):
CREATE INDEX IX_Order_Cover ON Orders(CustomerId)
INCLUDE (OrderDate, Total);  -- No need to go to table for these columns
48How to optimize a slow SQL query?▼
Step-by-step approach:

1. CHECK EXECUTION PLAN:
   - SET STATISTICS IO ON
   - SET STATISTICS TIME ON
   - Look for Table Scans (bad) vs Index Seeks (good)

2. ADD PROPER INDEXES:
   - Index columns in WHERE, JOIN, ORDER BY
   - Use covering indexes (INCLUDE)
   - Remove unused indexes

3. AVOID SELECT *:
   -- BAD:
   SELECT * FROM Orders WHERE CustomerId = 5
   -- GOOD:
   SELECT OrderId, OrderDate, Total FROM Orders WHERE CustomerId = 5

4. AVOID FUNCTIONS ON INDEXED COLUMNS:
   -- BAD (can't use index):
   WHERE YEAR(OrderDate) = 2024
   -- GOOD (uses index):
   WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'

5. USE EXISTS INSTEAD OF IN (for subqueries):
   -- Slower:
   WHERE Id IN (SELECT OrderId FROM OrderItems WHERE Qty > 10)
   -- Faster:
   WHERE EXISTS (SELECT 1 FROM OrderItems WHERE OrderId = Orders.Id AND Qty > 10)

6. PAGINATION:
   -- Use OFFSET-FETCH instead of loading all:
   ORDER BY Id OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY

7. AVOID CURSORS � Use set-based operations

8. UPDATE STATISTICS:
   UPDATE STATISTICS TableName

9. CHECK FOR PARAMETER SNIFFING:
   OPTION (RECOMPILE) -- Force new plan

10. AVOID N+1 in application code � Use JOINs or batch queries
49Write query to find Nth highest salary?▼
Method 1: Using DENSE_RANK (Best):
SELECT Salary FROM (
    SELECT Salary, DENSE_RANK() OVER (ORDER BY Salary DESC) AS Rank
    FROM Employees
) t
WHERE Rank = 3;  -- 3rd highest

Method 2: Using OFFSET-FETCH:
SELECT DISTINCT Salary
FROM Employees
ORDER BY Salary DESC
OFFSET 2 ROWS FETCH NEXT 1 ROWS ONLY;  -- 3rd highest (0-based offset)

Method 3: Using subquery:
SELECT MAX(Salary) FROM Employees
WHERE Salary < (SELECT MAX(Salary) FROM Employees);  -- 2nd highest only

Method 4: Generic Nth using CTE:
WITH RankedSalaries AS (
    SELECT Salary, DENSE_RANK() OVER (ORDER BY Salary DESC) AS Rank
    FROM Employees
)
SELECT DISTINCT Salary FROM RankedSalaries WHERE Rank = @N;

DENSE_RANK vs ROW_NUMBER vs RANK:
- ROW_NUMBER: 1,2,3,4,5 (no ties)
- RANK: 1,2,2,4,5 (ties skip numbers)
- DENSE_RANK: 1,2,2,3,4 (ties don't skip)

For salary questions, use DENSE_RANK (handles duplicate salaries correctly).
50What is CTE vs Temp Table vs Table Variable?▼
CTE (Common Table Expression):
- Temporary named result set within a single query
- Exists only during that query execution
- Good for readability and recursive queries
- No physical storage

- In-memory (small datasets)

- Good for small datasets (< 1000 rows)

DECLARE @Results TABLE (Id INT, Name NVARCHAR(100));

|----------------|----------------|----------------|----------------|
| Storage        | None (inline)  | tempdb         | Memory         |
| Indexes        | No             | Yes            | Limited        |
| Scope          | Single query   | Session        | Batch          |
| Best for       | Readability    | Large data     | Small data     |

51Stored Procedure vs Inline Query � when to use?▼
STORED PROCEDURE:
- Pre-compiled SQL stored in database
- Execution plan cached (faster repeated execution)
- Security (grant EXECUTE without table access)
- Reduces network traffic
- Can contain complex logic (IF, WHILE, TRY-CATCH)

CREATE PROCEDURE GetOrdersByCustomer
    @CustomerId INT,
    @FromDate DATE = NULL
AS
BEGIN
    SELECT o.Id, o.OrderDate, o.Total
    FROM Orders o
    WHERE o.CustomerId = @CustomerId
    AND (@FromDate IS NULL OR o.OrderDate >= @FromDate)
    ORDER BY o.OrderDate DESC;
END

-- Call:
EXEC GetOrdersByCustomer @CustomerId = 5, @FromDate = '2024-01-01';

INLINE QUERY (EF Core / Dapper):
- Written in application code
- Easier to maintain with code
- Version controlled with application
- EF Core generates optimized SQL

When to use SP:

- When DBA manages database

- Legacy systems

When to use Inline/EF Core:
- Simple CRUD operations
- When using Code First approach
- Rapid development
- When logic should be in application layer
- Microservices (DB per service)

52What are Window Functions (ROW_NUMBER, RANK, PARTITION BY)?▼
Window Functions perform calculations across a set of rows related to current row WITHOUT grouping.

ROW_NUMBER � Unique sequential number:
SELECT Name, Department, Salary,
    ROW_NUMBER() OVER (ORDER BY Salary DESC) AS RowNum
FROM Employees;
-- Result: 1, 2, 3, 4, 5 (no ties)

RANK � Rank with gaps for ties:
SELECT Name, Salary,
    RANK() OVER (ORDER BY Salary DESC) AS Rank
FROM Employees;
-- If two people have same salary: 1, 2, 2, 4, 5 (skips 3)

DENSE_RANK � Rank without gaps:
SELECT Name, Salary,
    DENSE_RANK() OVER (ORDER BY Salary DESC) AS DenseRank
FROM Employees;
-- If two people have same salary: 1, 2, 2, 3, 4 (no skip)

PARTITION BY � Window per group:
SELECT Name, Department, Salary,
    ROW_NUMBER() OVER (PARTITION BY Department ORDER BY Salary DESC) AS RankInDept
FROM Employees;
-- Ranks reset for each department!
-- IT: 1,2,3  HR: 1,2,3  Finance: 1,2,3

Practical: Top 3 earners per department:
WITH Ranked AS (
    SELECT *, DENSE_RANK() OVER (PARTITION BY Department ORDER BY Salary DESC) AS Rank
    FROM Employees
)
SELECT * FROM Ranked WHERE Rank <= 3;

Running Total:
SELECT OrderDate, Amount,
    SUM(Amount) OVER (ORDER BY OrderDate) AS RunningTotal
FROM Orders;
