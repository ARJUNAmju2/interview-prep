Git (Quick Essentials)

4 Questions — Usually 1-2 asked in interviews
1What is the difference between Git Merge and Rebase?▼
MERGE:
- Combines two branches by creating a NEW merge commit
- Preserves complete history (all commits visible)
- Non-destructive (safe)
- Creates a "merge commit" node

git checkout main
git merge feature-branch
// History: A--B--C--M (merge commit)
//               \  /
//                D--E (feature commits)

REBASE:
- Moves your branch commits ON TOP of another branch
- Creates LINEAR history (cleaner)
- Rewrites commit history (destructive)
- No merge commit

git checkout feature-branch
git rebase main
// History: A--B--C--D'--E' (linear, clean)

When to use:
- Merge: Public/shared branches (main, develop) — safe
- Rebase: Local/feature branches before merging — clean history

Golden Rule: NEVER rebase public/shared branches!

Team workflow:
git checkout feature/login
git rebase main              // Update feature with latest main
git checkout main
git merge feature/login      // Fast-forward merge (clean)
2What branching strategy do you follow?▼
GITFLOW (most common answer for interviews):

Branches:
- main (production-ready code)
- develop (integration branch)
- feature/* (new features)
- release/* (prepare for release)
- hotfix/* (urgent production fixes)

Flow:
1. Create feature branch from develop:
   git checkout -b feature/login develop

2. Work on feature, commit regularly

3. Merge back to develop:
   git checkout develop
   git merge feature/login

4. Create release branch when ready:
   git checkout -b release/1.0 develop

5. After testing, merge to main AND develop:
   git checkout main
   git merge release/1.0
   git tag v1.0

6. Hotfix (urgent):
   git checkout -b hotfix/bug-fix main
   // Fix → merge to main AND develop

TRUNK-BASED (simpler, modern):
- Everyone commits to main (or short-lived branches)
- Feature flags for incomplete features
- CI/CD deploys frequently
- Used by: Google, Facebook

Interview answer:
"We follow GitFlow. Feature branches from develop, 
PRs with code review, merge to develop, then release 
branches for production deployment."
3How do you resolve merge conflicts?▼
Merge conflict occurs when two branches modify the SAME line in the same file.

Steps to resolve:
1. Git marks conflicting files:
   <<<<<<< HEAD (your changes)
   public int Calculate() { return a + b; }
   =======
   public int Calculate() { return a * b; }
   >>>>>>> feature-branch (their changes)

2. Manually edit — keep correct code:
   public int Calculate() { return a + b; }  // Choose one or combine

3. Remove conflict markers (<<<, ===, >>>)

4. Stage and commit:
   git add .
   git commit -m "Resolved merge conflict in Calculator.cs"

Tools:
- VS Code built-in merge editor
- Visual Studio merge tool
- Beyond Compare / KDiff3

Prevention:
- Pull frequently (git pull --rebase)
- Small, focused branches
- Communicate with team about shared files
- Short-lived feature branches

Interview answer:
"I open the conflicting file, understand both changes, 
decide which to keep or combine both, remove markers, 
test the code, then commit. I use VS Code's merge editor 
for complex conflicts."
4What is a Pull Request (PR)? Your PR process?▼
Pull Request (PR) is a request to merge your branch into another branch, with code review by team members.

PR Process:
1. Create feature branch and implement
2. Push to remote: git push origin feature/login
3. Create PR on GitHub/Azure DevOps/Bitbucket
4. Add description, link to task/ticket
5. Reviewers review code, add comments
6. Address feedback, push fixes
7. Approve → Merge (squash/merge/rebase)
8. Delete feature branch

What I check in code review:
- Code follows team conventions
- No hardcoded values
- Proper error handling
- Unit tests included
- No security issues (SQL injection, exposed secrets)
- Performance (N+1 queries, unnecessary loops)
- SOLID principles followed

Common merge strategies:
- Merge commit: Preserves all commits (verbose history)
- Squash merge: Combines all into ONE commit (clean history)
- Rebase merge: Linear history without merge commit

Interview answer:
"I create a feature branch, implement the feature with 
small commits, push and create a PR. I add description 
and link the Jira ticket. Team reviews, I address comments, 
then we squash-merge to keep history clean."
