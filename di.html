Dependency Injection

1What is Dependency Injection (DI)?▼
Dependency Injection is a design pattern where an object receives its dependencies from OUTSIDE rather than creating them itself.

WITHOUT DI (tight coupling):
public class OrderService
{
    private SqlOrderRepository _repo = new SqlOrderRepository();  // Creates own dependency
    private SmtpEmailService _email = new SmtpEmailService();     // Hard-coded!

    public void PlaceOrder(Order order)
    {
        _repo.Save(order);
        _email.Send("Order placed");
    }
}
// Problems:
// - Can't test without real DB and SMTP
// - Can't swap implementations
// - Violates SOLID (DIP)

WITH DI (loose coupling):
public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly IEmailService _email;

    public OrderService(IOrderRepository repo, IEmailService email)  // Injected!
    {
        _repo = repo;
        _email = email;
    }

    public void PlaceOrder(Order order)
    {
        _repo.Save(order);
        _email.Send("Order placed");
    }
}

// Registration in Program.cs:
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddScoped<IEmailService, SmtpEmailService>();

Benefits:
- Loose coupling (depends on interface, not concrete class)
- Testable (inject mocks in unit tests)
- Swappable (change implementation without changing service)
- Follows SOLID principles (DIP)
2What is Scoped vs Transient vs Singleton?▼
Three service lifetimes in ASP.NET Core DI:

TRANSIENT (AddTransient):
- NEW instance every time it's requested
- Created fresh for each injection point
- Use for: Lightweight, stateless services

builder.Services.AddTransient<IEmailService, EmailService>();

// Controller gets instance A
// Service in same request gets instance B (different!)

SCOPED (AddScoped):
- ONE instance per HTTP REQUEST
- Same instance shared within a single request
- Disposed at end of request
- Use for: DbContext, repositories, per-request services

builder.Services.AddScoped<IOrderRepository, OrderRepository>();

// Controller gets instance A
// Service in same request gets instance A (same!)
// Next request gets instance B (new!)

SINGLETON (AddSingleton):
- ONE instance for ENTIRE application lifetime
- Same instance shared across ALL requests and users
- Created on first request, never disposed until app stops
- Use for: Caching, configuration, logging, HttpClient

builder.Services.AddSingleton<ICacheService, MemoryCacheService>();

// ALL requests, ALL users get same instance

| Lifetime  | Instance per      | Use for                    |
|-----------|-------------------|----------------------------|
| Transient | Every injection   | Lightweight, stateless     |
| Scoped    | HTTP request      | DbContext, repositories    |
| Singleton | App lifetime      | Cache, config, logging     |

IMPORTANT RULE:
- Singleton can inject: Singleton only
- Scoped can inject: Scoped + Singleton
- Transient can inject: Transient + Scoped + Singleton

// WRONG (captive dependency):
// Singleton service injecting Scoped service = BUG!
// The scoped service never gets disposed!
3What are types of Dependency Injection?▼
3 Types of DI:

1. CONSTRUCTOR INJECTION (Recommended in ASP.NET Core):
public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly ILogger<OrderService> _logger;

    public OrderService(IOrderRepository repo, ILogger<OrderService> logger)
    {
        _repo = repo;
        _logger = logger;
    }
}
// Dependencies are REQUIRED — class can't work without them
// Most common in ASP.NET Core

2. METHOD INJECTION (via parameter):
public class ReportService
{
    public void GenerateReport(IReportFormatter formatter)
    {
        // formatter injected per method call
        var data = GetData();
        formatter.Format(data);
    }
}
// Use when: dependency varies per method call

3. PROPERTY INJECTION (via setter):
public class NotificationService
{
    public ILogger Logger { get; set; }  // Optional dependency

    public void Notify(string message)
    {
        Logger?.LogInformation(message);  // May or may not be set
    }
}
// Use when: dependency is OPTIONAL
// Not recommended in ASP.NET Core (use constructor)

ASP.NET Core also supports:
// [FromServices] in action methods:
public IActionResult Index([FromServices] IProductService service)
{
    return View(service.GetAll());
}

// @inject in Razor views:
@inject IConfiguration Config
<p>@Config["AppName"]</p>

Best Practice: Always use Constructor Injection in ASP.NET Core.
4What is DI Container / IoC Container?▼
DI Container (IoC Container) is a framework that manages object creation and lifetime automatically.

ASP.NET Core has BUILT-IN DI container (IServiceProvider).

How it works:
1. REGISTER services at startup (what to create)
2. RESOLVE dependencies automatically (when needed)
3. DISPOSE when lifetime ends

// 1. Register (Program.cs):
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IProductService, ProductService>();
builder.Services.AddScoped<IEmailService, SmtpEmailService>();
builder.Services.AddSingleton<ICacheService, RedisCacheService>();

// 2. Resolve (automatic via constructor):
public class ProductController : Controller
{
    private readonly IProductService _service;  // Auto-resolved!

    public ProductController(IProductService service)
    {
        _service = service;
    }
}

// Container resolves entire dependency chain:
// ProductController needs IProductService
//   → ProductService needs IProductRepository
//     → ProductRepository needs DbContext
//       → DbContext needs connection string
// ALL resolved automatically!

Third-party containers (more features):
- Autofac
- Ninject
- Unity
- StructureMap

Built-in vs Autofac:
| Feature              | Built-in    | Autofac     |
|----------------------|-------------|-------------|
| Basic DI             | Yes         | Yes         |
| Named registrations  | No          | Yes         |
| Property injection   | No          | Yes         |
| Decorator pattern    | Manual      | Built-in    |
| Module registration  | No          | Yes         |

For most projects, built-in container is sufficient.
5How to register multiple implementations of same interface?▼
When you have multiple classes implementing the same interface:

public interface INotificationService { void Send(string msg); }
public class EmailNotification : INotificationService { ... }
public class SmsNotification : INotificationService { ... }
public class PushNotification : INotificationService { ... }

Method 1: Inject IEnumerable (get ALL):
builder.Services.AddScoped<INotificationService, EmailNotification>();
builder.Services.AddScoped<INotificationService, SmsNotification>();
builder.Services.AddScoped<INotificationService, PushNotification>();

public class OrderService
{
    private readonly IEnumerable<INotificationService> _notifiers;

    public OrderService(IEnumerable<INotificationService> notifiers)
    {
        _notifiers = notifiers;  // Gets ALL 3 implementations
    }

    public void NotifyAll(string message)
    {
        foreach (var notifier in _notifiers)
            notifier.Send(message);  // Sends via all channels
    }
}

Method 2: Factory pattern with keyed services (.NET 8):
builder.Services.AddKeyedScoped<INotificationService, EmailNotification>("email");
builder.Services.AddKeyedScoped<INotificationService, SmsNotification>("sms");

public class OrderService
{
    private readonly INotificationService _email;

    public OrderService([FromKeyedServices("email")] INotificationService email)
    {
        _email = email;
    }
}

Method 3: Manual factory:
builder.Services.AddScoped<EmailNotification>();
builder.Services.AddScoped<SmsNotification>();
builder.Services.AddScoped<Func<string, INotificationService>>(sp => key =>
{
    return key switch
    {
        "email" => sp.GetRequiredService<EmailNotification>(),
        "sms" => sp.GetRequiredService<SmsNotification>(),
        _ => throw new ArgumentException()
    };
});
6What is Captive Dependency problem?▼
Captive Dependency: When a longer-lived service captures a shorter-lived service, causing the shorter-lived one to live longer than intended.

PROBLEM:
// Singleton captures Scoped — BUG!
builder.Services.AddSingleton<ICacheService, CacheService>();
builder.Services.AddScoped<IDbContext, AppDbContext>();

public class CacheService : ICacheService  // Singleton (lives forever)
{
    private readonly IDbContext _context;  // Scoped (should die per request)

    public CacheService(IDbContext context)
    {
        _context = context;  // This DbContext NEVER gets disposed!
        // Same stale DbContext used for ALL requests = data bugs!
    }
}

RULES:
✓ Singleton → can inject → Singleton only
✓ Scoped    → can inject → Scoped + Singleton
✓ Transient → can inject → Transient + Scoped + Singleton

✗ Singleton → CANNOT inject → Scoped or Transient
✗ Scoped    → CANNOT inject → (nothing restricted below)

SOLUTION - Use IServiceScopeFactory:
public class CacheService : ICacheService  // Singleton
{
    private readonly IServiceScopeFactory _scopeFactory;

    public CacheService(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task RefreshCache()
    {
        using var scope = _scopeFactory.CreateScope();
        var context = scope.ServiceProvider.GetRequiredService<IDbContext>();
        // Now DbContext is properly scoped and disposed!
    }
}

ASP.NET Core validates this at startup (in Development):
// Throws error if captive dependency detected
builder.Services.BuildServiceProvider(new ServiceProviderOptions
{
    ValidateScopes = true
});
7How does DI work in ASP.NET Core? Show complete example.▼
Complete DI flow in ASP.NET Core:

// 1. Define interfaces:
public interface IProductService
{
    Task<List<Product>> GetAllAsync();
    Task<Product> GetByIdAsync(int id);
    Task CreateAsync(ProductDto dto);
}

// 2. Implement:
public class ProductService : IProductService
{
    private readonly IProductRepository _repo;
    private readonly ILogger<ProductService> _logger;

    public ProductService(IProductRepository repo, ILogger<ProductService> logger)
    {
        _repo = repo;
        _logger = logger;
    }

    public async Task<List<Product>> GetAllAsync()
    {
        _logger.LogInformation("Getting all products");
        return await _repo.GetAllAsync();
    }
}

// 3. Register in Program.cs:
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(connStr));
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IProductService, ProductService>();

// 4. Inject in Controller:
public class ProductController : Controller
{
    private readonly IProductService _service;

    public ProductController(IProductService service)
    {
        _service = service;  // DI container provides this automatically
    }

    public async Task<IActionResult> Index()
    {
        var products = await _service.GetAllAsync();
        return View(products);
    }
}

// DI resolves the ENTIRE chain:
// Controller → IProductService → ProductService
//   → IProductRepository → ProductRepository → DbContext
//   → ILogger → Logger
// ALL automatic!
8How does DI help in Unit Testing?▼
DI makes code testable by allowing you to inject MOCK objects instead of real ones.

Without DI (untestable):
public class OrderService
{
    private SqlRepository _repo = new SqlRepository();  // Real DB!
    // Can't test without actual database connection
}

With DI (testable):
public class OrderService
{
    private readonly IOrderRepository _repo;
    public OrderService(IOrderRepository repo) { _repo = repo; }
}

Unit Test (using Moq):
[Fact]
public async Task PlaceOrder_ValidOrder_SavesAndReturnsTrue()
{
    // Arrange - Create mock
    var mockRepo = new Mock<IOrderRepository>();
    mockRepo.Setup(r => r.SaveAsync(It.IsAny<Order>()))
            .ReturnsAsync(true);

    var mockEmail = new Mock<IEmailService>();

    var service = new OrderService(mockRepo.Object, mockEmail.Object);

    // Act
    var result = await service.PlaceOrder(new Order { Id = 1, Total = 100 });

    // Assert
    Assert.True(result);
    mockRepo.Verify(r => r.SaveAsync(It.IsAny<Order>()), Times.Once);
    mockEmail.Verify(e => e.SendAsync(It.IsAny<string>(), It.IsAny<string>()), Times.Once);
}

// No real database! No real email server!
// Fast, isolated, reliable tests.

Benefits:
- Test business logic in isolation
- No external dependencies (DB, API, email)
- Fast execution
- Predictable results
- Can test edge cases easily
