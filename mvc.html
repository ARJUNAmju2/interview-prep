MVC Interview Questions

1 Q1. What is MVC (Model-View-Controller) design pattern? ▼ 
MVC is a software architectural/design pattern that separates an application 
into three main interconnected components:

- Model: Represents data and business logic
- View: Represents the UI/presentation layer
- Controller: Handles user input and acts as intermediary between Model and View

The main goal is "Separation of Concerns" — each component has a single 
responsibility, making the application easier to develop, test, and maintain.

Flow:
User Request ? Controller ? Model (data) ? Controller ? View ? Response to User
2 Q2. What is Model, View, and Controller — explain each with responsibilities? ▼ 
MODEL:
- Represents the data and business logic of the application
- Contains classes that define the shape of data (properties)
- Handles data validation using Data Annotations
- Communicates with database (via EF Core or other ORM)
- Examples: Employee.cs, Product.cs, OrderViewModel.cs

VIEW:
- Responsible for presenting data to the user (UI)
- Contains HTML, CSS, JavaScript with Razor syntax (.cshtml files)
- Should NOT contain business logic
- Receives data from Controller and renders it
- Examples: Index.cshtml, Create.cshtml, Edit.cshtml

CONTROLLER:
- Acts as the coordinator between Model and View
- Handles incoming HTTP requests
- Processes user input
- Calls business logic/services
- Selects which View to return
- Examples: HomeController.cs, ProductController.cs
3 Q3. What is the flow of request in MVC architecture? ▼ 
Step-by-step flow:

1. User sends HTTP request (e.g., types URL in browser)
2. Routing engine matches the URL to a specific Controller/Action
3. Controller is instantiated by Controller Factory
4. Action method is invoked by Action Invoker
5. Action method processes the request:
   - May interact with Model/Database
   - May call services/business logic
6. Action method returns an ActionResult (View, JSON, Redirect, etc.)
7. View Engine (Razor) renders the View with Model data
8. HTML response is sent back to the user's browser

Example:
URL: /Product/Details/5
? ProductController ? Details(int id=5) ? fetches product ? returns View(product)
4 Q4. Why MVC pattern is used? What problems does it solve? ▼ 
Problems it solves:
1. Tight Coupling: Without MVC, UI and business logic are mixed together
2. Testability: Hard to unit test when everything is in one place
3. Maintainability: Changes in UI affect business logic and vice versa
4. Team Collaboration: Multiple developers can't work independently
5. Code Reusability: Same logic repeated in multiple places

Benefits of MVC:
- Separation of Concerns (SoC)
- Parallel development (UI dev + backend dev work simultaneously)
- Easy unit testing (test Controller without View)
- Multiple Views for same Model (web, mobile, API)
- Clean URLs with routing
- Better code organization and maintainability
- Supports TDD (Test-Driven Development)
5 Q5. What are the advantages and disadvantages of MVC? ▼ 
ADVANTAGES:
- Clear separation of concerns
- Easy to unit test
- Supports multiple views for same data
- SEO-friendly URLs
- Full control over HTML output
- No ViewState or Page lifecycle (lighter than WebForms)
- Parallel development possible
- Easy integration with JavaScript frameworks
- Better for large-scale applications

DISADVANTAGES:
- Steeper learning curve for beginners
- More files and folders to manage
- Complexity increases for small applications
- No drag-and-drop like WebForms
- Requires understanding of HTTP, HTML, CSS
- More code needed compared to WebForms for simple CRUD
6 Q6. What is Separation of Concerns (SoC) in MVC? ▼ 
Separation of Concerns means each component has ONE specific responsibility 
and doesn't overlap with others:

- Model: ONLY handles data and business rules
- View: ONLY handles presentation/UI
- Controller: ONLY handles request coordination

Example of VIOLATION (bad practice):
- Writing SQL queries in Controller
- Writing business logic in View
- Writing HTML in Controller

Example of PROPER SoC:
- Controller calls a Service ? Service calls Repository ? Repository calls DB
- Controller passes ViewModel to View
- View only displays data, no calculations

Benefits:
- Change UI without touching business logic
- Change database without touching UI
- Test each layer independently
7 Q7. What is the difference between MVC and 3-Tier Architecture? ▼ 
MVC (Design Pattern):
- Presentation pattern for organizing UI code
- Model, View, Controller
- Controller directly communicates with Model
- Primarily about UI organization
- All 3 components can be in same project

3-Tier Architecture (Architectural Pattern):
- Application-level architecture
- Presentation Layer, Business Logic Layer (BLL), Data Access Layer (DAL)
- Each tier is physically/logically separated
- Tiers communicate through interfaces
- Can be deployed on different servers

Key Difference:
- MVC is a DESIGN PATTERN (how to organize code)
- 3-Tier is an ARCHITECTURE PATTERN (how to structure application)
- They can be used TOGETHER: MVC in Presentation Tier + BLL + DAL

Example:
Presentation (MVC) ? Business Layer (Services) ? Data Layer (Repository/EF Core)
8 Q8. What is the difference between MVC vs MVP vs MVVM? ▼ 
MVC (Model-View-Controller):
- Controller handles user input
- View is passive, receives data from Controller
- Used in: ASP.NET Core MVC, Ruby on Rails, Spring MVC
- Flow: User ? Controller ? Model ? View

MVP (Model-View-Presenter):
- Presenter handles all logic
- View is completely passive (interface-based)
- Presenter updates View through interface
- Used in: Windows Forms, older Android
- Flow: User ? View ? Presenter ? Model ? Presenter ? View

MVVM (Model-View-ViewModel):
- ViewModel exposes data via data binding
- Two-way data binding between View and ViewModel
- View automatically updates when ViewModel changes
- Used in: WPF, Angular, React, Blazor
- Flow: User ? View ? ViewModel ? Model

Key Differences:
| Aspect      | MVC              | MVP              | MVVM             |
|-------------|------------------|------------------|------------------|
| Input       | Controller       | View             | View             |
| Binding     | One-way          | Manual           | Two-way          |
| Testability | Good             | Better           | Best             |
| Complexity  | Low              | Medium           | High             |

9 Q9. What is a Model in MVC? ▼ 
A Model represents the data and business logic of the application.

Types of Models:
1. Domain Model / Entity Model: Represents database table
2. ViewModel: Shaped for a specific View's needs
3. DTO (Data Transfer Object): For transferring data between layers

Example - Domain Model:
public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
    public decimal Salary { get; set; }
    public int DepartmentId { get; set; }
    public Department Department { get; set; }  // Navigation property
}

Responsibilities of Model:
- Define data structure (properties)
- Data validation rules (Data Annotations)
- Business rules and calculations
- Relationships between entities
10 Q10. What is the difference between ViewModel, DTO, and Domain Model? ▼ 
DOMAIN MODEL (Entity):
- Directly maps to database table
- Contains navigation properties
- Used by EF Core for database operations
- Should NOT be exposed directly to View

Example:
public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string PasswordHash { get; set; }  // Sensitive!
    public decimal Salary { get; set; }
    public Department Department { get; set; }
}

VIEWMODEL:
- Shaped specifically for a View's requirements
- May combine data from multiple entities
- Contains only what the View needs
- Contains UI-specific validation

Example:
public class EmployeeCreateViewModel
{
    [Required]
    public string Name { get; set; }
    
    [EmailAddress]
    public string Email { get; set; }
    
    public List<SelectListItem> Departments { get; set; }  // For dropdown
    public int SelectedDepartmentId { get; set; }
}

DTO (Data Transfer Object):
- Used to transfer data between layers/services
- No behavior, only properties
- Used in API responses
- Flat structure (no navigation properties)

Example:
public class EmployeeDto
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string DepartmentName { get; set; }  // Flattened
}

Key Differences:
| Aspect       | Domain Model      | ViewModel          | DTO              |
|--------------|-------------------|--------------------|------------------|
| Purpose      | Database mapping  | View-specific      | Data transfer    |
| Validation   | Business rules    | UI validation      | Minimal          |
| Used in      | DAL/Repository    | Controller ? View  | API/Services     |
| Contains     | All properties    | View-needed only   | Transfer-needed  |
11 Q11. What is a Strongly Typed View? ▼ 
A Strongly Typed View is a View that is bound to a specific Model class using 
the @model directive at the top of the .cshtml file.

Example:
@model Employee   ? This makes it strongly typed

<h2>@Model.Name</h2>
<p>Email: @Model.Email</p>
<p>Salary: @Model.Salary</p>

Controller:
public IActionResult Details(int id)
{
    Employee emp = _context.Employees.Find(id);
    return View(emp);  // Passing strongly typed model
}

Benefits:
- Compile-time type checking (errors caught at build time)
- IntelliSense support in Visual Studio
- No need for type casting
- Cleaner and safer code
- Refactoring support
12 Q12. What is the difference between Strongly Typed and Weakly Typed Views? ▼ 
STRONGLY TYPED VIEW:
- Uses @model directive
- Compile-time checking
- IntelliSense available
- Type-safe
- Recommended approach

Example:
@model Employee
<h2>@Model.Name</h2>

WEAKLY TYPED VIEW (using ViewData/ViewBag):
- No @model directive needed
- No compile-time checking
- No IntelliSense
- Requires type casting
- Error-prone

Example:
// Controller
ViewData["Name"] = "John";
ViewBag.Salary = 50000;

// View
<h2>@ViewData["Name"]</h2>
<p>@ViewBag.Salary</p>

Why Strongly Typed is preferred:
- If you rename a property, compiler catches the error
- ViewBag errors only appear at runtime
- Better maintainability
- Professional standard
13 Q13. When to use ViewModel vs passing Model directly? ▼ 
USE MODEL DIRECTLY when:
- View needs all properties of the entity
- Simple CRUD operations
- No additional data needed (like dropdowns)
- No security concern (no sensitive fields)

Example:
public IActionResult Details(int id)
{
    var product = _repo.GetById(id);
    return View(product);  // Direct model
}

USE VIEWMODEL when:
- View needs data from MULTIPLE entities
- Need to exclude sensitive properties (password, etc.)
- Need additional UI data (dropdown lists, flags)
- Form has different shape than database table
- Need UI-specific validation different from entity validation

Example:
public IActionResult Create()
{
    var viewModel = new EmployeeCreateViewModel
    {
        Departments = _deptRepo.GetAll().Select(d => new SelectListItem
        {
            Value = d.Id.ToString(),
            Text = d.Name
        }).ToList()
    };
    return View(viewModel);
}

Best Practice: ALWAYS use ViewModels for Create/Edit forms.
14 Q14. What is AutoMapper and why is it used? ▼ 
AutoMapper is a library that automatically maps properties from one object to 
another, eliminating manual property-by-property copying.

Without AutoMapper (manual mapping):
var viewModel = new EmployeeViewModel
{
    Id = employee.Id,
    Name = employee.Name,
    Email = employee.Email,
    DepartmentName = employee.Department.Name
    // Imagine 20+ properties...
};

With AutoMapper:
// Configuration (in Program.cs or Profile class)
public class MappingProfile : Profile
{
    public MappingProfile()
    {
        CreateMap<Employee, EmployeeViewModel>();
        CreateMap<EmployeeCreateViewModel, Employee>();
    }
}

// Usage in Controller
var viewModel = _mapper.Map<EmployeeViewModel>(employee);
var employee = _mapper.Map<Employee>(createViewModel);

Setup in ASP.NET Core:
// Program.cs
builder.Services.AddAutoMapper(typeof(MappingProfile));

// Controller
public class EmployeeController : Controller
{
    private readonly IMapper _mapper;
    
    public EmployeeController(IMapper mapper)
    {
        _mapper = mapper;
    }
}

Benefits:
- Reduces boilerplate code
- Convention-based (matches by property name)
- Supports custom mappings for complex scenarios
- Reduces errors in manual mapping
- Easy to maintain
15 Q15. What is Data Annotation in Model? ▼ 
Data Annotations are attributes applied to Model properties to define 
validation rules, display settings, and database schema configurations.

Namespace: System.ComponentModel.DataAnnotations

Common Validation Annotations:
public class Employee
{
    [Key]
    public int Id { get; set; }
    
    [Required(ErrorMessage = "Name is required")]
    [StringLength(100, MinimumLength = 2)]
    [Display(Name = "Full Name")]
    public string Name { get; set; }
    
    [Required]
    [EmailAddress(ErrorMessage = "Invalid email format")]
    public string Email { get; set; }
    
    [Range(18, 65, ErrorMessage = "Age must be between 18-65")]
    public int Age { get; set; }
    
    [Required]
    [DataType(DataType.Password)]
    [MinLength(8)]
    public string Password { get; set; }
    
    [Compare("Password", ErrorMessage = "Passwords don't match")]
    public string ConfirmPassword { get; set; }
    
    [Phone]
    public string PhoneNumber { get; set; }
    
    [Url]
    public string Website { get; set; }
    
    [RegularExpression(@"^[A-Z]{2}\d{4}$", ErrorMessage = "Invalid code")]
    public string EmployeeCode { get; set; }
}

Categories:
1. Validation: [Required], [StringLength], [Range], [RegularExpression]
2. Display: [Display], [DisplayFormat], [DataType]
3. Database/EF: [Key], [Table], [Column], [ForeignKey], [NotMapped]
4. Comparison: [Compare]

17 Q17. What is Razor View Engine? ▼ 
Razor is the view engine in ASP.NET Core that allows mixing C# code with HTML 
using a clean and concise syntax.

Razor Syntax Rules:
- @ symbol transitions from HTML to C#
- @{ } for multi-line C# code blocks
- @Model to access the model
- @if, @foreach, @for for control structures

Examples:
<!-- Single expression -->
<h1>Hello, @Model.Name</h1>

<!-- Code block -->
@{
    var greeting = "Welcome";
    var currentDate = DateTime.Now;
}
<p>@greeting, today is @currentDate.ToShortDateString()</p>

<!-- Conditional -->
@if (Model.IsAdmin)
{
    <p>Admin Panel</p>
}
else
{
    <p>User Panel</p>
}

<!-- Loop -->
@foreach (var item in Model.Products)
{
    <li>@item.Name - @item.Price.ToString("C")</li>
}

<!-- Raw HTML output -->
@Html.Raw("<b>Bold Text</b>")

<!-- Explicit expression -->
<p>Email: @(Model.FirstName)@domain.com</p>

Features:
- Compact syntax (less typing than ASPX <% %>)
- IntelliSense support
- Automatic HTML encoding (prevents XSS)
- Supports C# and VB.NET
18 Q18. What is the difference between Razor and ASPX View Engine? ▼ 
RAZOR (.cshtml):
- Syntax: @Model.Name, @{ code }, @if() { }
- File extension: .cshtml
- Compact and clean
- Automatic HTML encoding
- Used in ASP.NET Core (default and only option)
- IntelliSense support
- Less typing required

ASPX (.aspx) - Web Forms View Engine:
- Syntax: <%= Model.Name %>, <% code %>, <%: encoded %>
- File extension: .aspx
- Verbose syntax
- Manual encoding needed
- Used in older ASP.NET MVC (1-5)
- NOT available in ASP.NET Core

Comparison:
Razor:    <p>Hello, @Model.Name</p>
ASPX:     <p>Hello, <%: Model.Name %></p>

Razor:    @if(condition) { <p>Yes</p> }
ASPX:     <% if(condition) { %> <p>Yes</p> <% } %>

Note: In ASP.NET Core, only Razor is supported. ASPX is legacy.
19 Q19. What is _Layout.cshtml (Master Page concept)? ▼ 
_Layout.cshtml is the master/template page that defines the common structure 
shared across multiple views (like header, footer, navigation).

Location: Views/Shared/_Layout.cshtml

Example _Layout.cshtml:
<!DOCTYPE html>
<html>
<head>
    <title>@ViewData["Title"] - My App</title>
    <link rel="stylesheet" href="~/css/site.css" />
    @RenderSection("Styles", required: false)
</head>
<body>
    <header>
        <nav><!-- Navigation menu --></nav>
    </header>
    
    <main>
        @RenderBody()   ? Child view content renders here
    </main>
    
    <footer>
        <p>&copy; 2024 My Company</p>
    </footer>
    
    <script src="~/js/site.js"></script>
    @RenderSection("Scripts", required: false)
</body>
</html>

Child View (Index.cshtml):
@{
    ViewData["Title"] = "Home";
}

<h1>Welcome to Home Page</h1>
<p>This content goes into @RenderBody()</p>

@section Scripts {
    <script src="~/js/home.js"></script>
}

Key Points:
- @RenderBody() — renders the child view content (required, only one)
- @RenderSection() — renders named sections from child views
- Multiple layouts possible (admin layout, public layout)
- Can be nested (layout within layout)
20 Q20. What is _ViewStart.cshtml and its purpose? ▼ 
_ViewStart.cshtml contains code that runs BEFORE every view is rendered.
It's primarily used to set the default Layout for all views.

Location: Views/_ViewStart.cshtml

Content:
@{
    Layout = "_Layout";
}

How it works:
- Executes before each view in the same folder or subfolders
- Sets default layout so you don't repeat it in every view
- Can be overridden in individual views
- Can have multiple _ViewStart files (hierarchical)

Override in specific view:
@{
    Layout = "_AdminLayout";  // Use different layout
}
// OR
@{
    Layout = null;  // No layout (standalone page)
}

Hierarchical example:
Views/_ViewStart.cshtml          ? Layout = "_Layout" (default for all)
Views/Admin/_ViewStart.cshtml    ? Layout = "_AdminLayout" (for Admin views)
21 Q21. What is _ViewImports.cshtml? ▼ 
_ViewImports.cshtml contains common directives (using statements, tag helpers, 
etc.) that are automatically applied to all views in the same folder and subfolders.

Location: Views/_ViewImports.cshtml

Typical content:
@using MyApp
@using MyApp.Models
@using MyApp.ViewModels
@addTagHelper *, Microsoft.AspNetCore.Mvc.TagHelpers
@addTagHelper *, MyApp.TagHelpers

Purpose:
- Avoids repeating @using statements in every view
- Registers Tag Helpers globally
- Sets common namespaces

Without _ViewImports (every view would need):
@using MyApp.Models
@model Employee
<h1>@Model.Name</h1>

With _ViewImports (cleaner views):
@model Employee
<h1>@Model.Name</h1>

Can also contain:
- @inject (for DI in views)
- @model (common base model)
- @addTagHelper / @removeTagHelper
22 Q22. What are Partial Views and when to use them? ▼ 
A Partial View is a reusable view component that renders a portion of HTML.
It's like a "sub-view" that can be embedded in other views.

Use cases:
- Reusable UI components (navigation, sidebar, footer)
- Breaking large views into smaller manageable pieces
- Rendering repeated content (product card, employee row)

Creating a Partial View:
File: Views/Shared/_EmployeeCard.cshtml
@model Employee

<div class="card">
    <h3>@Model.Name</h3>
    <p>@Model.Email</p>
    <p>@Model.Department</p>
</div>

Using Partial View in parent view:
<!-- Method 1: Tag Helper (recommended in ASP.NET Core) -->
<partial name="_EmployeeCard" model="employee" />

<!-- Method 2: HTML Helper -->
@await Html.PartialAsync("_EmployeeCard", employee)

<!-- Method 3: In a loop -->
@foreach (var emp in Model.Employees)
{
    <partial name="_EmployeeCard" model="emp" />
}

Naming Convention: Prefix with underscore (_EmployeeCard.cshtml)

Key Points:
- Does NOT have its own Controller action
- Receives model from parent view
- Cannot have its own Layout
- Rendered inline within parent view
23 Q23. What is the difference between Html.Partial vs Html.RenderPartial? ▼ 
Html.Partial():
- Returns: MvcHtmlString (HTML string)
- Renders output to a STRING first, then writes to response
- Can be assigned to a variable
- Slightly slower (extra string allocation)
- Syntax: @Html.Partial("_PartialView", model)

Html.RenderPartial():
- Returns: void
- Writes DIRECTLY to the response output stream
- Cannot be assigned to a variable
- Slightly faster (no intermediate string)
- Must be used inside @{ } code block
- Syntax: @{ Html.RenderPartial("_PartialView", model); }

ASP.NET Core equivalents:
- @await Html.PartialAsync("_PartialView", model)
- @{ await Html.RenderPartialAsync("_PartialView", model); }
- <partial name="_PartialView" model="model" />  ? Recommended

When to use which:
- Use Html.Partial / PartialAsync for simple cases
- Use RenderPartial / RenderPartialAsync for large content (better performance)
- Use <partial> Tag Helper in ASP.NET Core (cleanest syntax)
24 Q24. What is the difference between Html.Action vs Html.RenderAction? ▼ 
Note: These are from ASP.NET MVC 5. In ASP.NET Core, use View Components instead.

Html.Action():
- Calls a CHILD ACTION method on a Controller
- Returns MvcHtmlString
- The action method must be marked with [ChildActionOnly]
- Can have its own logic, database calls, etc.

Html.RenderAction():
- Same as Html.Action but writes directly to output stream
- Returns void
- Better performance for large content

Example (MVC 5):
// Controller
[ChildActionOnly]
public ActionResult CategoryMenu()
{
    var categories = _repo.GetAll();
    return PartialView("_CategoryMenu", categories);
}

// View
@Html.Action("CategoryMenu", "Category")

ASP.NET Core Replacement ? View Components:
// ViewComponent
public class CategoryMenuViewComponent : ViewComponent
{
    public async Task<IViewComponentResult> InvokeAsync()
    {
        var categories = await _repo.GetAllAsync();
        return View(categories);
    }
}

// View
@await Component.InvokeAsync("CategoryMenu")
// OR
<vc:category-menu></vc:category-menu>
25 Q25. What are View Components and how are they different from Partial Views? ▼ 
View Components are reusable UI components that have their own logic 
(like mini-controllers). They are the ASP.NET Core replacement for 
[ChildActionOnly] actions.

PARTIAL VIEW:
- No independent logic
- Receives data from parent view
- Just renders HTML
- Simple, lightweight

VIEW COMPONENT:
- Has its own class with logic (like a mini-controller)
- Can have its own data access, DI
- Independent of parent view's model
- More powerful and testable

Creating a View Component:

Step 1: Create the class
public class RecentProductsViewComponent : ViewComponent
{
    private readonly IProductRepository _repo;
    
    public RecentProductsViewComponent(IProductRepository repo)
    {
        _repo = repo;
    }
    
    public async Task<IViewComponentResult> InvokeAsync(int count = 5)
    {
        var products = await _repo.GetRecentAsync(count);
        return View(products);
    }
}

Step 2: Create the View
Location: Views/Shared/Components/RecentProducts/Default.cshtml
@model List<Product>

<div class="recent-products">
    @foreach (var product in Model)
    {
        <div>@product.Name - @product.Price</div>
    }
</div>

Step 3: Use in any View
@await Component.InvokeAsync("RecentProducts", new { count = 10 })
// OR using Tag Helper
<vc:recent-products count="10"></vc:recent-products>

When to use View Components:
- Dynamic navigation menus
- Shopping cart widget
- Login panel
- Sidebar content
- Any reusable component needing its own data/logic
26 Q26. What are Sections in Layout (@RenderSection, @RenderBody)? ▼ 
Sections allow child views to inject content into specific areas of the Layout.

@RenderBody():
- Renders the MAIN content of the child view
- Only ONE @RenderBody() per layout
- Required — every layout must have it
- All content in child view (not in a section) goes here

@RenderSection():
- Renders named sections defined in child views
- Can be required or optional
- Multiple sections allowed

Layout (_Layout.cshtml):
<html>
<head>
    <title>@ViewData["Title"]</title>
    <link href="~/css/site.css" rel="stylesheet" />
    @RenderSection("Styles", required: false)
</head>
<body>
    <nav>...</nav>
    
    <div class="container">
        @RenderBody()
    </div>
    
    <footer>...</footer>
    
    <script src="~/js/site.js"></script>
    @RenderSection("Scripts", required: false)
</body>
</html>

Child View (Create.cshtml):
@{
    ViewData["Title"] = "Create Product";
}

<h1>Create Product</h1>
<form>...</form>

@section Styles {
    <link href="~/css/form-styles.css" rel="stylesheet" />
}

@section Scripts {
    <script src="~/js/validation.js"></script>
    <partial name="_ValidationScriptsPartial" />
}

Parameters:
- required: true ? child view MUST define this section (error if missing)
- required: false ? section is optional

Check if section is defined:
@if (IsSectionDefined("Sidebar"))
{
    @RenderSection("Sidebar")
}
else
{
    <p>Default sidebar content</p>
}

31 Q31. What is Client-Side vs Server-Side rendering? ▼ 
SERVER-SIDE RENDERING (SSR):
- HTML is generated on the SERVER
- Browser receives complete HTML
- Used in: ASP.NET Core MVC (Razor Views)
- Each page request = full HTML from server

Flow: Request ? Server generates HTML ? Full HTML sent to browser

Pros:
- Better SEO (search engines can read content)
- Faster initial page load
- Works without JavaScript
- Better for content-heavy sites

Cons:
- Full page reload for every action
- More server load
- Slower subsequent interactions

CLIENT-SIDE RENDERING (CSR):
- HTML is generated in the BROWSER using JavaScript
- Server sends minimal HTML + JavaScript bundle
- Used in: React, Angular, Vue.js
- Single Page Application (SPA)

Flow: Request ? Server sends JS bundle ? Browser renders HTML

Pros:
- Rich, interactive UI
- No full page reloads (faster after initial load)
- Better user experience
- Less server load after initial request

Cons:
- Slower initial load (download JS bundle)
- Poor SEO (without SSR/pre-rendering)
- Requires JavaScript enabled
- More complex development

HYBRID APPROACH:
- ASP.NET Core MVC + AJAX calls
- Server renders initial page, JavaScript handles interactions
- Best of both worlds for many applications

Example in MVC:
// Server-side: Full page render
public IActionResult Index()
{
    var products = _repo.GetAll();
    return View(products);  // Server renders full HTML
}

// Client-side: AJAX partial update
// JavaScript fetches data and updates DOM without page reload
fetch('/api/products')
    .then(response => response.json())
    .then(data => renderProducts(data));

35 Q35. What is IActionResult and why is it used? ▼ 
IActionResult is an interface that represents the result of an action method.
It allows returning DIFFERENT types of responses from the same action.

Why use IActionResult:
- Flexibility to return different response types
- Can return View, JSON, Redirect, File, StatusCode, etc.
- Polymorphism — one return type, multiple implementations

{

        return NotFound();           // 404 StatusCodeResult

        return Unauthorized();       // 401 UnauthorizedResult
    
    if (Request.Headers["Accept"] == "application/json")
        return Json(product);        // JsonResult

{

    if (product == null)
        return NotFound();
    return product;  // Automatically wraps in OkObjectResult

- IActionResult: Can return any result type (most flexible)

37 Q37. What is RedirectToAction vs RedirectToRoute vs Redirect? ▼ 
All three perform HTTP 302 redirect but differ in how they specify the target:

Redirect(string url):
- Redirects to an absolute or relative URL string
- No route validation
- Can redirect to external URLs
return Redirect("https://google.com");
return Redirect("/Product/Index");

RedirectToAction(action, controller, routeValues):
- Redirects to a specific Controller/Action
- Route-aware (generates URL from route table)
- Type-safe with nameof()
return RedirectToAction("Index");                          // Same controller
return RedirectToAction("Index", "Product");               // Different controller
return RedirectToAction("Details", "Product", new { id = 5 }); // With params
return RedirectToAction(nameof(Index));                    // Type-safe

RedirectToRoute(routeName, routeValues):
- Redirects using a named route
- Useful for custom named routes
return RedirectToRoute("ProductDetails", new { id = 5 });

Permanent Redirects (301):
return RedirectPermanent("/new-url");
return RedirectToActionPermanent("Index", "Product");
return RedirectToRoutePermanent("routeName");

LocalRedirect(string localUrl):
- Only allows local URLs (prevents open redirect attacks)
- Throws exception for external URLs
return LocalRedirect("/Product/Index");  // OK
return LocalRedirect("https://evil.com");  // Throws exception!

41 Q41. How does TempData work internally (TempData providers)? ▼ 
TempData stores data that persists for ONE subsequent request (typically 
used with redirects in PRG pattern).

Internal Working:
1. Data is stored at end of current request
2. Data is loaded at beginning of next request
3. Data is MARKED FOR DELETION after being read
4. Data is actually deleted at end of that request

TempData Providers (storage mechanisms):

1. Cookie-based (Default in ASP.NET Core):
builder.Services.AddControllersWithViews()
    .AddCookieTempDataProvider();
- Stores data in encrypted cookies
- Limited size (~4KB)
- No server memory needed

2. Session-based:
builder.Services.AddControllersWithViews()
    .AddSessionStateTempDataProvider();
builder.Services.AddSession();
- Stores data in server session
- Larger data possible
- Requires session configuration

Lifecycle:
Request 1: TempData["Msg"] = "Saved";  ? Stored
           RedirectToAction("Index");
           
Request 2: var msg = TempData["Msg"];   ? Read & marked for deletion
           // msg = "Saved"
           
Request 3: var msg = TempData["Msg"];   ? null (already deleted)
42 Q42. What is TempData.Keep() vs TempData.Peek()? ▼ 
By default, TempData is deleted after being read. Keep() and Peek() prevent this.

TempData.Keep():
- Retains the value for ANOTHER subsequent request
- Must be called AFTER reading
- Marks the key to NOT be deleted

// Request 1
TempData["Message"] = "Hello";

// Request 2
var msg = TempData["Message"];  // Read it (marked for deletion)
TempData.Keep("Message");       // Cancel deletion, keep for next request

// Request 3
var msg = TempData["Message"];  // Still available! "Hello"

TempData.Peek():
- Reads the value WITHOUT marking it for deletion
- Combines read + keep in one step
- Value remains available for next request

// Request 1
TempData["Message"] = "Hello";

// Request 2
var msg = TempData.Peek("Message");  // Read WITHOUT marking for deletion
// msg = "Hello"

// Request 3
var msg = TempData["Message"];  // Still available! "Hello"

Difference:
- Keep(): Read first, then decide to keep ? TempData["key"] then TempData.Keep("key")
- Peek(): Read and keep in one step ? TempData.Peek("key")

Use case: Display a notification that should persist across multiple page navigations.

44 Q44. Explain the complete MVC request lifecycle/pipeline. ▼ 
Complete ASP.NET Core MVC Request Pipeline:

1. HTTP Request arrives at Kestrel server
2. Middleware Pipeline executes (in order):
   - UseExceptionHandler / UseDeveloperExceptionPage
   - UseHttpsRedirection
   - UseStaticFiles
   - UseRouting          ? Route matching happens here
   - UseCors
   - UseAuthentication
   - UseAuthorization
   - UseEndpoints        ? Route execution happens here
3. Routing matches URL to Controller/Action
4. Controller Factory creates Controller instance (with DI)
5. Filters execute (Authorization ? Resource ? Action filters)
6. Model Binding binds request data to action parameters
7. Model Validation runs (Data Annotations)
8. Action Method executes
9. Action Result is produced (ViewResult, JsonResult, etc.)
10. Result Filters execute
11. Result Execution (View rendering by Razor engine)
12. Response flows back through middleware pipeline (reverse order)
13. HTTP Response sent to client

Detailed Filter Pipeline:
Authorization Filters ? Resource Filters (Before) ? Model Binding ? 
Action Filters (Before) ? ACTION EXECUTES ? Action Filters (After) ? 
Result Filters (Before) ? RESULT EXECUTES ? Result Filters (After) ? 
Resource Filters (After)
45 Q45. What happens when a URL is hit in browser to response rendered? ▼ 
Step-by-step journey of a request (e.g., GET /Product/Details/5):

1. BROWSER: User types URL or clicks link

11. VIEW ENGINE: Razor engine locates Details.cshtml

47 Q47. What is Route Table and when is it created? ▼ 
The Route Table is a collection of all defined routes in the application.
It's used by the routing engine to match incoming URLs to endpoints.

When is it created:
- Created during application startup (when app.MapControllerRoute is called)
- Built once and cached for the lifetime of the application
- In ASP.NET Core, it's part of the Endpoint Routing system

In ASP.NET Core (Endpoint Routing):
// Program.cs - Routes are registered at startup
var app = builder.Build();

app.UseRouting();  // Adds route matching to middleware pipeline

app.MapControllerRoute(        // Adds routes to endpoint table
    name: "areas",
    pattern: "{area:exists}/{controller=Home}/{action=Index}/{id?}");

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

app.MapRazorPages();           // Adds Razor Pages routes

How it works:
1. At startup: All routes are collected into an endpoint data source
2. UseRouting(): Middleware that MATCHES the URL to an endpoint

- Minimal API routes

49 Q49. What is Action Invoker? ▼ 
Action Invoker is responsible for invoking (executing) the action method 
on the controller, including running filters and model binding.

In ASP.NET Core, this is handled by the ControllerActionInvoker.

Responsibilities:
1. Execute Authorization Filters
2. Execute Resource Filters
3. Perform Model Binding (bind request data to parameters)
4. Execute Model Validation
5. Execute Action Filters (OnActionExecuting)
6. Invoke the Action Method
7. Execute Action Filters (OnActionExecuted)
8. Execute Result Filters (OnResultExecuting)
9. Execute the Action Result (render view, serialize JSON)
10. Execute Result Filters (OnResultExecuted)

Request ? Controller Created ? Action Invoker takes over:
  ? Filters ? Model Binding ? Validation ? Action ? Result ? Response

The Action Invoker handles:
- Synchronous actions: IActionResult Method()
- Asynchronous actions: Task<IActionResult> MethodAsync()
- Actions with parameters: Method(int id, string name)
- Actions with complex models: Method(CreateViewModel model)
50 Q50. What is Model Binding — how does it work step by step? ▼ 
Model Binding is the process of mapping HTTP request data to action method 
parameters automatically.

Step-by-step process:
1. Action method is identified (e.g., Create(ProductViewModel model))
2. Model Binder looks at parameter type (ProductViewModel)
3. Creates an instance of the parameter type
4. For each property, searches for matching values in these sources (in order):
   a. Form data (POST body)
   b. Route values (/Product/Edit/5 ? id=5)
   c. Query string (?page=2&search=phone)
   d. Headers (if [FromHeader] specified)
   e. Body (if [FromBody] specified for JSON/XML)
5. Converts string values to appropriate types (string "5" ? int 5)
6. Validates using Data Annotations
7. Populates ModelState with any errors

Example:
// URL: /Product/Edit/5?category=electronics
// Form POST body: Name=iPhone&Price=999

[HttpPost]
public IActionResult Edit(int id, ProductViewModel model)
{
    // id = 5 (from route)
    // model.Name = "iPhone" (from form)
    // model.Price = 999 (from form)
    // model.Category = "electronics" (from query string)
}

Complex Model Binding:
public class OrderViewModel
{
    public string CustomerName { get; set; }
    public List<OrderItem> Items { get; set; }  // Collection binding
    public Address ShippingAddress { get; set; }  // Nested object
}

// Form fields for collection:
// Items[0].ProductId = 1
// Items[0].Quantity = 2
// Items[1].ProductId = 3
// Items[1].Quantity = 1
51 Q51. What are Value Providers in Model Binding? ▼ 
Value Providers are components that supply data to the Model Binder from 
different sources of the HTTP request.

Built-in Value Providers (in priority order):
1. FormValueProvider      ? Form POST data
2. RouteValueProvider     ? Route parameters (/controller/action/{id})
3. QueryStringValueProvider ? Query string (?key=value)
4. JQueryFormValueProvider ? jQuery-style form data

How they work:
- Each Value Provider reads from a specific source
- Model Binder queries them in ORDER until a value is found
- First match wins

Example:
// URL: /Product/Edit/5?Name=Phone
// Form body: Name=Laptop

public IActionResult Edit(int id, string Name)
{
    // id = 5 (from RouteValueProvider)
    // Name = "Laptop" (from FormValueProvider - higher priority than QueryString)
}

Override with attributes:
public IActionResult Search(
    [FromQuery] string keyword,      // Only from query string
    [FromRoute] int id,              // Only from route
    [FromForm] string name,          // Only from form body
    [FromHeader] string authorization, // Only from headers
    [FromBody] ProductDto product)   // Only from request body (JSON/XML)

Custom Value Provider:
public class CookieValueProvider : IValueProvider
{
    public bool ContainsPrefix(string prefix) { ... }
    public ValueProviderResult GetValue(string key) { ... }
}

1. Form values (POST body - form data)

3. Query string (?param=value)

53 Q53. What are Action Methods? ▼ 
Action Methods are public methods in a Controller that handle HTTP requests 
and return a response. Each action method corresponds to a URL endpoint.

Rules for Action Methods:
- Must be PUBLIC (private/protected methods are not actions)
- Must return IActionResult or a specific type
- Cannot be static
- Cannot be overloaded (without different HTTP method attributes)
- Can be synchronous or asynchronous

Example:
public class ProductController : Controller
{
    // Simple action - no parameters
    public IActionResult Index()
    {
        return View();
    }
    
    // Action with parameter
    public IActionResult Details(int id)
    {
        var product = _service.GetById(id);
        return View(product);
    }
    
    // Async action
    public async Task<IActionResult> List(string category)
    {
        var products = await _service.GetByCategoryAsync(category);
        return View(products);
    }
    
    // Action with multiple parameters
    public IActionResult Search(string keyword, int page = 1, int pageSize = 10)
    {
        var results = _service.Search(keyword, page, pageSize);
        return View(results);
    }
}

Non-Action methods (excluded from routing):
[NonAction]

54 Q54. What is the difference between [HttpGet] vs [HttpPost]? ▼ 
[HttpGet]:
- Handles HTTP GET requests
- Used for READING/RETRIEVING data
- Data passed via URL (query string, route)
- Idempotent (same request = same result)
- Can be bookmarked
- Cached by browser
- Limited data size (URL length limit ~2048 chars)

[HttpPost]:
- Handles HTTP POST requests
- Used for CREATING/SUBMITTING data
- Data passed in request body
- NOT idempotent (may create new resource each time)
- Cannot be bookmarked
- Not cached
- No data size limit

Example - Typical CRUD pattern:
public class EmployeeController : Controller
{
    // GET: /Employee/Create (show empty form)
    [HttpGet]
    public IActionResult Create()
    {
        return View();
    }
    
    // POST: /Employee/Create (process form submission)
    [HttpPost]
    [ValidateAntiForgeryToken]
    public IActionResult Create(EmployeeViewModel model)
    {
        if (!ModelState.IsValid)
            return View(model);
        
        _service.Add(model);
        TempData["Success"] = "Employee created!";
        return RedirectToAction(nameof(Index));
    }
    
    // GET: /Employee/Edit/5 (show form with data)
    [HttpGet]
    public IActionResult Edit(int id)
    {
        var employee = _service.GetById(id);
        return View(employee);
    }
    
    // POST: /Employee/Edit/5 (process edit)
    [HttpPost]
    [ValidateAntiForgeryToken]
    public IActionResult Edit(int id, EmployeeViewModel model)
    {
        if (!ModelState.IsValid)
            return View(model);
        
        _service.Update(id, model);
        return RedirectToAction(nameof(Index));
    }
}

PRG Pattern (Post-Redirect-Get):
- POST processes data ? Redirect (302) ? GET shows result
- Prevents duplicate form submission on browser refresh
55 Q55. What is [HttpPut], [HttpDelete], [HttpPatch]? ▼ 
These are HTTP method attributes used primarily in Web APIs (RESTful services):

[HttpPut] - UPDATE (full replacement):
- Replaces the ENTIRE resource
- Client sends complete updated object
- Idempotent (same request = same result)

[HttpPatch] - UPDATE (partial):
- Updates ONLY specified fields
- Client sends only changed properties
- Used with JsonPatchDocument

[HttpDelete] - DELETE:
- Removes a resource
- Idempotent

Example - RESTful API Controller:
[Route("api/[controller]")]
[ApiController]
public class ProductsController : ControllerBase
{
    // GET api/products
    [HttpGet]
    public async Task<ActionResult<IEnumerable<Product>>> GetAll()
    {
        return Ok(await _service.GetAllAsync());
    }
    
    // GET api/products/5
    [HttpGet("{id}")]
    public async Task<ActionResult<Product>> GetById(int id)
    {
        var product = await _service.GetByIdAsync(id);
        if (product == null) return NotFound();
        return Ok(product);
    }
    
    // POST api/products
    [HttpPost]
    public async Task<ActionResult<Product>> Create(CreateProductDto dto)
    {
        var product = await _service.CreateAsync(dto);
        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
    }
    
    // PUT api/products/5 (full update)
    [HttpPut("{id}")]
    public async Task<IActionResult> Update(int id, UpdateProductDto dto)
    {
        await _service.UpdateAsync(id, dto);
        return NoContent();
    }
    
    // PATCH api/products/5 (partial update)
    [HttpPatch("{id}")]
    public async Task<IActionResult> Patch(int id, 
        [FromBody] JsonPatchDocument<Product> patchDoc)
    {
        var product = await _service.GetByIdAsync(id);
        patchDoc.ApplyTo(product);
        await _service.SaveAsync();
        return Ok(product);
    }
    
    // DELETE api/products/5
    [HttpDelete("{id}")]
    public async Task<IActionResult> Delete(int id)
    {
        await _service.DeleteAsync(id);
        return NoContent();
    }
}

PUT vs PATCH:
PUT: Send ENTIRE object ? { "id":5, "name":"Phone", "price":999, "category":"Electronics" }
PATCH: Send ONLY changes ? { "price": 899 }

57 Q57. What is [NonAction] attribute? ▼ 
[NonAction] attribute marks a public method in a Controller so that it is 
NOT treated as an action method (not accessible via URL).

Why needed:
- By default, ALL public methods in a Controller are treated as actions
- Sometimes you need public helper methods that shouldn't be endpoints

Example:
public class ProductController : Controller
{
    public IActionResult Index()
    {
        var products = GetFilteredProducts("active");
        return View(products);
    }
    
    [NonAction]  // This cannot be accessed via URL
    public List<Product> GetFilteredProducts(string status)
    {
        // Helper method used internally
        return _context.Products.Where(p => p.Status == status).ToList();
    }
    
    [NonAction]
    public string FormatPrice(decimal price)
    {
        return price.ToString("C");
    }
}

Without [NonAction]:
- /Product/GetFilteredProducts would be a valid URL (security risk!)
- /Product/FormatPrice would be accessible

Better alternatives:
- Make the method private or protected (then [NonAction] not needed)
- Move helper methods to a separate service class
- Use [NonAction] only when method MUST be public (e.g., for testing)

60 Q60. What is async Action Method and why to use it? ▼ 
Async action methods use async/await pattern to perform non-blocking I/O 
operations, improving server scalability.

Synchronous (blocks thread):
public IActionResult GetProducts()
{
    var products = _context.Products.ToList();  // Thread BLOCKED waiting for DB
    return View(products);
}

Asynchronous (non-blocking):
public async Task<IActionResult> GetProducts()
{
    var products = await _context.Products.ToListAsync();  // Thread RELEASED
    return View(products);
}

Why use async:
1. SCALABILITY: Thread is released back to thread pool during I/O wait
2. THROUGHPUT: Server can handle more concurrent requests
3. RESPONSIVENESS: Other requests can use the freed thread

When to use async:
- Database calls (EF Core: ToListAsync, FindAsync, SaveChangesAsync)
- HTTP calls (HttpClient.GetAsync)
- File I/O (File.ReadAllTextAsync)
- Any I/O-bound operation

When NOT to use async:
- CPU-bound operations (calculations, in-memory processing)
- Simple operations with no I/O
- When it adds complexity without benefit

Example - Multiple async operations:
public async Task<IActionResult> Dashboard()
{
    // Run in parallel (independent operations)
    var productsTask = _productService.GetAllAsync();
    var ordersTask = _orderService.GetRecentAsync();
    var statsTask = _statsService.GetDashboardStatsAsync();
    
    await Task.WhenAll(productsTask, ordersTask, statsTask);
    
    var viewModel = new DashboardViewModel
    {
        Products = await productsTask,
        RecentOrders = await ordersTask,
        Stats = await statsTask
    };
    
    return View(viewModel);
}

Best Practices:
- Always use async for I/O operations
- Don't use .Result or .Wait() (causes deadlocks)
- Use async all the way (don't mix sync and async)
- Suffix async methods with "Async" in services (not in actions)
- Use CancellationToken for long-running operations:

public async Task<IActionResult> Report(CancellationToken cancellationToken)
{
    var data = await _service.GenerateReportAsync(cancellationToken);
    return View(data);
}

61 Q61. What is Model Binding in MVC? ▼ 
Model Binding is the automatic process of extracting data from HTTP requests 
(form data, route values, query strings, headers, body) and mapping it to 
action method parameters or model properties.

Without Model Binding (manual extraction):
public IActionResult Create()
{
    string name = Request.Form["Name"];
    int age = int.Parse(Request.Form["Age"]);
    string email = Request.Query["email"];

}

With Model Binding (automatic):
public IActionResult Create(string name, int age, string email)
{
    // Automatically mapped! Clean and type-safe
}

// Or with complex model:
public IActionResult Create(EmployeeViewModel model)
{
    // All properties automatically populated from request
}

Model Binding supports:
- Simple types: int, string, bool, DateTime, decimal, etc.
- Complex types: Custom classes with properties
- Collections: List<T>, arrays, Dictionary<K,V>
- Nested objects: Address.City, Address.ZipCode

How form fields map to model:
<form>
    <input name="Name" value="John" />
    <input name="Age" value="30" />
    <input name="Address.City" value="New York" />
    <input name="Skills[0]" value="C#" />
    <input name="Skills[1]" value="SQL" />
</form>

public class EmployeeViewModel
{

62 Q62. What are [FromBody], [FromQuery], [FromRoute], [FromForm], [FromHeader]? ▼ 
These attributes explicitly specify WHERE the model binder should look for data.

[FromRoute] - From URL route segments:
// URL: /api/products/5
[HttpGet("{id}")]
public IActionResult Get([FromRoute] int id) { }  // id = 5

[FromQuery] - From query string:
// URL: /api/products?page=2&size=10
[HttpGet]
public IActionResult Get([FromQuery] int page, [FromQuery] int size) { }

[FromForm] - From form POST data:
[HttpPost]
public IActionResult Create([FromForm] ProductViewModel model) { }

[FromBody] - From request body (JSON/XML):
// Body: {"name":"Phone","price":999}
[HttpPost]
public IActionResult Create([FromBody] ProductDto dto) { }

[FromHeader] - From HTTP headers:
public IActionResult Get([FromHeader(Name = "X-Request-Id")] string requestId) { }

[FromServices] - From DI container:
public IActionResult Get([FromServices] IProductService service) { }

Important Rules:
- [FromBody] can only be used ONCE per action (one body)
- [ApiController] automatically infers [FromBody] for complex types
- [FromForm] and [FromBody] cannot be used together
- For MVC views (forms), [FromForm] is default for complex types

Example combining multiple sources:
[HttpPut("{id}")]
public IActionResult Update(
    [FromRoute] int id,
    [FromBody] UpdateProductDto dto,
    [FromHeader(Name = "If-Match")] string etag,
    [FromQuery] bool notify = false)
{
    // id from URL, dto from JSON body, etag from header, notify from query
}
63 Q63. What is [Bind] attribute and how to use it? ▼ 
[Bind] attribute restricts which properties of a model should be included 
in model binding. It's used to prevent Over-Posting attacks.

Include specific properties only:
[HttpPost]
public IActionResult Create([Bind("Name,Email,DepartmentId")] Employee employee)
{
    // Only Name, Email, DepartmentId will be bound
    // Even if attacker sends IsAdmin=true, it won't be bound
}

On Model class:
[Bind("Name,Email,Phone")]
public class EmployeeViewModel
{
    public string Name { get; set; }
    public string Email { get; set; }
    public string Phone { get; set; }
    public bool IsAdmin { get; set; }  // Won't be bound
}

Exclude specific properties:
// In older MVC (not recommended in Core):
[Bind(Exclude = "Id,IsAdmin")]

Better alternatives in ASP.NET Core:
1. Use ViewModels (recommended):
public class CreateEmployeeViewModel  // Only has safe properties
{
    public string Name { get; set; }
    public string Email { get; set; }
    // No IsAdmin property here!
}

2. Use [BindNever] on specific properties:
public class Employee
{
    public int Id { get; set; }
    
    [BindNever]
    public bool IsAdmin { get; set; }  // Never bound from request
    
    [BindNever]
    public DateTime CreatedDate { get; set; }
}

Best Practice: Use ViewModels instead of [Bind] — cleaner and more maintainable.
64 Q64. What is Over-Posting/Mass Assignment attack and how to prevent? ▼ 
Over-Posting (Mass Assignment) is a security vulnerability where an attacker 
sends extra form fields that map to sensitive model properties.

Example of the attack:
// Domain Model
public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
    public bool IsAdmin { get; set; }  // Sensitive!
    public decimal Salary { get; set; }  // Sensitive!
}

// Vulnerable Controller
[HttpPost]
public IActionResult Create(Employee employee)  // Binds ALL properties!
{
    _context.Employees.Add(employee);
    _context.SaveChanges();
    return RedirectToAction("Index");
}

// Attacker's form (adds hidden field):
<input type="hidden" name="IsAdmin" value="true" />
<input type="hidden" name="Salary" value="999999" />
// Now attacker is admin with huge salary!

Prevention Methods:

1. USE VIEWMODELS (Best approach):
public class CreateEmployeeViewModel
{
    [Required]
    public string Name { get; set; }
    [EmailAddress]
    public string Email { get; set; }
    // No IsAdmin, No Salary — can't be over-posted!
}

[HttpPost]
public IActionResult Create(CreateEmployeeViewModel model)
{
    var employee = new Employee
    {
        Name = model.Name,
        Email = model.Email,
        IsAdmin = false,  // Set explicitly
        Salary = 0
    };
    _context.Employees.Add(employee);
    _context.SaveChanges();
    return RedirectToAction("Index");
}

2. [Bind] attribute:
public IActionResult Create([Bind("Name,Email")] Employee employee) { }

3. [BindNever] attribute:
public class Employee
{
    [BindNever] public bool IsAdmin { get; set; }
    [BindNever] public decimal Salary { get; set; }
}

4. TryUpdateModelAsync with include list:
await TryUpdateModelAsync(employee, "", e => e.Name, e => e.Email);
65 Q65. What is ModelState and ModelState.IsValid? ▼ 
ModelState is a dictionary that contains the state of model binding and

ModelState.IsValid:
- Returns TRUE if all validations pass (no errors)
- Returns FALSE if any validation fails

68 Q68. What is IValidatableObject interface? ▼ 
IValidatableObject allows you to implement complex validation logic that 
involves multiple properties of the same model (cross-property validation).

It's called AFTER all Data Annotation validations pass.

Example:
public class EventViewModel : IValidatableObject
{
    [Required]
    public string Title { get; set; }
    
    [Required]
    public DateTime StartDate { get; set; }
    
    [Required]
    public DateTime EndDate { get; set; }
    
    public int MinAttendees { get; set; }
    public int MaxAttendees { get; set; }
    
    public IEnumerable<ValidationResult> Validate(ValidationContext validationContext)
    {
        // Cross-property validation
        if (EndDate <= StartDate)
        {
            yield return new ValidationResult(
                "End date must be after start date",
                new[] { nameof(EndDate) });
        }
        
        if (StartDate < DateTime.Now)
        {
            yield return new ValidationResult(
                "Start date cannot be in the past",
                new[] { nameof(StartDate) });
        }
        
        if (MaxAttendees < MinAttendees)
        {
            yield return new ValidationResult(
                "Max attendees must be >= Min attendees",
                new[] { nameof(MaxAttendees) });
        }
        
        // Can even access services via DI
        var dbContext = (AppDbContext)validationContext
            .GetService(typeof(AppDbContext));
        
        if (dbContext.Events.Any(e => e.Title == Title))
        {
            yield return new ValidationResult(
                "Event with this title already exists",
                new[] { nameof(Title) });
        }
    }
}

When to use:
- Validation depends on multiple properties together
- Complex business rules
- Need access to services/database during validation
- Rules that can't be expressed with simple attributes

IValidatableObject vs Custom Attribute:
- IValidatableObject: Model-specific, multiple properties, access to DI
- Custom Attribute: Reusable across models, single property focus
69 Q69. What is Client-Side Validation vs Server-Side Validation? ▼ 
SERVER-SIDE VALIDATION:
- Runs on the SERVER after form submission
- Uses ModelState.IsValid
- ALWAYS required (never trust client)
- Catches all validation (even if JS disabled)
- Requires round-trip to server

Example:

}

CLIENT-SIDE VALIDATION:
- Runs in BROWSER using JavaScript (before form submission)
- Provides instant feedback (no server round-trip)
- Better user experience
- Can be bypassed (never rely on it alone)
- Uses jQuery Validation + jQuery Unobtrusive Validation

72 Q72. What are Filters and why are they used? ▼ 
Filters are attributes/classes that run code BEFORE or AFTER specific stages 
in the MVC request pipeline. They allow you to add cross-cutting concerns 
without modifying action methods.

Why use Filters:
- Avoid code duplication (DRY principle)
- Cross-cutting concerns (logging, authorization, caching, error handling)
- Separate infrastructure code from business logic
- Can be applied globally, per-controller, or per-action

Common use cases:
- Authorization checks
- Logging/auditing
- Exception handling
- Caching
- Input validation
- Response modification
- Performance measurement

Example:
// Without filter (repeated code in every action)
public IActionResult Index()
{
    _logger.LogInformation("Index called at " + DateTime.Now);
    // ... action logic
    _logger.LogInformation("Index completed at " + DateTime.Now);
}

// With filter (clean, reusable)
[LogAction]
public IActionResult Index()
{
    // ... only action logic, logging handled by filter
}
73 Q73. What are the 5 types of Filters? ▼ 
1. AUTHORIZATION FILTERS:
   - Run FIRST in the pipeline
   - Determine if user is authorized
   - Can short-circuit (stop pipeline)
   - Interface: IAuthorizationFilter
   - Example: [Authorize], custom auth checks

2. RESOURCE FILTERS:
   - Run AFTER authorization, BEFORE model binding
   - Can short-circuit
   - Good for caching (skip entire pipeline)
   - Interface: IResourceFilter / IAsyncResourceFilter
   - Example: Response caching

3. ACTION FILTERS:
   - Run BEFORE and AFTER action method execution
   - Can modify action arguments or result
   - Interface: IActionFilter / IAsyncActionFilter
   - Example: Logging, validation, auditing

4. EXCEPTION FILTERS:
   - Handle unhandled exceptions from action/filters
   - Run when exception occurs in action or action filters
   - Interface: IExceptionFilter / IAsyncExceptionFilter
   - Example: Global error handling, error logging

5. RESULT FILTERS:
   - Run BEFORE and AFTER action result execution (view rendering)
   - Can modify the result
   - Interface: IResultFilter / IAsyncResultFilter
   - Example: Modify response headers, wrap response

Execution Order:
Authorization ? Resource (Before) ? Model Binding ? 
Action (Before) ? ACTION ? Action (After) ? 
Exception (if error) ? Result (Before) ? RESULT ? Result (After) ? 
Resource (After)
74 Q74. What is Authorization Filter? ▼ 
Authorization Filters run FIRST and determine whether the user is authorized 
to access the resource. They can short-circuit the pipeline.

Built-in: [Authorize] attribute

Interface: IAuthorizationFilter
public interface IAuthorizationFilter : IFilterMetadata
{
    void OnAuthorization(AuthorizationFilterContext context);
}

Example - Custom Authorization Filter:
public class CustomAuthFilter : IAuthorizationFilter
{
    public void OnAuthorization(AuthorizationFilterContext context)
    {
        var user = context.HttpContext.User;
        
        if (!user.Identity.IsAuthenticated)
        {
            context.Result = new UnauthorizedResult();  // Short-circuit
            return;
        }
        
        // Check custom condition
        var hasPermission = user.HasClaim("Permission", "Admin");
        if (!hasPermission)
        {
            context.Result = new ForbidResult();  // 403
        }
    }
}

// Usage
[ServiceFilter(typeof(CustomAuthFilter))]
public IActionResult AdminPanel() { }

Built-in Authorization:
[Authorize]                              // Must be authenticated
[Authorize(Roles = "Admin,Manager")]     // Must have role
[Authorize(Policy = "MinAge18")]         // Must satisfy policy
[AllowAnonymous]                         // Skip authorization

Note: In ASP.NET Core, prefer Policy-based authorization over custom 
authorization filters for most scenarios.
75 Q75. What is Resource Filter? ▼ 
Resource Filters run AFTER authorization but BEFORE everything else 
(model binding, action filters, action). They also run AFTER the result.

Use cases:
- Short-circuit pipeline (return cached response)
- Modify model binding behavior
- Wrap the entire action execution

Interface:
public interface IResourceFilter : IFilterMetadata
{
    void OnResourceExecuting(ResourceExecutingContext context);
    void OnResourceExecuted(ResourceExecutedContext context);
}

Example - Caching Resource Filter:
public class CacheResourceFilter : IResourceFilter
{
    private readonly IMemoryCache _cache;
    
    public CacheResourceFilter(IMemoryCache cache)
    {
        _cache = cache;
    }
    
    public void OnResourceExecuting(ResourceExecutingContext context)
    {
        var cacheKey = context.HttpContext.Request.Path;
        
        if (_cache.TryGetValue(cacheKey, out string cachedResult))
        {
            // Short-circuit: return cached response, skip action entirely
            context.Result = new ContentResult
            {
                Content = cachedResult,
                ContentType = "text/html"
            };
        }
    }
    
    public void OnResourceExecuted(ResourceExecutedContext context)
    {
        // Cache the response after action executes
        var cacheKey = context.HttpContext.Request.Path;
        if (context.Result is ViewResult viewResult)
        {
            // Store result in cache
            _cache.Set(cacheKey, viewResult, TimeSpan.FromMinutes(5));
        }
    }
}
76 Q76. What is Action Filter (OnActionExecuting, OnActionExecuted)? ▼ 
Action Filters run immediately BEFORE and AFTER the action method executes.
Most commonly used filter type.

Interface:
public interface IActionFilter : IFilterMetadata
{
    void OnActionExecuting(ActionExecutingContext context);   // Before action
    void OnActionExecuted(ActionExecutedContext context);     // After action
}

Example - Logging Action Filter:
public class LogActionFilter : IActionFilter
{
    private readonly ILogger<LogActionFilter> _logger;
    
    public LogActionFilter(ILogger<LogActionFilter> logger)
    {
        _logger = logger;
    }
    
    public void OnActionExecuting(ActionExecutingContext context)
    {
        var actionName = context.ActionDescriptor.DisplayName;
        var parameters = context.ActionArguments;
        _logger.LogInformation($"Executing: {actionName} with params: {JsonSerializer.Serialize(parameters)}");
    }
    
    public void OnActionExecuted(ActionExecutedContext context)
    {
        var actionName = context.ActionDescriptor.DisplayName;
        
        if (context.Exception != null)
            _logger.LogError($"Action {actionName} threw: {context.Exception.Message}");
        else
            _logger.LogInformation($"Executed: {actionName} successfully");
    }
}

Example - Validation Action Filter:
public class ValidateModelFilter : IActionFilter
{
    public void OnActionExecuting(ActionExecutingContext context)
    {
        if (!context.ModelState.IsValid)
        {
            context.Result = new BadRequestObjectResult(context.ModelState);
            // Short-circuits - action won't execute
        }
    }
    
    public void OnActionExecuted(ActionExecutedContext context) { }
}

Using as Attribute:
public class TimingActionFilter : ActionFilterAttribute
{

    public override void OnActionExecuting(ActionExecutingContext context)
    {
        _stopwatch = Stopwatch.StartNew();
    }
    
    public override void OnActionExecuted(ActionExecutedContext context)

78 Q78. What is Exception Filter? ▼ 
Exception Filters handle unhandled exceptions that occur during action 
execution or within action/result filters.

Interface:
public interface IExceptionFilter : IFilterMetadata
{
    void OnException(ExceptionContext context);
}

Example - Global Exception Filter:
public class GlobalExceptionFilter : IExceptionFilter
{
    private readonly ILogger<GlobalExceptionFilter> _logger;
    private readonly IWebHostEnvironment _env;
    
    public GlobalExceptionFilter(ILogger<GlobalExceptionFilter> logger, 
        IWebHostEnvironment env)
    {
        _logger = logger;
        _env = env;
    }
    
    public void OnException(ExceptionContext context)
    {
        _logger.LogError(context.Exception, 
            "Unhandled exception in {Action}", 
            context.ActionDescriptor.DisplayName);
        
        if (_env.IsDevelopment())
        {
            // Show detailed error in development
            context.Result = new ObjectResult(new
            {
                Error = context.Exception.Message,
                StackTrace = context.Exception.StackTrace
            })
            { StatusCode = 500 };
        }
        else
        {
            // Show generic error in production
            context.Result = new ViewResult
            {
                ViewName = "Error",
                StatusCode = 500
            };
        }
        
        context.ExceptionHandled = true;  // Mark as handled
    }
}

Register globally in Program.cs:
builder.Services.AddControllersWithViews(options =>
{
    options.Filters.Add<GlobalExceptionFilter>();
});

Important:
- context.ExceptionHandled = true ? Exception is handled, pipeline continues
- If not set to true, exception propagates to middleware
- Exception filters DON'T catch exceptions in:
  - Middleware
  - Razor view rendering
  - Result filters
79 Q79. What is the execution order of Filters? ▼ 
Filters execute in a specific order, and within each type, they follow 
Global ? Controller ? Action order.

EXECUTION ORDER (top to bottom):
1. Authorization Filters
2. Resource Filters - OnResourceExecuting
3. Model Binding
4. Action Filters - OnActionExecuting
5. *** ACTION METHOD EXECUTES ***
6. Action Filters - OnActionExecuted
7. Exception Filters (only if exception occurred)
8. Result Filters - OnResultExecuting
9. *** RESULT EXECUTES (View rendering) ***
10. Result Filters - OnResultExecuted
11. Resource Filters - OnResourceExecuted

SCOPE ORDER (for same filter type):
Executing (Before): Global ? Controller ? Action
Executed (After):   Action ? Controller ? Global

Example:
// Global filter registered in Program.cs
options.Filters.Add<GlobalActionFilter>();

// Controller-level filter
[ControllerActionFilter]
public class ProductController : Controller
{
    // Action-level filter
    [ActionLevelFilter]
    public IActionResult Index() { }
}

Execution:
OnActionExecuting:  Global ? Controller ? Action
ACTION EXECUTES
OnActionExecuted:   Action ? Controller ? Global

Override order with Order property:
[MyFilter(Order = 1)]   // Lower number = runs first
[MyFilter(Order = 2)]

});

2. CONTROLLER-LEVEL (applies to all actions in that controller):
[ServiceFilter(typeof(AuditActionFilter))]
[Authorize(Roles = "Admin")]
public class AdminController : Controller
{
    public IActionResult Index() { }      // Filter applies
    public IActionResult Settings() { }   // Filter applies
}

3. ACTION-LEVEL (applies to specific action only):
public class ProductController : Controller
{
    public IActionResult Index() { }  // No filter
    
    [ServiceFilter(typeof(AuditActionFilter))]  // Only this action
    [Authorize(Roles = "Manager")]
    public IActionResult Delete(int id) { }
}

Execution order:
Global ? Controller ? Action (for "Executing/Before")
Action ? Controller ? Global (for "Executed/After")

When to use which:
- Global: Exception handling, logging, HTTPS enforcement
- Controller: Authorization for admin area, audit for sensitive controllers
- Action: Specific validation, rate limiting on specific endpoints
82 Q82. What is ServiceFilter vs TypeFilter? ▼ 
Both are used to apply filters that require Dependency Injection.

ServiceFilter:
- Resolves filter from DI container
- Filter MUST be registered in DI (AddScoped/AddTransient/AddSingleton)
- Cannot pass constructor parameters

// Register in DI
builder.Services.AddScoped<AuditActionFilter>();

// Usage
[ServiceFilter(typeof(AuditActionFilter))]
public IActionResult Index() { }

TypeFilter:
- Creates filter instance using DI + allows passing constructor parameters
- Does NOT need to be registered in DI
- Can pass additional arguments

// Filter with constructor parameters
public class RoleCheckFilter : IActionFilter
{
    private readonly string _role;
    private readonly IUserService _userService;  // From DI
    
    public RoleCheckFilter(string role, IUserService userService)
    {
        _role = role;           // From TypeFilter arguments
        _userService = userService;  // From DI container
    }
    
    public void OnActionExecuting(ActionExecutingContext context) { }
    public void OnActionExecuted(ActionExecutedContext context) { }
}

// Usage - pass "Admin" as constructor argument
[TypeFilter(typeof(RoleCheckFilter), Arguments = new object[] { "Admin" })]
public IActionResult AdminAction() { }

Comparison:
| Feature          | ServiceFilter              | TypeFilter                  |
|------------------|----------------------------|-----------------------------|
| DI Registration  | Required                   | Not required                |
| Parameters       | Cannot pass                | Can pass via Arguments      |
| Lifetime         | Controlled by DI           | Created per request         |
| Performance      | Slightly better (cached)   | New instance each time      |

Best Practice:
- Use ServiceFilter when filter has no extra parameters
- Use TypeFilter when you need to pass arguments to the filter

87 Q87. What are different State Management techniques in MVC? ▼ 
HTTP is stateless — each request is independent. State management techniques 
help maintain data across requests.

CLIENT-SIDE (stored on user's browser):
1. Cookies - Small data stored in browser
2. Query String - Data in URL (?key=value)
3. Hidden Fields - Hidden form inputs
4. ViewData/ViewBag - Single request only (server-side but per-request)

SERVER-SIDE (stored on server):
5. Session - Per-user data on server
6. TempData - Data for next request (redirect)
7. Cache (IMemoryCache) - Shared across all users
8. Database - Persistent storage
9. Distributed Cache (Redis) - Shared across servers

Comparison:
| Technique    | Scope          | Lifetime        | Size Limit    |
|--------------|----------------|-----------------|---------------|
| Cookie       | Per user       | Configurable    | ~4KB          |
| Query String | Per request    | URL lifetime    | ~2048 chars   |
| Hidden Field | Per form       | Form submission | No limit      |
| ViewData     | Per request    | Current request | No limit      |
| TempData     | Per user       | Next request    | Limited       |
| Session      | Per user       | Session timeout | Configurable  |
| Cache        | All users      | Configurable    | Server memory |
| Database     | Persistent     | Permanent       | Unlimited     |
88 Q88. What is Session in ASP.NET Core MVC? ▼ 
Session stores user-specific data on the server, identified by a session ID 
cookie sent to the browser.

Key characteristics:
- Per-user storage (each user has their own session)
- Stored on server (in-memory by default)
- Identified by session cookie (.AspNetCore.Session)
- Default timeout: 20 minutes of inactivity
- Not shared across servers (unless distributed)

Basic usage:
// Store data
HttpContext.Session.SetString("Username", "John");
HttpContext.Session.SetInt32("CartCount", 5);

// Retrieve data
string username = HttpContext.Session.GetString("Username");
int? cartCount = HttpContext.Session.GetInt32("CartCount");

// Remove
HttpContext.Session.Remove("Username");

// Clear all
HttpContext.Session.Clear();

// Store complex objects (serialize to JSON)
public static class SessionExtensions
{
    public static void SetObject<T>(this ISession session, string key, T value)
    {
        session.SetString(key, JsonSerializer.Serialize(value));
    }
    
    public static T GetObject<T>(this ISession session, string key)
    {
        var value = session.GetString(key);
        return value == null ? default : JsonSerializer.Deserialize<T>(value);
    }
}

// Usage
HttpContext.Session.SetObject("Cart", cartItems);
var cart = HttpContext.Session.GetObject<List<CartItem>>("Cart");

90 Q90. What is the difference between Session vs TempData vs Cache? ▼ 
| Feature      | Session              | TempData             | Cache (IMemoryCache) |
|--------------|----------------------|----------------------|----------------------|
| Scope        | Per user             | Per user             | All users (shared)   |
| Lifetime     | Until timeout        | Next request only    | Configurable expiry  |
| Storage      | Server (memory/Redis)| Cookie/Session       | Server memory        |
| Use case     | User-specific data   | Redirect messages    | Frequently accessed  |
|              | (cart, preferences)  | (success/error msg)  | shared data          |
| Survives     | Multiple requests    | ONE redirect         | Until expiration     |
| redirect?    | Yes                  | Yes (once)           | N/A                  |

SESSION - User-specific, multiple requests:
// Shopping cart, user preferences, wizard steps
HttpContext.Session.SetString("Theme", "dark");
// Available until session expires (e.g., 30 min inactivity)

TEMPDATA - User-specific, next request only:
// Success/error messages after redirect (PRG pattern)
TempData["Message"] = "Product saved successfully!";
return RedirectToAction("Index");
// Available in Index action, then deleted

CACHE - Shared across ALL users:
// Product catalog, configuration, lookup data
_cache.Set("AllCategories", categories, TimeSpan.FromHours(1));
// Same data served to all users, reduces DB calls

When to use:
- Session: Login state, shopping cart, user preferences
- TempData: Flash messages, one-time notifications after redirect
- Cache: Database query results, API responses, computed data shared by all
91 Q91. What are Cookies and how to use them in MVC? ▼ 
Cookies are small pieces of data stored in the user's browser, sent with 
every subsequent request to the same domain.

Creating/Writing Cookies:
public IActionResult SetPreferences(string theme, string language)
{
    // Simple cookie
    Response.Cookies.Append("Theme", theme);
    
    // Cookie with options
    var cookieOptions = new CookieOptions
    {
        Expires = DateTimeOffset.Now.AddDays(30),  // Expiry
        HttpOnly = true,       // Not accessible via JavaScript
        Secure = true,         // Only sent over HTTPS
        SameSite = SameSiteMode.Strict,  // CSRF protection
        Path = "/",            // Available for entire site
        Domain = ".mysite.com" // Available for subdomains
    };
    
    Response.Cookies.Append("Language", language, cookieOptions);
    
    // Store complex data (serialize)
    var preferences = new { Theme = theme, Language = language };
    Response.Cookies.Append("Prefs", JsonSerializer.Serialize(preferences), cookieOptions);
    
    return RedirectToAction("Index");
}

Reading Cookies:
public IActionResult Index()
{
    string theme = Request.Cookies["Theme"] ?? "light";
    string language = Request.Cookies["Language"] ?? "en";
    
    ViewBag.Theme = theme;
    return View();
}

Deleting Cookies:
public IActionResult ClearPreferences()
{
    Response.Cookies.Delete("Theme");
    Response.Cookies.Delete("Language");
    return RedirectToAction("Index");
}

Cookie Types:
- Session Cookie: No Expires set ? deleted when browser closes
- Persistent Cookie: Has Expires ? stored until expiry date

Limitations:
- ~4KB size limit per cookie
- ~20 cookies per domain
- User can disable/delete cookies
- Sent with EVERY request (affects performance)

Security:
- HttpOnly = true ? prevents XSS (JavaScript can't read)
- Secure = true ? only sent over HTTPS
- SameSite = Strict ? prevents CSRF attacks

93 Q93. What is Hidden Field? ▼ 
Hidden Fields are HTML input elements that are not visible to the user but 
submit data with the form. Used to pass data between requests without 
displaying it.

HTML:
<input type="hidden" name="Id" value="5" />

With Tag Helper:
<input asp-for="Id" type="hidden" />
// OR
@Html.HiddenFor(m => m.Id)

Common use cases:
1. Passing ID during Edit operations:

    <div class="form-group">
        <label asp-for="Name"></label>
        <input asp-for="Name" class="form-control" />
    </div>
    
    <button type="submit">Save</button>
</form>

2. Anti-forgery token (automatically added):
<form asp-action="Create" method="post">
    <!-- asp-action automatically adds: -->
    <!-- <input name="__RequestVerificationToken" type="hidden" value="..." /> -->
</form>

3. Tracking state across form steps:
<input type="hidden" name="Step" value="2" />
<input type="hidden" name="PreviousData" value="@Model.SerializedStep1" />

Security Warning:
- Hidden fields are NOT secure!
- Users can view/modify them using browser DevTools
- NEVER store sensitive data (passwords, tokens) in hidden fields
- Always validate on server side
- Use for non-sensitive data only (IDs, step numbers)

Better alternatives for sensitive data:
- Session (server-side)
- Encrypted cookies
- Database storage with reference ID

94 Q94. What is Bundling and Minification? ▼ 
Bundling: Combining multiple CSS/JS files into a single file to reduce 
HTTP requests.

Minification: Removing unnecessary characters (whitespace, comments, 
short variable names) to reduce file size.

Before bundling (6 HTTP requests):
<link href="~/css/bootstrap.css" />
<link href="~/css/site.css" />
<link href="~/css/custom.css" />
<script src="~/js/jquery.js"></script>
<script src="~/js/bootstrap.js"></script>
<script src="~/js/site.js"></script>

After bundling (2 HTTP requests):
<link href="~/css/bundle.min.css" />
<script src="~/js/bundle.min.js"></script>

Benefits:
- Fewer HTTP requests (faster page load)
- Smaller file sizes (less bandwidth)
- Better performance on slow connections
- Browser caching with version hash

Minification example:
// Before (readable):
function calculateTotal(price, quantity) {
    var total = price * quantity;
    return total;
}

// After minification:
function calculateTotal(n,t){return n*t}

public async Task<IActionResult> Upload(FileUploadViewModel model)
{
    if (!ModelState.IsValid)
        return View(model);
    
    if (model.File != null && model.File.Length > 0)
    {
        // Validate file
        var allowedExtensions = new[] { ".jpg", ".png", ".pdf" };
        var extension = Path.GetExtension(model.File.FileName).ToLower();
        
        if (!allowedExtensions.Contains(extension))
        {
            ModelState.AddModelError("File", "Invalid file type");
            return View(model);
        }
        
        if (model.File.Length > 5 * 1024 * 1024) // 5MB limit
        {
            ModelState.AddModelError("File", "File too large (max 5MB)");
            return View(model);
        }
        
        // Generate unique filename
        var fileName = Guid.NewGuid() + extension;
        var filePath = Path.Combine(_env.WebRootPath, "uploads", fileName);
        
        // Ensure directory exists
        Directory.CreateDirectory(Path.GetDirectoryName(filePath));
        
        // Save file
        using (var stream = new FileStream(filePath, FileMode.Create))
        {
            await model.File.CopyToAsync(stream);
        }
        
        TempData["Success"] = "File uploaded successfully!";
    }
    
    return RedirectToAction("Index");
}

public async Task<IActionResult> Index(string search, int page = 1, int pageSize = 10)
{
    var query = _context.Products.AsQueryable();
    
    // Search
    if (!string.IsNullOrEmpty(search))
    {
        query = query.Where(p => p.Name.Contains(search) || 
                                  p.Description.Contains(search));
    }
    
    // Get total count for pagination
    var totalItems = await query.CountAsync();
    var totalPages = (int)Math.Ceiling(totalItems / (double)pageSize);
    
    // Apply pagination
    var products = await query
        .OrderBy(p => p.Name)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .Select(p => new ProductDto { Id = p.Id, Name = p.Name, Price = p.Price })
        .ToListAsync();
    
    var viewModel = new ProductListViewModel
    {
        Products = products,
        SearchKeyword = search,
        CurrentPage = page,
        TotalPages = totalPages,
        PageSize = pageSize
    };

[HttpPost]
[ValidateAntiForgeryToken]
[RequestSizeLimit(50 * 1024 * 1024)]  // 50MB total limit
public async Task<IActionResult> UploadMultiple(MultiFileUploadViewModel model)
{
    if (model.Files == null || model.Files.Count == 0)
    {
        ModelState.AddModelError("Files", "Please select at least one file");
        return View(model);
    }
    
    var uploadedFiles = new List<string>();
    var allowedExtensions = new[] { ".jpg", ".png", ".pdf" };
    long maxFileSize = 5 * 1024 * 1024; // 5MB per file
    
    foreach (var file in model.Files)
    {
        var extension = Path.GetExtension(file.FileName).ToLower();
        
        if (!allowedExtensions.Contains(extension))
        {
            ModelState.AddModelError("Files", $"Invalid file type: {file.FileName}");
            continue;
        }
        
        if (file.Length > maxFileSize)
        {
            ModelState.AddModelError("Files", $"File too large: {file.FileName}");
            continue;
        }
        
        var fileName = Guid.NewGuid() + extension;
        var filePath = Path.Combine(_env.WebRootPath, "uploads", fileName);
        
        Directory.CreateDirectory(Path.GetDirectoryName(filePath));
        
        using (var stream = new FileStream(filePath, FileMode.Create))
        {
            await file.CopyToAsync(stream);
        }
        
        uploadedFiles.Add(fileName);
    }
    
    if (!ModelState.IsValid)
        return View(model);
    
    TempData["Success"] = $"{uploadedFiles.Count} files uploaded successfully!";
    return RedirectToAction("Index");
}
