Project-Based Questions (Audit Module)

1Explain your project architecture.▼
Our Audit Solution follows a layered architecture with separate projects:

1. AuditSolution.Web (MVC - Presentation Layer)
   - ASP.NET Core MVC with Razor Views
   - Controllers serve views only (thin controllers)
   - Session-based authentication using custom SessionAuthFilter
   - CSP (Content Security Policy) middleware for security headers

2. AuditSolution.PrivateAPI (Web API - Backend)
   - RESTful API consumed by the Web layer via AJAX
   - JWT token-based authentication
   - Handles all business operations
   - Controllers like LoginController, AuditobservationController, etc.

3. AuditSolution.Core (Business + Data Layer)
   - BLL (Business Logic Layer): Business rules, validation
   - DAL (Data Access Layer): Oracle DB queries via OracleHelper
   - DTO (Data Transfer Objects): Request/Response models
   - DataSource: Connection and query management

4. AuditSolution.Helpers (Cross-cutting Concerns)
   - JwtService: Token generation/validation
   - OracleHelper: Generic DB helper (ExecuteDataTable, GetRecords<T>)
   - InputValidator: XSS, SQL Injection, HTML sanitization
   - BruteForceProtection: Account lockout after failed attempts
   - Email service, Encryption utilities
   - Custom Middleware (CSP, Path Traversal protection)

5. Audit_mail_console (Background Service)
   - Console app for sending scheduled audit emails

Flow: Browser → MVC Web → AJAX → Private API → BLL → DAL → Oracle DB

Why this architecture:
- Separation of concerns (each layer has single responsibility)
- API can be reused by mobile/other clients
- Security: Web and API are separate (API not directly exposed)
- Testable: BLL can be tested independently
2How does authentication work in your project?▼
We use a DUAL authentication approach:

1. WEB LAYER (Session-based):
   - Custom SessionAuthFilter (IActionFilter) checks for "_audit_session" cookie
   - If cookie missing → redirect to Login page
   - Login/Error pages are excluded from auth check
   - Cookie is HttpOnly + Secure (prevents XSS theft)

2. API LAYER (JWT-based):
   - Private API uses JWT tokens for authentication
   - JwtService generates token with claims (email, role)
   - Token expires after configurable duration (default 30 min)
   - Secret key stored in environment variable (AUDIT_JWT_SECRET)
   - Token includes: Email, Role, JTI (unique ID), IAT (issued at)

Login Flow:
1. User enters credentials on Login page
2. MVC sends AJAX POST to Private API → /api/Login/LoginEntryFN
3. API validates credentials against Oracle DB
4. If valid → generates JWT token + sets session cookie
5. If invalid → BruteForceProtection records failed attempt
6. After 5 failures → account locked for 15 minutes
7. On success → redirect to role-based dashboard

Security measures:
- Brute force protection (5 attempts → 15 min lockout)
- IP tracking for failed attempts
- JWT secret from environment variable (not in appsettings)
- HttpOnly + Secure cookies
- CAPTCHA service available
- Kestrel server header removed (options.AddServerHeader = false)
3How do you handle security (VAPT fixes) in your project?▼
We implemented multiple security layers after VAPT (Vulnerability Assessment and Penetration Testing):

1. INPUT VALIDATION (InputValidator class):
   - ContainsXss(): Detects script tags, event handlers, javascript: protocol
   - ContainsSqlInjection(): Detects ' OR, UNION SELECT, DROP, xp_ commands
   - ContainsHtml(): Detects HTML tags (encoded variants too)
   - SanitizeHtml(): Whitelist approach for rich-text fields
   - Checks raw + HTML-decoded + URL-decoded + double-decoded variants

2. CSP (Content Security Policy) MIDDLEWARE:
   - Generates unique nonce per request for inline scripts
   - Blocks unauthorized script execution
   - Headers: X-Content-Type-Options, X-Frame-Options, X-XSS-Protection

3. PATH TRAVERSAL MIDDLEWARE:
   - Blocks ../ and encoded path traversal attempts
   - Prevents access to files outside webroot

4. STATIC FILE PROTECTION:
   - Blocks access to .config, .json, .cs, .sql, .log, .bak files
   - Returns 404 for sensitive file extensions

5. HTTP METHOD RESTRICTION:
   - Only GET and POST allowed
   - Other methods (PUT, DELETE, OPTIONS) return 405

6. BRUTE FORCE PROTECTION:
   - 5 failed login attempts → 15 minute lockout
   - IP address tracked
   - Progressive lockout (lockout_count never resets)

7. ANTI-FORGERY TOKENS:
   - Cookie name: "_xsrf"
   - HttpOnly + Secure + SameSite
   - Prevents CSRF attacks

8. ENCRYPTION:
   - Request payload encryption (key from environment variable)
   - Password hashing (ClsCrypto)
   - JWT secret from environment variable

9. OTHER:
   - Kestrel server header removed
   - HTTPS forced
   - MaxRequestLineSize limited (8192)
   - ForwardedHeaders for proxy support
4How does your Data Access Layer work? Why not EF Core?▼
We use a custom OracleHelper class (ADO.NET based) instead of EF Core.

OracleHelper provides:
- ExecuteNonQuery(): INSERT, UPDATE, DELETE operations
- ExecuteScalar<T>(): Single value queries (COUNT, MAX)
- ExecuteReader(): Forward-only data reading
- ExecuteDataTable(): Returns DataTable
- ExecuteDataSet(): Returns DataSet (multiple tables)
- GetRecords<T>(): Generic method — maps DataTable to List<T> using reflection
- GetRecord<T>(): Maps single row to object
- ToDynamic(): Converts DataTable to List<dynamic> (ExpandoObject)

Generic mapping (reflection-based):
- Reads DataTable columns
- Matches column names to class property names (case-insensitive)
- Sets property values using PropertyInfo.SetValue()
- Handles DBNull → null conversion

Why NOT EF Core:
- Oracle DB with existing stored procedures
- Legacy database schema (not designed for Code First)
- Team familiarity with ADO.NET
- Complex Oracle-specific queries (PL/SQL blocks)
- Performance: Direct SQL gives more control for complex reports
- Existing OracleHelper was already proven in production

Connection management:
- Connection string from AppConfigManager (appsettings.json)
- Each method opens/closes connection (no connection pooling issues)
- OracleConnection.ClearPool() called in finally blocks
- Parameterized queries supported via OracleParameter[]

If I were to improve:
- Add using statements (IDisposable pattern)
- Use Dapper for simpler mapping (instead of custom reflection)
- Add async versions (ExecuteNonQueryAsync)
- Add connection pooling configuration

7Explain the custom middleware you implemented.▼
We have 3 custom middleware components:

1. CSP MIDDLEWARE (CspMiddleware):
   - Generates unique nonce per request
   - Adds Content-Security-Policy header
   - Allows only scripts with matching nonce
   - Prevents inline script injection (XSS)
   - Also adds: X-Content-Type-Options, X-Frame-Options

   // In Razor views:
   <script nonce="@ViewBag.CspNonce">
       // Only this script executes (has valid nonce)
   </script>

2. PATH TRAVERSAL MIDDLEWARE (PathTraversalMiddleware):
   - Checks request path for ../ patterns
   - Blocks encoded variants (%2e%2e, %252e)
   - Returns 400 Bad Request if detected
   - Prevents accessing files outside webroot

3. HTTP METHOD RESTRICTION (inline middleware):
   app.Use(async (context, next) => {
       if (context.Request.Method != "GET" && context.Request.Method != "POST")
       {
           context.Response.StatusCode = 405;
           return;
       }
       await next();
   });

4. SESSION AUTH FILTER (IActionFilter - not middleware but similar):
   - Checks "_audit_session" cookie on every request
   - Excludes Login and Error pages
   - Redirects to Login if not authenticated

Middleware order in pipeline:
UseForwardedHeaders → UseExceptionHandler → UseStaticFiles →
UseHttpsRedirection → PathTraversalMiddleware → CspMiddleware →
HTTP Method Check → UseRouting → UseAuthorization → MapControllers

Why middleware over filters:
- Middleware: Runs for ALL requests (including static files)
- Filters: Only for MVC controller actions
- Security headers need middleware (applies to everything)
8How did you implement brute force protection?▼
BruteForceProtection class handles account lockout:

Configuration:
- MaxFailedAttempts = 5
- LockoutMinutes = 15

Database table: AUDIT_LOGIN_ATTEMPTS
- emp_code (user ID)
- failed_count (current failed attempts)
- last_failed_time
- last_ip (IP address of attacker)
- is_locked (0/1)
- locked_until (timestamp)

Flow:
1. User attempts login
2. Check IsAccountLocked(userId) → if locked, reject immediately
3. If credentials wrong → RecordFailedAttempt(userId, ipAddress)
   - Increments failed_count
   - If failed_count >= 5 → sets is_locked=1, locked_until = now + 15 min
4. If credentials correct → ResetFailedAttempts(userId)
   - Resets failed_count to 0, is_locked to 0
5. GetRemainingLockoutSeconds() → shows user how long to wait

Security features:
- IP address sanitized (only allow IP-safe characters, max 45 chars)
- Expired lockouts auto-reset on next attempt
- Progressive lockout (lockout_count tracks total lockouts - never resets)
- Works at database level (survives app restart)

API integration:
- LoginController captures RemoteIpAddress from HttpContext
- Passes to BLL → BruteForceProtection
- Response includes lockout status and remaining seconds

Improvement I would make:
- Use parameterized queries instead of string concatenation
- Add rate limiting at IP level (not just user level)
- Add CAPTCHA after 3 failed attempts (before lockout)
9What was the most challenging problem you solved?▼
VAPT Security Remediation:

Challenge:
After a third-party VAPT audit, we received 20+ security vulnerabilities including XSS, SQL Injection, Path Traversal, Missing Security Headers, and Session Management issues. We had to fix all within 2 weeks without breaking existing functionality.

What I did:
1. Created InputValidator class with comprehensive XSS/SQL detection
   - Handles encoded variants (HTML-encoded, URL-encoded, double-encoded)
   - Whitelist-based HTML sanitizer for rich-text fields

2. Implemented CSP middleware with nonce-based script execution
   - Every inline script needs a unique nonce
   - Blocks injected scripts even if XSS bypasses input validation

3. Added Path Traversal middleware
   - Blocks ../ in all forms (raw, encoded, double-encoded)

4. Implemented Brute Force Protection
   - Database-backed lockout system
   - IP tracking, progressive lockout

5. Secured static files
   - Blocked access to .config, .json, .cs, .sql files

6. Moved secrets to environment variables
   - JWT secret, encryption keys out of appsettings.json

Result:
- All 20+ vulnerabilities fixed
- Re-audit passed with zero critical/high findings
- No functionality broken
- Performance not impacted

What I learned:
- Defense in depth (multiple layers of security)
- Never trust client input (validate on server always)
- Security headers are essential (CSP, X-Frame-Options)
- Secrets should never be in source code

18How do you handle concurrent users/session conflicts?▼
Multiple auditors can work simultaneously on different branches:

Concurrency handling:
1. OPTIMISTIC CONCURRENCY (database level):
   - Before update, check if record was modified since last read
   - Use timestamp/version column: WHERE last_modified = @originalTimestamp
   - If 0 rows affected → someone else modified → show conflict message

2. SESSION MANAGEMENT:
   - Each user has unique session (cookie-based)
   - CheckSessionFN API validates session is still active
   - Single session per user (new login invalidates old session)
   - Prevents same user logged in from multiple devices

3. RECORD LOCKING (for critical operations):
   - Audit observation: Once auditor starts editing, others see "In Progress"
   - Status-based workflow prevents two people approving same record
   - Database status column acts as soft lock

4. WORKFLOW-BASED ISOLATION:
   - Each auditor assigned specific branches
   - Assignment approval prevents duplicate assignments
   - Status transitions: Draft → Submitted → Approved (one-way)
   - Only current assignee can modify

What we DON'T do (and why):
- No pessimistic locking (would block users too long)
- No SignalR real-time updates (not needed for our workflow)
- No distributed locks (single DB server handles it)

If asked "what would you improve":
- Add real-time notifications when someone else modifies same record
- Implement proper ETag-based concurrency for API

   - Never serve files from webroot directly
   - Validate file content (not just extension)
   - Rename files (prevent path traversal)
   - Restrict folder permissions
   - Block executable files (.exe, .bat, .ps1)

Code pattern:
[HttpPost("upload")]
public async Task<IActionResult> Upload(IFormFile file)
{
    if (file == null || file.Length == 0)
        return BadRequest("No file");
    if (file.Length > 5 * 1024 * 1024)
        return BadRequest("File too large");
    
    var fileName = Guid.NewGuid() + Path.GetExtension(file.FileName);
    var path = Path.Combine(_uploadPath, fileName);
    using var stream = new FileStream(path, FileMode.Create);
    await file.CopyToAsync(stream);
    
    // Save path to DB
    return Ok(new { fileName });
}

Error handling in ApiManager:
try
{
    var response = await httpClient.PostAsync(url, content);
    if (!response.IsSuccessStatusCode)
    {
        // Log error
        ErrorLog.Write($"API Error: {response.StatusCode} at {url}");
        return new Response { StatusCode = 500, Message = "Service unavailable" };
    }
    return await response.Content.ReadAsAsync<Response>();
}
catch (TaskCanceledException)  // Timeout
{
    ErrorLog.Write($"API Timeout: {url}");
    return new Response { StatusCode = 408, Message = "Request timed out" };
}
catch (HttpRequestException ex)  // Connection refused
{
    ErrorLog.Write($"API Down: {url} - {ex.Message}");
    return new Response { StatusCode = 503, Message = "Service unavailable" };
}

25Explain a stored procedure you wrote.▼
Example: PROC_AUDIT_PUNCHING_BLOCK

Purpose: Automatically blocks branches where audit is overdue.

Logic:
1. Check all branches with pending audits
2. If audit not completed within deadline → mark branch as BLOCKED
3. Send alert notification to branch head
4. Log the blocking action with timestamp

Pseudo-code:
CREATE OR REPLACE PROCEDURE PROC_AUDIT_PUNCHING_BLOCK AS
    v_count NUMBER;
BEGIN
    -- Find branches with overdue audits
    FOR rec IN (
        SELECT branch_code, audit_due_date, branch_head_email
        FROM AUDIT_ASSIGNMENTS
        WHERE status = 'PENDING'
        AND audit_due_date < SYSDATE
        AND is_blocked = 0
    ) LOOP
        -- Block the branch
        UPDATE AUDIT_ASSIGNMENTS
        SET is_blocked = 1,
            blocked_date = SYSDATE,
            blocked_reason = 'Audit overdue'
        WHERE branch_code = rec.branch_code;

        -- Insert alert notification
        INSERT INTO AUDIT_ALERTS (branch_code, alert_type, alert_date, message)
        VALUES (rec.branch_code, 'BLOCK', SYSDATE, 'Branch blocked due to overdue audit');

        COMMIT;
    END LOOP;
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        INSERT INTO ERROR_LOG (proc_name, error_msg, error_date)
        VALUES ('PROC_AUDIT_PUNCHING_BLOCK', SQLERRM, SYSDATE);
        COMMIT;
END;

Called from:
- Scheduled job (Oracle DBMS_SCHEDULER) runs daily
- Also callable from API for manual blocking

Why SP instead of C# code:
- Runs directly on DB server (no network round-trip)
- Atomic operation (COMMIT/ROLLBACK)
- Can be scheduled by DBA
- Processes thousands of branches efficiently
- Business rule stays close to data
26How does session work if you have multiple servers?▼
Current setup: Single server (no load balancing needed yet)

Our session approach:
- Cookie-based session ("_audit_session" cookie)
- Session data stored in Oracle DB (not in-memory)
- CheckSessionFN API validates session against DB
- Any server can validate because session is in DB

Why DB-based session works for scaling:
- Session not tied to specific server
- Any server can read session from Oracle
- No sticky sessions needed
- Survives server restart

If we add load balancer (future):
Option 1: Database sessions (current - already works)
- All servers read/write session to same Oracle DB
- Slight latency (DB call per request)

Option 2: Distributed cache (Redis):
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = "redis-server:6379";
});
builder.Services.AddSession();
- Faster than DB
- Shared across all servers
- Auto-expiry

Option 3: Sticky sessions (not recommended):
- Load balancer routes same user to same server
- Problem: If server dies, session lost

Our validation flow:
1. User logs in → API creates session record in DB
2. Session ID returned as cookie
3. Every request → SessionAuthFilter checks cookie exists
4. Periodically → CheckSessionFN validates against DB
5. Logout → Session deleted from DB + cookie cleared
6. Timeout → DB record expires (configurable)

Best practice answer:
"Currently single server with DB-backed sessions. If we scale, 
we'd add Redis for distributed session — our architecture already 
supports it since sessions aren't stored in-memory."

28What design patterns did you use in your project?▼
Patterns used in Audit/Inspection projects:

1. SINGLETON PATTERN (BLL classes):
   public class LoginBLL
   {
       private static LoginBLL _instance;
       public static LoginBLL Instance =>
           _instance ?? (_instance = new LoginBLL());
   }
   // Used for: All BLL classes (stateless, reusable)
   // Why: No need to create new instance per request (no state)

2. LAYERED ARCHITECTURE PATTERN:
   Controller → BLL → DAL → Database
   // Separation of concerns
   // Each layer has single responsibility

3. DTO PATTERN (Data Transfer Objects):
   - Request DTOs: LoginRequest, ObservationRequest
   - Response DTOs: LoginResponse, wrapped in Response<T>
   // Prevents exposing internal models to API consumers

4. REPOSITORY PATTERN (OracleHelper):
   - Generic data access methods
   - GetRecords<T>(), GetRecord<T>(), ExecuteNonQuery()
   // Abstracts database operations

5. MIDDLEWARE PATTERN (ASP.NET Core pipeline):
   - CspMiddleware, PathTraversalMiddleware
   - Chain of responsibility for request processing

6. FILTER PATTERN (Action Filters):
   - SessionAuthFilter: Cross-cutting auth concern
   - CspNonceActionFilter: Adds nonce to every response

7. FACTORY-LIKE (OracleHelper command creation):
   - Determines CommandType based on query string
   - Text for SELECT/INSERT, StoredProcedure otherwise

8. OBSERVER (Email notifications):
   - When observation status changes → notify relevant users
   - Decoupled: Action doesn't know who gets notified

Interview answer:
"We use Singleton for BLL classes since they're stateless.
Layered architecture for separation of concerns. DTO pattern

29Did you face any DI lifetime issue? Real scenario.▼
Honest answer (our project uses static instances, not full DI):

"In our current project, BLL classes use static Singleton pattern
(LoginBLL.Instance) rather than ASP.NET Core's built-in DI container.
This was a design decision from early development."

Issue we faced:
- OracleHelper creates new connection per method call
- BLL is singleton (static) but OracleHelper is created inside methods
- No issue because OracleHelper is stateless (new instance per call)
- BUT: If we had shared state, singleton would cause thread-safety bugs

What I would do differently (shows growth):
// Current (static singleton):
public class LoginBLL
{
    private static LoginBLL _instance;
    public static LoginBLL Instance => _instance ?? (_instance = new LoginBLL());
}
// Controller: LoginBLL.Instance.LoginEntryFN(request);

// Better (proper DI):
public interface ILoginService { Response Login(LoginRequest req); }
public class LoginService : ILoginService { ... }

// Program.cs:
builder.Services.AddScoped<ILoginService, LoginService>();

// Controller:
public LoginController(ILoginService loginService) { _service = loginService; }

Why DI is better:
- Testable (mock ILoginService in unit tests)
- Scoped lifetime (proper per-request isolation)
- No thread-safety concerns
- Follows SOLID (Dependency Inversion)

Real DI issue I know about (for interview):
- Captive dependency: If Singleton injects Scoped service
- Our OracleHelper avoids this by being created fresh each time
- If we used DbContext (Scoped) inside Singleton BLL = BUG
- Solution: Use IServiceScopeFactory to create scope manually
