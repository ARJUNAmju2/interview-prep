Project-Based Questions (Audit Module)

1Explain your project architecture.▼
Sure. Let me explain the architecture of our Audit Solution project.

We follow a layered architecture pattern. The solution is divided into 5 separate projects, each with a clear responsibility.

The first layer is AuditSolution.Web — this is our ASP.NET Core MVC application. It handles the user interface using Razor Views. The controllers here are thin — they only serve views. All the actual business logic is handled by our API layer. So when a user interacts with the UI, JavaScript makes AJAX calls to our Private API.

The second layer is AuditSolution.PrivateAPI — this is our Web API project. It exposes RESTful endpoints that the web layer consumes internally. It handles all the business operations like login, audit observations, assignments, approvals, and reports. This API is NOT exposed to the internet — it sits behind our firewall and only our web application can access it.

The third layer is AuditSolution.Core — this contains our Business Logic Layer (BLL) and Data Access Layer (DAL). The BLL classes contain all the business rules — like validation, workflow logic, calculations. The DAL handles all database operations using our custom OracleHelper class. We also have DTOs here — separate Request and Response objects for each API endpoint.

The fourth layer is AuditSolution.Helpers — this is for cross-cutting concerns. It contains our JwtService for token generation, OracleHelper for database access, InputValidator for security (XSS, SQL injection prevention), Email service, Encryption utilities, and custom Middleware classes like CSP and Path Traversal protection.

Finally, we have Audit_mail_console — a separate console application that runs as a scheduled task for sending batch email notifications.

The request flow goes like this: Browser sends request to MVC Web, JavaScript makes AJAX call to Private API, API calls BLL for business logic, BLL calls DAL for database operations, DAL uses OracleHelper to communicate with Oracle Database, and the response flows back the same way.

We chose this architecture because it gives us clear separation of concerns — each layer has a single responsibility. The API can be reused if we ever build a mobile app. Security is better because the API is not directly exposed to users. And each layer can be tested independently.
2How does authentication work in your project?▼
We use a dual authentication approach in our project — session-based for the web layer and JWT token-based for the API layer.

Let me walk you through the complete login flow.

When a user enters their credentials on the login page, our JavaScript sends an AJAX POST request to the Private API endpoint — specifically /api/Login/LoginEntryFN. The API receives this request in the LoginController.

Before validating credentials, we first check if the account is locked. We have a BruteForceProtection class that checks the AUDIT_LOGIN_ATTEMPTS table in Oracle. If the user has failed 5 times within a window, their account is locked for 15 minutes, and we return an error immediately.

If the account is not locked, we validate the credentials against the database. The password is encrypted using our ClsCrypto class before comparison.

If credentials are valid, our JwtService generates a JWT token. The token includes claims like the user's email, role, a unique JTI (token ID), and an IAT (issued at timestamp). The token is signed using HMAC-SHA256 with a secret key that we store in a machine-level environment variable — never in appsettings.json for security.

The API returns this token to the web layer. The web layer then sets a session cookie called "_audit_session" with HttpOnly and Secure flags — this prevents JavaScript from reading the cookie (XSS protection) and ensures it's only sent over HTTPS.

For subsequent requests, we have a custom SessionAuthFilter — this is an IActionFilter that runs on every request. It checks if the "_audit_session" cookie exists. If not, it redirects to the login page. We exclude the Login and Error pages from this check.

For API calls, the JWT token is sent in the Authorization header as "Bearer token". The API validates the token's signature, expiry, and claims before processing the request.

On logout, we clear the session cookie and invalidate the session in the database. We also have a CheckSessionFN endpoint that the frontend periodically calls to verify the session is still active — this handles cases where the session expires or admin force-logs out a user.
3How do you handle security (VAPT fixes) in your project?▼
Security is something we take very seriously in our project. After a third-party VAPT audit, we received around 20 security vulnerabilities and I was responsible for fixing all of them. Let me explain the key security measures we implemented.

First, Input Validation. We created a comprehensive InputValidator class that checks every user input for three types of attacks — XSS (Cross-Site Scripting), SQL Injection, and HTML Injection. What makes our validator strong is that it doesn't just check the raw input — it also checks HTML-decoded, URL-decoded, and even double-URL-decoded variants. Attackers often encode their payloads to bypass simple filters, so we handle all those cases. For rich-text fields where users need basic formatting, we have a SanitizeHtml method that uses a whitelist approach — it only allows safe tags like bold, italic, lists, and strips everything else including event handlers, script tags, and dangerous attributes.

Second, Content Security Policy (CSP). We implemented a custom CSP Middleware that generates a unique nonce for every request. This nonce is passed to Razor views through ViewBag, and every inline script must include this nonce to execute. So even if an attacker manages to inject a script tag through some vulnerability, it won't execute because it won't have the correct nonce. The middleware also adds other security headers like X-Content-Type-Options: nosniff, X-Frame-Options: DENY, and X-XSS-Protection.

Third, Path Traversal Protection. We have a middleware that blocks any request containing ../ patterns — whether raw, URL-encoded, or double-encoded. This prevents attackers from accessing files outside our webroot.

Fourth, Static File Protection. In our Startup.cs, we configured UseStaticFiles with an OnPrepareResponse callback that blocks access to sensitive file extensions like .config, .json, .cs, .sql, .log, .bak. If someone tries to access these, we return a 404.

Fifth, Brute Force Protection. After 5 failed login attempts, we lock the account for 15 minutes. We track the IP address of failed attempts, and the lockout count never fully resets — it's progressive, meaning repeated lockouts result in longer lockout periods.

Sixth, we moved all sensitive secrets to environment variables — JWT secret key, payload encryption key — these are set at the machine level and never stored in source code or config files.

Seventh, we only allow GET and POST HTTP methods. Any other method like PUT, DELETE, or OPTIONS returns a 405 status code. This reduces our attack surface.

All these measures combined give us defense-in-depth — multiple layers of security so that if one layer fails, others still protect us.
4How does your Data Access Layer work? Why not EF Core?▼
Our Data Access Layer is built around a custom OracleHelper class that provides generic methods for all database operations. Let me explain how it works and why we chose this approach over Entity Framework Core.

The OracleHelper class is essentially an ADO.NET wrapper specifically designed for Oracle Database. It provides several methods — ExecuteNonQuery for INSERT, UPDATE, DELETE operations; ExecuteScalar for getting single values like COUNT or MAX; ExecuteDataTable and ExecuteDataSet for fetching tabular data; and ExecuteReader for forward-only data reading.

What makes it really useful is the generic method GetRecords of T. This method takes a SQL query, executes it, gets a DataTable, and then uses reflection to map each row to a strongly-typed C# object. It matches DataTable column names to class property names in a case-insensitive manner, handles DBNull to null conversion, and returns a List of T. So our BLL layer can simply call OracleHelper.GetRecords of AuditObservation with a query and get back a typed list. We also have GetRecord of T for single object mapping.

For connection management, each method opens a new connection, executes the operation, and closes it in a finally block. We also call OracleConnection.ClearPool to prevent connection pool issues. The connection string is read from appsettings.json through our AppConfigManager class.

Now, why didn't we use Entity Framework Core? There are several practical reasons. First, our database was already existing with a complex schema designed by our DBA team — it wasn't designed for Code First. Second, we have a lot of complex stored procedures and PL/SQL blocks that are easier to call directly through ADO.NET. Third, for our reporting queries which involve complex Oracle-specific syntax like CONNECT BY for hierarchies, analytical functions, and PL/SQL anonymous blocks, raw SQL gives us more control. Fourth, our team was already experienced with this approach and the OracleHelper was proven in production.

However, if I were to improve this today, I would add async methods for better scalability, use parameterized queries everywhere to prevent SQL injection, implement the IDisposable pattern properly with using statements, and possibly use Dapper as a lightweight alternative that still gives us the control of raw SQL but with better mapping capabilities than our custom reflection approach.
5How does the Web layer communicate with the API?▼
The communication between our MVC Web layer and the Private API happens through AJAX calls, facilitated by a centralized ApiManager helper class.

Here's how the flow works end-to-end. When a user performs an action on the UI — say, submitting an audit observation — the JavaScript on the page collects the form data, creates a JSON object, and makes an AJAX POST request. This request goes to our Private API endpoint, not back to the MVC controller.

The ApiManager is a helper class in our Helpers project that centralizes all HTTP communication. It handles several things — setting the base URL (configured in appsettings.json), adding the JWT token to the Authorization header for every request, applying request payload encryption using our RequestEncryption class (the encryption key comes from an environment variable), setting proper content-type headers, and handling timeout and error scenarios.

On the API side, the controller receives the request, deserializes it into a strongly-typed Request DTO (like ObservationRequest), passes it to the BLL layer for processing, and returns a standardized Response wrapper object. This Response wrapper always contains a statusCode, a message, and a data property — so our frontend always knows the format to expect.

For example, when fetching audit observations for a dashboard, the JavaScript calls something like POST /api/AuditObservation/GetObservations with filter parameters. The API processes it through BLL which calls DAL which queries Oracle, and returns a Response containing the list of observations.

We chose AJAX over form-based postbacks because it gives us a smoother user experience — no full page reloads. The user stays on the same page and only the data section updates. It also cleanly separates our frontend from backend — the MVC controllers only serve views, all data operations go through the API.

The reason we have a separate Private API instead of putting everything in the MVC controllers directly is security and reusability. The API can be consumed by a mobile app in the future, and keeping it separate means our API layer can be deployed and scaled independently if needed.
6How do you handle role-based access in the Audit module?▼
Our Audit module has a multi-role system where different users see completely different interfaces and have different permissions. Let me explain how we implemented this.

We have six main roles — Auditor who conducts the actual audits, Audit Manager who oversees auditors and approves their work, Audit Head who gives final approval, Executive who sees high-level dashboards and summary reports, MIS team who generates detailed reports, and Client or User Management who responds to audit observations with action plans.

When a user logs in, the API validates their credentials and retrieves their role from the database. This role is included as a claim in the JWT token. Based on the role, the frontend redirects them to their specific dashboard — for example, an Auditor goes to Auditor_Dashboard, an Audit Manager goes to AM_Dashboard, and so on.

Each role has its own dedicated set of API controllers. For example, we have Aud_dashboardController for auditors, AMdashController for Audit Managers, AHdashController for Audit Head, ExecutiveController, and MisController. This means even if someone somehow gets the URL for another role's page, the API won't serve them data because it validates the role before processing.

The workflow is sequential and role-dependent. An Auditor creates an observation and submits it. Then only the Audit Manager can see it in their approval queue. The Manager can either approve it (which sends it to Audit Head) or return it (which sends it back to the Auditor for correction). Once the Audit Head confirms, it goes to User Management who must respond with an action plan. The Auditor then verifies whether the action plan was actually implemented.

At each stage, the record's status changes — DRAFT, SUBMITTED, APPROVED, RETURNED, CONFIRMED — and only the correct role can perform the next action. This prevents unauthorized state transitions.

On the frontend, menu items are shown or hidden based on the user's role using JavaScript. But this is only for UX — the real security is on the API side where every endpoint validates the role before processing.
7Explain the custom middleware you implemented.▼
We implemented three custom middleware components in our Audit project, each addressing a specific security concern identified during our VAPT assessment.

The first and most important is our CSP Middleware — Content Security Policy. This middleware generates a cryptographically unique nonce string for every incoming HTTP request. This nonce is stored in HttpContext.Items so that our Razor views can access it through ViewBag. In our views, every inline script tag includes this nonce attribute. When the browser receives the response, the CSP header tells it to only execute scripts that have a matching nonce. So even if an attacker manages to inject a script tag through an XSS vulnerability, it won't execute because it won't have the correct nonce for that request. The middleware also adds other security headers — X-Content-Type-Options to prevent MIME sniffing, X-Frame-Options DENY to prevent clickjacking, and Referrer-Policy for privacy.

The second middleware is our Path Traversal Middleware. This checks every incoming request URL for directory traversal patterns. Attackers use sequences like ../ or their encoded equivalents like %2e%2e%2f or even double-encoded %252e%252e to try to access files outside the webroot — like configuration files, source code, or system files. Our middleware decodes the URL, checks for these patterns, and immediately returns a 400 Bad Request if detected. This runs early in the pipeline before routing, so malicious requests never reach our controllers.

The third is an inline middleware that restricts HTTP methods. We only allow GET and POST in our application — we don't need PUT, DELETE, OPTIONS, or TRACE. So we added a simple middleware using app.Use that checks the request method and returns 405 Method Not Allowed for anything other than GET or POST. This reduces our attack surface because attackers can't use methods like OPTIONS to discover our API structure or use TRACE for cross-site tracing attacks.

The middleware order in our pipeline is very specific — we use ForwardedHeaders first for proxy support, then ExceptionHandler for error catching, then StaticFiles with our security filter, then HTTPS redirection, then Path Traversal middleware, then CSP middleware, then the HTTP method check, then Routing, and finally Authorization. This order ensures security checks happen before any business logic runs.
8How did you implement brute force protection?▼
Brute force protection was one of the VAPT findings we had to address. The concern was that an attacker could keep trying different passwords on a user account without any limitation. Here's how I implemented the solution.

We created a BruteForceProtection class with a database-backed tracking system. We have a table called AUDIT_LOGIN_ATTEMPTS in Oracle that stores the employee code, failed attempt count, last failed timestamp, the IP address of the attacker, a locked flag, and a locked-until timestamp.

The flow works like this. When a login attempt comes in, the first thing we do is call IsAccountLocked. This queries the database to check if the user has is_locked set to 1 and locked_until is still in the future. If they're locked, we immediately reject the login and return the remaining lockout seconds so the frontend can show a countdown.

If the account is not locked and the credentials are wrong, we call RecordFailedAttempt. This does several things — if the user has no record in the attempts table, it creates one with failed_count of 1. If a record exists, it increments the failed_count and updates the last_failed_time and IP address. Then it checks if the failed_count has reached our threshold of 5. If it has, it sets is_locked to 1 and locked_until to the current time plus 15 minutes.

If the credentials are correct, we call ResetFailedAttempts which sets failed_count back to 0 and clears the locked flag. This allows the user to log in normally after their lockout expires.

We also track the attacker's IP address. The LoginController captures the RemoteIpAddress from HttpContext.Connection and passes it through the request. We sanitize this IP to only allow safe characters and limit it to 45 characters to prevent any injection through the IP field.

One important design decision — the lockout is progressive. We have a lockout_count field that tracks how many times the account has been locked total, and this never resets even after successful login. This can be used in the future for escalating lockout durations or alerting administrators about potential attacks.

If I were to improve this today, I would replace the string concatenation in queries with parameterized queries for better SQL injection safety, add rate limiting at the IP level not just user level, and introduce CAPTCHA after 3 failed attempts as a softer deterrent before the hard lockout kicks in.
9What was the most challenging problem you solved?▼
The most challenging task I handled was the complete VAPT security remediation for our Audit Solution. Let me explain why it was challenging and how I approached it.

We received a VAPT report from a third-party security firm with over 20 vulnerabilities — including Critical and High severity findings like Cross-Site Scripting, SQL Injection possibilities, missing security headers, path traversal vulnerabilities, information disclosure through error messages, and weak session management. We had a strict deadline of 2 weeks to fix everything because the application was about to go live.

The challenge wasn't just fixing individual issues — it was fixing them without breaking any existing functionality. Our application has complex workflows with multiple roles, AJAX calls, rich-text editors, and dynamic content. A wrong security fix could easily break something.

Here's how I approached it systematically. First, I categorized the vulnerabilities by severity and by fix type. Some fixes were global like adding security headers through middleware — one change fixed multiple findings. Others were specific to certain input fields or pages.

For XSS prevention, I built the InputValidator class from scratch. The tricky part was handling encoded payloads — attackers use HTML encoding, URL encoding, double encoding, and mixed encoding to bypass simple filters. So I made the validator check the raw input plus all decoded variants. For rich-text fields, I couldn't just strip all HTML because users need formatting. So I implemented a whitelist-based sanitizer that preserves safe tags while removing dangerous ones.

For the CSP implementation, the challenge was that we had inline scripts throughout the application. I had to generate a unique nonce per request and update every view to include the nonce. This required touching almost every Razor view file.

For path traversal, I had to be careful not to block legitimate URLs that might contain encoded characters for valid reasons.

The result was that all 20-plus vulnerabilities were fixed within the deadline. The re-audit came back with zero Critical or High findings. No functionality was broken, and performance was not impacted. This experience taught me the importance of defense-in-depth — having multiple security layers so that if one is bypassed, others still protect you.
10How do you handle errors and logging?▼
Error handling in our project works at multiple levels to ensure that errors are caught gracefully, logged properly, and never exposed to end users.

At the top level, we have the global exception handler configured in our Startup.cs — app.UseExceptionHandler pointing to /Home/Error. This catches any unhandled exception that bubbles up from our application and redirects to a generic error page. The user never sees a stack trace or technical error message.

At the API level, we follow a consistent response pattern. Every API endpoint returns a Response wrapper object with statusCode, message, and data properties. If something goes wrong in the BLL or DAL, the catch block returns a Response with statusCode 500 and a generic message like "An error occurred while processing your request." The actual exception details are never sent to the client.

We have an ErrorLog helper class that captures errors and writes them to a log file with timestamp, user information, the action being performed, and the full exception details including inner exceptions. This helps us debug issues without exposing sensitive information to users.

We also have a SafeError class that maps internal error types to user-friendly messages. For example, if a database connection timeout occurs, the user sees "Service temporarily unavailable, please try again" instead of "ORA-12170: TNS:Connect timeout occurred."

At the database level, our OracleHelper has try-catch in every method with finally blocks that ensure connections are always closed and disposed. If a query fails, it returns empty results rather than crashing — this is graceful degradation.

For the frontend, our AJAX calls have error callbacks that show user-friendly toast notifications using SweetAlert when API calls fail, with appropriate messages based on the HTTP status code.

What I would improve if given the chance — I would implement structured logging using Serilog with different sinks like file, database, and possibly a centralized logging system. I would add correlation IDs to trace a request across all layers. And I would implement health check endpoints so we can monitor application health proactively.
11How does the email/notification system work?▼
We have two email mechanisms in our project — inline emails for immediate notifications and a scheduled console application for batch emails.

For inline emails, we have an Email helper class that sends emails immediately when certain actions happen. For example, when an auditor submits an observation, the system immediately sends an email to the Audit Manager notifying them that a new observation is waiting for their approval. Similarly, when the Manager approves or returns an observation, the relevant person gets notified instantly. These emails use SMTP and are sent synchronously during the API request. We use HTML email templates with placeholders that get replaced with actual data like employee name, branch name, observation details, and action links.

For batch emails, we have a separate console application called Audit_mail_console. This runs as a Windows Scheduled Task — configured to run at specific times, like daily at 9 AM. It queries the database for pending notifications — things like daily audit summaries, reminder emails for overdue actions, weekly status reports to management. It processes all pending emails in a batch, marks them as sent in the database, and handles retry logic for any that fail.

We chose a separate console application for batch emails because it doesn't block the web request — users don't have to wait while emails are being sent. It can retry failed emails without affecting the web application. It runs independently, so even if the web app is down for maintenance, scheduled emails still go out. And it handles bulk emails efficiently without impacting web application performance.

The email triggers in our workflow include — observation created notifies Audit Manager, observation approved notifies Audit Head, observation returned notifies the Auditor, action plan submitted notifies the Auditor for verification, audit commenced notifies all assigned auditors, and daily summary reports go to management.
12What would you improve/refactor in this project?▼
This is a question I actually think about often, and I have several improvements in mind. Let me share the key ones.

First, in the Data Access Layer, I would replace all string concatenation in SQL queries with parameterized queries. Currently some of our older code like the BruteForceProtection class builds queries using string concatenation, which is a SQL injection risk even though we have input validation. I would also add async versions of all OracleHelper methods — right now they're synchronous which means threads are blocked during database calls. Using async would improve our scalability significantly. And I would consider using Dapper as a lightweight ORM instead of our custom reflection-based mapping — it's faster and less code to maintain.

Second, in architecture, I would replace the static Singleton pattern in our BLL classes with proper Dependency Injection. Currently we use LoginBLL.Instance which is a static singleton — this makes unit testing very difficult because you can't mock it. With DI, we would register BLL classes as scoped services and inject interfaces into controllers, making everything testable. I would also introduce IHttpClientFactory for our ApiManager instead of manually creating HttpClient instances.

Third, for security improvements, I would implement refresh tokens. Currently when the JWT expires, the user has to log in again. With refresh tokens, we could silently get a new access token without interrupting the user's work. I would also add comprehensive audit trail logging — tracking who did what, when, from where — for compliance purposes.

Fourth, for testing, I would add unit tests for the BLL layer and integration tests for API endpoints. Currently we have no automated tests, which means we rely on manual testing before deployments.

Fifth, for observability, I would implement structured logging using Serilog, add correlation IDs for request tracing across layers, and set up health check endpoints for monitoring.

I mention these improvements in interviews because it shows I think critically about code quality and I'm not just maintaining code — I'm always looking for ways to make it better.

17Why do you have both Public API and Private API?▼
We separate our APIs into Public and Private for security and access control purposes. Let me explain the difference and why we made this architectural decision.

The Private API is consumed exclusively by our MVC Web application. It sits on our internal network, behind the firewall, and is not accessible from the internet. It handles all business operations — login, data retrieval, CRUD operations, approvals, reports. Since it's internal, it trusts that requests coming to it have already passed through our web layer's security checks.

The Public API, on the other hand, is exposed to external clients — specifically our mobile application used by Area Managers for field inspections. Since it's internet-facing, it has additional security measures — stricter rate limiting, CORS configuration, Swagger documentation for external developers, and it only exposes a limited subset of endpoints. Not everything available in the Private API is available publicly.

The reason for this separation comes down to the principle of least privilege and reducing attack surface. If we only had one API exposed to the internet, all our internal operations would be potentially attackable. By separating them, we keep most of our business logic behind the firewall. The Public API is like a controlled gateway — it only allows specific operations that mobile users need.

From a deployment perspective, the Private API runs on an internal port that's only accessible within our network. The Public API runs on a different port that's exposed through our DMZ. The MVC Web application is the only public-facing component that users interact with directly.

This also helps with monitoring — we can track external API usage separately from internal usage, apply different rate limits, and if the Public API is under attack, our internal operations continue unaffected.

In the AM_Inspection project, the Public API is what the mobile app calls for GPS tracking and inspection submissions. The Private API handles the same data but for the web dashboard where managers review and approve inspections.
18How do you handle concurrent users/session conflicts?▼
In our Audit module, we can have multiple auditors, managers, and executives all working simultaneously. Here's how we handle concurrency and prevent conflicts.

The primary mechanism is our workflow-based isolation. Each auditor is assigned to specific branches, and assignments go through an approval process. This means two auditors can never work on the same branch's audit simultaneously — the assignment system prevents it. Similarly, once an observation is submitted, only the assigned Audit Manager can act on it. The status transitions are one-way — DRAFT to SUBMITTED to APPROVED to CONFIRMED — so there's no scenario where two people modify the same record at the same step.

For session management, each user has a unique session tracked in the database. When a user logs in, we create a session record. If the same user tries to log in from another device or browser, the new login invalidates the old session — we enforce single-session-per-user. The frontend periodically calls CheckSessionFN to verify the session is still valid. If it's been invalidated, the user is redirected to login.

For the rare cases where concurrent modification could happen — like two managers updating configuration settings — we use optimistic concurrency at the database level. Before updating a record, we check if it was modified since we last read it by comparing a last_modified timestamp. If someone else modified it in between, we return an error asking the user to refresh and try again.

We don't use pessimistic locking because it would block users for too long in a web application context. We also don't use SignalR for real-time updates because our workflow naturally prevents conflicts — each step has a single owner.

If I were to enhance this in the future, I would add real-time notifications when someone else modifies a record you're viewing, and implement proper ETag-based concurrency headers for our API responses.

20How do you handle file uploads in your project?▼
File uploads are used in our project for audit evidence — auditors attach photos, documents, and PDFs to their observations as proof of findings. Here's how we handle it securely.

On the frontend, we have a file input with accept attributes to restrict file types visually. Before uploading, JavaScript validates the file size — we enforce a 5MB limit per file. The file is sent as FormData through an AJAX POST request to our API endpoint.

On the API side, we receive the file as IFormFile. Our FileUploadValidator helper class performs several security checks. First, it validates the file extension against a whitelist — we only allow .jpg, .png, .pdf, .doc, and .xlsx. Second, it checks the actual content type of the file, not just the extension — because an attacker could rename a .exe to .jpg. Third, it enforces the size limit server-side as well, because client-side validation can be bypassed.

For storage, we generate a unique filename using GUID plus the original extension. We never use the original filename because it could contain path traversal characters or special characters that cause issues. The file is saved to a dedicated folder on the server that's outside the webroot — this means files can't be accessed directly through a URL. The folder structure is organized by year and month for manageability.

We store only the generated filename and path in the Oracle database, not the file content itself. When a user wants to view or download the file, they make an API request. The API verifies the user has permission to access that file, then returns it as a FileResult with proper Content-Disposition headers.

Security measures specifically for uploads include — we block all executable extensions like .exe, .bat, .ps1, .dll. We restrict folder permissions so the upload directory can't execute scripts. We scan filenames for path traversal patterns. And we never serve files from a publicly accessible directory.

This approach ensures that even if an attacker manages to upload a malicious file, it can't be executed because it's stored outside webroot and served only through our controlled API endpoint.
21What database design decisions did you make?▼
Our Oracle Database design follows a normalized structure with clear separation between master data and transactional data. Let me explain the key design decisions.

For table structure, we have master tables like Branches, Departments, Roles, and Question Masters that hold reference data which rarely changes. Then we have transactional tables like AUDIT_OBSERVATIONS, AUDIT_ASSIGNMENTS, AUDIT_ACTION_PLANS, and AUDIT_SCORECARD that hold the actual business data that grows over time.

Every table has standard audit columns — CREATED_BY, CREATED_DATE, MODIFIED_BY, MODIFIED_DATE. This gives us a complete audit trail of who created or modified any record and when. We never hard-delete records — instead we use an IS_ACTIVE or IS_DELETED flag for soft deletion. This preserves data integrity and allows recovery if needed.

For the workflow, we use a STATUS column that tracks the current state of a record. Observations go through DRAFT, SUBMITTED, APPROVED, RETURNED, CONFIRMED states. Each status change is logged with the timestamp and user who performed the action. This prevents invalid state transitions and provides a complete history.

We use Oracle Sequences for auto-incrementing primary keys since Oracle doesn't have SQL Server's IDENTITY feature. Each table has its own sequence, and we use triggers or application-level code to generate the next value.

For indexing, we have primary keys on all tables, indexes on frequently queried columns like emp_code, branch_code, and status. For complex report queries that join multiple tables, we have composite indexes. Our DBA monitors query performance and adds indexes when slow queries are identified.

We chose stored procedures for complex business operations that involve multiple steps. For example, PROC_AUDIT_PUNCHING_BLOCK runs daily to check overdue audits and automatically block non-compliant branches. Having this in a stored procedure means it runs directly on the database server without network round-trips, executes atomically with proper COMMIT/ROLLBACK, and can be scheduled through Oracle's DBMS_SCHEDULER.

For hierarchical queries like organizational structure, we use Oracle's CONNECT BY clause which efficiently traverses parent-child relationships — something that would require recursive CTEs in SQL Server.
22How do you handle API failures/timeouts?▼
Since our MVC Web layer depends entirely on the Private API for data, handling API failures gracefully is critical for user experience. Here's our approach.

In our ApiManager helper class, every HTTP call is wrapped in try-catch blocks with specific exception handling. We handle three main failure scenarios.

First, timeout — if the API doesn't respond within 30 seconds, a TaskCanceledException is thrown. We catch this specifically and return a response with status code 408 and a message saying the request timed out. The user sees a friendly message asking them to try again.

Second, connection failure — if the API server is completely down, an HttpRequestException is thrown. We catch this and return a 503 Service Unavailable response. The frontend shows a message like "Service is temporarily unavailable, please try again in a few minutes."

Third, unexpected errors — any other exception is caught by a general catch block, logged to our error log with full details, and a generic 500 error is returned to the frontend.

On the frontend JavaScript side, our AJAX calls have a timeout setting of 30 seconds. The error callback checks the status code and shows appropriate messages — network error for status 0, timeout message for 408, service unavailable for 503, and a generic error for anything else. We use SweetAlert or toast notifications to show these messages without disrupting the user's work.

One important thing — we never silently swallow errors. Every failure is logged with timestamp, the API endpoint that failed, the error details, and the user who was affected. This helps us quickly identify and fix issues.

What I would improve in this area — I would implement a retry policy using the Polly library. For transient failures like momentary network blips, we would retry 3 times with exponential backoff before giving up. I would also add a circuit breaker pattern — if the API fails 5 consecutive times, we stop calling it for 30 seconds to give it time to recover, instead of bombarding it with requests. And for critical operations like saving audit observations, I would implement a local queue — save the data locally and retry submission when the API comes back up, so users don't lose their work.

24How do you manage configuration across environments?▼
We manage configuration using a combination of appsettings.json files for non-sensitive settings and environment variables for secrets. Let me explain our approach.

ASP.NET Core has built-in support for environment-specific configuration. We have appsettings.json as the base configuration shared across all environments, appsettings.Development.json for local development with debug-level settings and local database connections, and appsettings.Production.json for production URLs and optimized timeouts. 25Explain a stored procedure you wrote.▼
Let me explain PROC_AUDIT_PUNCHING_BLOCK — a stored procedure that automatically blocks branches where audits are overdue.

The business requirement was — if a branch hasn't completed its scheduled audit within the deadline, certain operational activities for that branch should be blocked automatically. The branch head and relevant managers should be notified, and the blocking should be logged for audit trail purposes.

The procedure works like this. It starts by querying the AUDIT_ASSIGNMENTS table to find all branches where the audit status is still PENDING and the due date has passed, and the branch is not already blocked. This gives us a list of non-compliant branches.

For each such branch, the procedure does three things. First, it updates the AUDIT_ASSIGNMENTS record — setting is_blocked to 1, recording the blocked_date as SYSDATE, and storing the reason as "Audit overdue." Second, it inserts a record into the AUDIT_ALERTS table with the branch code, alert type "BLOCK", current timestamp, and a notification message. This alerts table is what our email console application reads to send notifications. Third, it commits after each branch to ensure partial progress is saved even if the procedure fails midway through a large batch.

The procedure has exception handling — a WHEN OTHERS block that rolls back the current iteration, logs the error to an ERROR_LOG table with the procedure name, Oracle error message (SQLERRM), and timestamp, then commits the error log and continues to the next branch.

This procedure runs daily through Oracle DBMS_SCHEDULER — configured to execute at 6 AM before business hours start. It can also be triggered manually from our API if an administrator needs to run an ad-hoc blocking check.

We chose to implement this as a stored procedure rather than C# code because it runs entirely on the database server with no network overhead, it's atomic per branch with proper transaction control, the DBA can monitor and tune it independently, and it executes efficiently even when processing hundreds of branches because there's no data transfer between application and database — everything happens at the data layer.
26How does session work if you have multiple servers?▼
Currently we run on a single server, so session management is straightforward. But our architecture is designed in a way that would support scaling to multiple servers without major changes. Let me explain how.

Our session is database-backed rather than stored in application memory. When a user logs in, we create a session record in Oracle with the session ID, user details, login timestamp, and expiry time. The session ID is sent to the browser as a cookie called "_audit_session" with HttpOnly and Secure flags.

For every subsequent request, our SessionAuthFilter checks if this cookie exists. For periodic validation, the frontend calls CheckSessionFN API which verifies the session against the database — checking if it exists, hasn't expired, and hasn't been invalidated.

The reason this approach is scalable is that the session data lives in Oracle, not in the application server's memory. If we add a second server behind a load balancer, both servers would read from the same Oracle database. So regardless of which server handles a particular request, it can validate the session because the source of truth is the shared database.

This is fundamentally different from in-memory session where your session data is stuck on one server. With in-memory sessions and a load balancer, you'd need sticky sessions which create single points of failure — if that server goes down, all users on it lose their sessions.

If we were to scale further and needed better session performance, I would introduce Redis as a distributed cache. Redis is faster than Oracle for simple key-value lookups like session validation, and it's designed for high-throughput scenarios. ASP.NET Core has built-in support for Redis-backed distributed sessions through AddStackExchangeRedisCache, so the change would be minimal.

The key takeaway is — our architecture already supports horizontal scaling because sessions aren't tied to a specific server instance. The database is our single source of truth for session state.
27How do you handle pagination for large data sets?▼
Our audit reports can contain thousands of records — all observations across all branches over months. Loading all of them at once would be slow and consume too much memory. So we implement server-side pagination.

The approach is — the frontend sends the page number, page size, search term, and sort column to the API. The API passes these to the BLL which constructs an Oracle query with proper OFFSET and FETCH, executes it, and returns only the requested page of data along with the total count for generating page navigation.

On the Oracle side, we use the ROWNUM approach for pagination since our database version supports it. The query structure is — an inner query with the actual WHERE conditions and ORDER BY, wrapped in a middle query that adds ROWNUM and limits to the end row, wrapped in an outer query that filters for rows greater than the start row. For Oracle 12c and above, we also use the cleaner OFFSET-FETCH syntax.

The API response includes the data array for the current page, totalCount for knowing how many pages exist, and totalPages calculated as ceiling of totalCount divided by pageSize.

On the frontend, we use jQuery DataTables with server-side processing enabled. DataTables handles the UI part — rendering the table, showing page numbers, handling sort clicks, and sending the appropriate parameters to our API. When a user clicks page 3 or sorts by a column, DataTables sends a new AJAX request with the updated parameters and our API returns just that page of data.

Search and filtering also happen at the database level. When the user types in the search box, the search term is sent to the API which adds it to the WHERE clause. We never load all data to the client and filter with JavaScript — that would defeat the purpose of pagination.

This approach means even with 50,000 records in the database, the initial page load only fetches 10-25 records, rendering is fast, and the browser uses minimal memory. Pagination, searching, sorting — all happen efficiently at the database level using proper indexes.
28What design patterns did you use in your project?▼
We use several design patterns in our project, some intentionally and some that emerged from our architecture. Let me walk through the main ones.

The most prominent is the Singleton pattern in our BLL classes. Each BLL class like LoginBLL, AuditObservationBLL has a static Instance property that returns a single instance. We chose this because our BLL classes are stateless — they don't hold any data between calls. They just contain methods that take a request, process business logic, call the DAL, and return a response. Since there's no state, creating a new instance for every request would be wasteful. However, I acknowledge this is not the ideal implementation — proper ASP.NET Core DI with scoped lifetime would be better for testability.

We follow the Layered Architecture pattern — Controller, BLL, DAL, Database — where each layer has a single responsibility and only communicates with adjacent layers. Controllers never directly access the database, and the DAL never contains business rules.

The DTO pattern is used extensively. We have separate Request and Response DTOs for every API endpoint. LoginRequest, LoginResponse, ObservationRequest, ObservationResponse — these ensure we never expose our internal domain models directly. The Response wrapper provides a consistent structure with statusCode, message, and data.

Our OracleHelper acts as a Repository pattern implementation — providing generic data access methods like GetRecords of T and GetRecord of T that abstract away the details of Oracle connection management, DataTable manipulation, and object mapping.

The Middleware pattern is central to our ASP.NET Core pipeline — CSP, Path Traversal, and HTTP method restriction all follow the chain of responsibility where each middleware decides whether to pass the request to the next one or short-circuit.

Our Action Filters like SessionAuthFilter follow the Aspect-Oriented pattern — cross-cutting concerns applied declaratively without cluttering our business code.

The email notification system follows an Observer-like pattern — when an observation status changes, the system notifies relevant users without the core logic knowing who gets notified.

In interviews, I'm honest about our patterns — I mention what we use, why, and what I would improve. This shows I understand patterns beyond textbook definitions.
29Did you face any DI lifetime issue? Real scenario.▼
I want to be honest here — our project uses a static Singleton pattern for BLL classes rather than ASP.NET Core's built-in DI container. So I haven't faced a classical DI lifetime issue like captive dependency in this project. But let me explain our setup, why it works, and what could go wrong.

Our BLL classes use static instances — LoginBLL.Instance returns a singleton. Inside each BLL method, we create a new OracleHelper instance to execute database operations. The OracleHelper itself creates a new Oracle connection, executes the query, and closes the connection within each method call. So even though the BLL is a singleton, the database resources are properly scoped to each method call — there's no shared state, no stale connections.

This approach works for us because our BLL is truly stateless. But if we had used something like Entity Framework's DbContext as a singleton — that would be a serious bug. DbContext is not thread-safe and maintains a change tracker that would accumulate objects across all requests, causing memory leaks and data corruption. That would be a captive dependency problem — a shorter-lived service captured by a longer-lived one.

If I were to refactor to proper DI, I would register BLL classes as Scoped services. This means one instance per HTTP request — ensuring thread safety and proper lifecycle. I would define interfaces like ILoginService, IObservationService, register them in Program.cs with AddScoped, and inject them into controllers through constructors.

The benefits would be significant — unit testability through mocking interfaces, proper lifetime management by the DI container, no static state to worry about, and following the Dependency Inversion Principle.

I've studied DI lifetime issues thoroughly even though our current codebase doesn't use full DI. I know that a Singleton should never depend on a Scoped service because the Scoped service would never get disposed — living forever inside the Singleton. The fix is to inject IServiceScopeFactory into the Singleton and create a scope manually when needed.

I present this honestly in interviews — I explain what our code does, acknowledge its limitations, and demonstrate that I understand the better approach and why it matters.
