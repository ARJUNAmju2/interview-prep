EF Core Interview Questions

1What is Entity Framework Core?▼
Entity Framework Core (EF Core) is a lightweight, cross-platform ORM (Object-Relational Mapper) for .NET that allows developers to work with databases using C# objects instead of writing raw SQL.

Key Features:
- Maps C# classes to database tables
- LINQ queries translated to SQL
- Change tracking (tracks modifications)
- Migrations (version control for database schema)
- Cross-platform (SQL Server, PostgreSQL, MySQL, SQLite)
- Lazy/Eager/Explicit loading

Without EF Core (raw SQL):
var cmd = new SqlCommand("SELECT * FROM Products WHERE Price > 100", conn);
var reader = cmd.ExecuteReader();

With EF Core (C# objects):
var products = await _context.Products
    .Where(p => p.Price > 100)
    .ToListAsync();

DbContext - The main class:
public class AppDbContext : DbContext
{
    public DbSet<Product> Products { get; set; }
    public DbSet<Category> Categories { get; set; }
    public DbSet<Order> Orders { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // Fluent API configurations
    }
}
2What is Code First vs Database First approach?▼
CODE FIRST:
- You write C# classes FIRST
- EF Core generates database from your classes
- Use Migrations to update database schema
- Full control over code
- Preferred for new projects

Flow: C# Classes → Migrations → Database

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
}

Commands:
dotnet ef migrations add InitialCreate
dotnet ef database update

DATABASE FIRST:
- Database exists FIRST
- EF Core generates C# classes from database
- Use Scaffold-DbContext command
- Used for existing/legacy databases

Flow: Database → Scaffold → C# Classes

Command:
dotnet ef dbcontext scaffold "ConnectionString" Microsoft.EntityFrameworkCore.SqlServer -o Models

When to use:
- Code First: New projects, full control, team collaboration
- Database First: Legacy databases, DBA-managed schemas
3What are Migrations? How to use them?▼
Migrations are version control for your database schema. They track changes to your model and generate SQL to update the database.

Common Commands:
dotnet ef migrations add AddProductTable     // Create migration
dotnet ef database update                     // Apply to database
dotnet ef migrations remove                   // Remove last migration
dotnet ef database update PreviousMigration   // Rollback
dotnet ef migrations list                     // List all migrations
dotnet ef migrations script                   // Generate SQL script

Workflow:
1. Modify your model class (add property, new class, etc.)
2. Run: dotnet ef migrations add MigrationName
3. Review generated migration file
4. Run: dotnet ef database update

Generated Migration:
public partial class AddProductTable : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.CreateTable(
            name: "Products",
            columns: table => new
            {
                Id = table.Column<int>(nullable: false)
                    .Annotation("SqlServer:Identity", "1, 1"),
                Name = table.Column<string>(maxLength: 200),
                Price = table.Column<decimal>(type: "decimal(18,2)")
            },
            constraints: table => table.PrimaryKey("PK_Products", x => x.Id));
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropTable(name: "Products");
    }
}

Best Practices:
- Give meaningful migration names
- Review generated SQL before applying to production
- Use dotnet ef migrations script for production deployments
- Never edit applied migrations
4What is Lazy Loading vs Eager Loading vs Explicit Loading?▼
Three strategies for loading related data:

EAGER LOADING (Include) - Load related data WITH the query:
var orders = await _context.Orders
    .Include(o => o.Customer)           // Load Customer
    .Include(o => o.OrderItems)         // Load OrderItems
        .ThenInclude(oi => oi.Product)  // Load Product inside OrderItem
    .ToListAsync();

// SQL: JOIN query - ONE database call
// Best when: You KNOW you need related data

LAZY LOADING - Load related data WHEN accessed:
// Setup: Install Microsoft.EntityFrameworkCore.Proxies
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseLazyLoadingProxies().UseSqlServer(connStr));

// Properties must be virtual:
public class Order
{
    public virtual Customer Customer { get; set; }  // Loaded on first access
    public virtual ICollection<OrderItem> Items { get; set; }
}

var order = await _context.Orders.FindAsync(1);  // 1 query
var name = order.Customer.Name;  // ANOTHER query triggered here!

// Problem: N+1 query issue (many small queries)
// Best when: You MIGHT need related data

EXPLICIT LOADING - Load related data ON DEMAND:
var order = await _context.Orders.FindAsync(1);

// Load explicitly when needed:
await _context.Entry(order)
    .Reference(o => o.Customer)
    .LoadAsync();

await _context.Entry(order)
    .Collection(o => o.OrderItems)
    .LoadAsync();

// Best when: You decide at runtime whether to load

| Strategy | Queries | When to use              | Risk           |
|----------|---------|--------------------------|----------------|
| Eager    | 1 (JOIN)| Know you need data       | Over-fetching  |
| Lazy     | N+1     | Might need data          | N+1 problem    |
| Explicit | On demand| Conditional loading     | Manual control |

Best Practice: Use Eager Loading (Include) in most cases.
5What is DbContext lifetime? Why Scoped?▼
DbContext should be registered as SCOPED (one instance per HTTP request).

Registration:
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));
// Default lifetime: Scoped

Why SCOPED (not Singleton or Transient):
- Scoped: One DbContext per request → tracks changes within request → disposed after
- Singleton: DANGEROUS! Not thread-safe, stale data, memory leaks
- Transient: New instance every injection → can't track changes across services

Scoped behavior:
Request 1: Controller → Service → Repository (ALL get SAME DbContext)
Request 2: Gets a NEW DbContext

Why this matters:
public class OrderService
{
    private readonly AppDbContext _context;  // Same instance as repository

    public void CreateOrder(Order order)
    {
        _context.Orders.Add(order);
        _context.SaveChanges();  // Saves ALL tracked changes in this request
    }
}

DbContext is NOT thread-safe:
- Never share across threads
- Never use Singleton for DbContext
- For background services, create scope manually:
using var scope = _serviceProvider.CreateScope();
var context = scope.ServiceProvider.GetRequiredService<AppDbContext>();
6What is Fluent API vs Data Annotations?▼
Both configure how EF Core maps classes to database. Fluent API is more powerful.

DATA ANNOTATIONS (on model class):
public class Product
{
    [Key]
    public int Id { get; set; }

    [Required]
    [MaxLength(200)]
    public string Name { get; set; }

    [Column(TypeName = "decimal(18,2)")]
    public decimal Price { get; set; }

    [ForeignKey("Category")]
    public int CategoryId { get; set; }
    public Category Category { get; set; }
}

FLUENT API (in DbContext.OnModelCreating):
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>(entity =>
    {
        entity.HasKey(p => p.Id);
        entity.Property(p => p.Name).IsRequired().HasMaxLength(200);
        entity.Property(p => p.Price).HasColumnType("decimal(18,2)");

        // Relationships
        entity.HasOne(p => p.Category)
              .WithMany(c => c.Products)
              .HasForeignKey(p => p.CategoryId)
              .OnDelete(DeleteBehavior.Restrict);

        // Index
        entity.HasIndex(p => p.Name).IsUnique();

        // Seed data
        entity.HasData(new Product { Id = 1, Name = "Phone", Price = 999 });
    });
}

Fluent API can do MORE:
- Complex relationships
- Composite keys
- Table splitting
- Owned types
- Query filters (soft delete)
- Shadow properties

Best Practice: Use Fluent API for relationships and complex config.
Use Data Annotations for simple validation ([Required], [MaxLength]).
7How does Change Tracking work in EF Core?▼
Change Tracking monitors entity states and generates appropriate SQL on SaveChanges().

Entity States:
- Added      → INSERT
- Modified   → UPDATE
- Deleted    → DELETE
- Unchanged  → No SQL
- Detached   → Not tracked

Example:
// Added state
var product = new Product { Name = "Phone", Price = 999 };
_context.Products.Add(product);  // State: Added
await _context.SaveChangesAsync();  // INSERT INTO Products...

// Modified state
var product = await _context.Products.FindAsync(1);  // State: Unchanged
product.Price = 899;  // State: Modified (auto-detected)
await _context.SaveChangesAsync();  // UPDATE Products SET Price = 899 WHERE Id = 1

// Deleted state
var product = await _context.Products.FindAsync(1);
_context.Products.Remove(product);  // State: Deleted
await _context.SaveChangesAsync();  // DELETE FROM Products WHERE Id = 1

Disable tracking (read-only queries - better performance):
var products = await _context.Products
    .AsNoTracking()  // No change tracking = faster
    .Where(p => p.Price > 100)
    .ToListAsync();

// Use AsNoTracking for:
// - Read-only queries (display lists, reports)
// - API GET endpoints
// - When you don't need to update the data
8What is Repository Pattern with EF Core?▼
Repository Pattern abstracts data access logic behind an interface.

Interface:
public interface IRepository<T> where T : class
{
    Task<T> GetByIdAsync(int id);
    Task<IEnumerable<T>> GetAllAsync();
    Task AddAsync(T entity);
    void Update(T entity);
    void Delete(T entity);
    Task SaveAsync();
}

Implementation:
public class Repository<T> : IRepository<T> where T : class
{
    private readonly AppDbContext _context;
    private readonly DbSet<T> _dbSet;

    public Repository(AppDbContext context)
    {
        _context = context;
        _dbSet = context.Set<T>();
    }

    public async Task<T> GetByIdAsync(int id) => await _dbSet.FindAsync(id);
    public async Task<IEnumerable<T>> GetAllAsync() => await _dbSet.ToListAsync();
    public async Task AddAsync(T entity) => await _dbSet.AddAsync(entity);
    public void Update(T entity) => _dbSet.Update(entity);
    public void Delete(T entity) => _dbSet.Remove(entity);
    public async Task SaveAsync() => await _context.SaveChangesAsync();
}

Registration:
builder.Services.AddScoped(typeof(IRepository<>), typeof(Repository<>));

Usage in Controller:
public class ProductController : Controller
{
    private readonly IRepository<Product> _repo;

    public ProductController(IRepository<Product> repo) { _repo = repo; }

    public async Task<IActionResult> Index()
    {
        var products = await _repo.GetAllAsync();
        return View(products);
    }
}

Benefits:
- Testable (mock IRepository in unit tests)
- Swappable (change DB without changing controllers)
- Single Responsibility (controller doesn't know about EF)

Debate: Some argue DbContext IS already a repository + unit of work.
Use Repository when: Multiple data sources, complex queries, need abstraction.
9IEnumerable vs IQueryable in EF Core?▼
IEnumerable (client-side filtering):
IEnumerable<Product> products = _context.Products;
var expensive = products.Where(p => p.Price > 100).ToList();
// SQL: SELECT * FROM Products (loads ALL rows)
// Then filters in C# memory — SLOW for large tables!

IQueryable (server-side filtering):
IQueryable<Product> products = _context.Products;
var expensive = products.Where(p => p.Price > 100).ToList();
// SQL: SELECT * FROM Products WHERE Price > 100
// Filters at database — FAST!

Key Rule:
- Keep as IQueryable as long as possible
- Call .ToList() / .ToListAsync() only at the end

Good pattern:
public IQueryable<Product> GetProducts()
{
    return _context.Products;  // Returns IQueryable
}

// Caller adds more filters (all translated to SQL):
var result = await _repo.GetProducts()
    .Where(p => p.Category == "Electronics")
    .OrderBy(p => p.Name)
    .Skip(20).Take(10)
    .ToListAsync();  // ONE optimized SQL query

Bad pattern:
public List<Product> GetProducts()
{
    return _context.Products.ToList();  // Loads ALL into memory
}
// Caller can't add efficient DB filters anymore!
10What is N+1 Query Problem?▼
N+1 Problem: 1 query to get parent records + N queries to get child records for each parent.

Problem:
var orders = await _context.Orders.ToListAsync();  // 1 query (get 100 orders)

foreach (var order in orders)
{
    var customer = order.Customer.Name;  // 100 separate queries! (lazy loading)
}
// Total: 101 queries for 100 orders!

Solution - Eager Loading:
var orders = await _context.Orders
    .Include(o => o.Customer)  // JOIN in single query
    .ToListAsync();
// Total: 1 query with JOIN

Solution - Projection (Select):
var orders = await _context.Orders
    .Select(o => new OrderDto
    {
        Id = o.Id,
        CustomerName = o.Customer.Name,  // EF generates efficient JOIN
        Total = o.OrderItems.Sum(i => i.Price)
    })
    .ToListAsync();
// Total: 1 optimized query

How to detect:
- Enable EF Core logging
- Use tools like MiniProfiler
- Watch for multiple similar queries in logs

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connStr)
           .LogTo(Console.WriteLine, LogLevel.Information)
           .EnableSensitiveDataLogging());
11What are Global Query Filters (Soft Delete)?▼
Global Query Filters automatically apply a WHERE clause to all queries for an entity.

Common use: Soft Delete (mark as deleted instead of actually deleting)

Model:
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public bool IsDeleted { get; set; }  // Soft delete flag
}

Configure filter:
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    // All queries automatically add WHERE IsDeleted = 0
    modelBuilder.Entity<Product>()
        .HasQueryFilter(p => !p.IsDeleted);
}

Usage:
// Automatically excludes deleted products:
var products = await _context.Products.ToListAsync();
// SQL: SELECT * FROM Products WHERE IsDeleted = 0

// Soft delete:
product.IsDeleted = true;
await _context.SaveChangesAsync();
// Product still in DB but hidden from queries

// Include deleted (bypass filter):
var allProducts = await _context.Products
    .IgnoreQueryFilters()
    .ToListAsync();
// SQL: SELECT * FROM Products (includes deleted)

Other uses:
- Multi-tenancy: .HasQueryFilter(p => p.TenantId == currentTenantId)
- Active records: .HasQueryFilter(p => p.IsActive)
12How to handle Transactions in EF Core?▼
SaveChanges() is already a transaction (all or nothing).

For multiple SaveChanges or cross-context operations, use explicit transactions:

using var transaction = await _context.Database.BeginTransactionAsync();
try
{
    // Operation 1
    var order = new Order { CustomerId = 1, Total = 500 };
    _context.Orders.Add(order);
    await _context.SaveChangesAsync();

    // Operation 2
    var payment = new Payment { OrderId = order.Id, Amount = 500 };
    _context.Payments.Add(payment);
    await _context.SaveChangesAsync();

    // Operation 3
    var inventory = await _context.Inventory.FindAsync(productId);
    inventory.Quantity -= 1;
    await _context.SaveChangesAsync();

    await transaction.CommitAsync();  // All succeed
}
catch
{
    await transaction.RollbackAsync();  // All fail
    throw;
}

When to use explicit transactions:
- Multiple SaveChanges calls that must be atomic
- Cross-service operations
- When you need the ID from first save for second operation

SaveChanges alone is enough when:
- All changes are in single SaveChanges call
- _context.Orders.Add(order);
- _context.OrderItems.AddRange(items);
- await _context.SaveChangesAsync();  // Already atomic!
